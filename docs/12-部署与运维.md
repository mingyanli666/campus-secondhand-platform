# 第一部分：部署架构

```
                          ┌─────────────────────────────────┐
   浏览器  ──── :80 ────▶ │  frontend (nginx:1.27-alpine)   │
                          │  ├── /           静态文件 + SPA 回退 │
                          │  ├── /api/    ──▶ 反向代理到后端     │
                          │  └── /uploads/ ─▶ 反向代理到后端     │
                          └───────────────┬─────────────────┘
                                          │ 内网（docker network: udp）
                          ┌───────────────▼─────────────────┐
                          │  backend (JRE 17 + jar)         │
                          │  :8080  仅容器内可达，不对外暴露   │
                          └───┬─────────────────────┬───────┘
                              │                     │
                  ┌───────────▼──────┐   ┌──────────▼────────┐
                  │  mysql:8.0       │   │  redis:7-alpine   │
                  │  命名卷持久化      │   │  AOF 持久化        │
                  │  healthcheck     │   │  healthcheck      │
                  └──────────────────┘   └───────────────────┘
```

**只有 nginx 对外暴露端口。** MySQL 和 Redis 都在内网，宿主机的 3306 / 6379 不受影响 ——
这一点在开发机上尤其重要：本机可能已经装了 MySQL 占用 3306，容器化后不会有端口冲突。

# 第二部分：为什么容器化

## 2.1 容器化之前的问题

项目的 README 原本是这样写的：

```bash
mysql -uroot -p < sql/init.sql        # 需要本机装 MySQL 8
docker run -d --name udp-redis ...    # 需要本机装 Docker
# 改 application.yml 里的数据库密码
cd backend && mvn spring-boot:run     # 需要本机装 JDK 17 + Maven
cd frontend && npm install && npm run dev   # 需要本机装 Node 20
```

**5 个前置条件、7 条命令、还要手工改配置文件。** 换一台机器就要重来一遍，
而且"我这里能跑"是最经典的问题来源。

容器化之后：

```bash
cp .env.example .env
docker compose up -d --build
```

**2 条命令，零前置条件**（只要有 Docker）。

## 2.2 容器化解决的四个问题

| 问题 | 解法 |
| --- | --- |
| 环境不一致 | 依赖全部固化在镜像里，JDK / Node / MySQL 版本都写死 |
| 启动顺序不对 | `healthcheck` + `depends_on: condition: service_healthy` |
| 数据随容器丢失 | 命名卷（MySQL 数据、Redis 数据、上传图片） |
| 配置散落各处 | 环境变量集中到 `.env`，密钥不进版本库 |

# 第三部分：后端镜像的多阶段构建

```dockerfile
# ---------- 阶段一：构建 ----------
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /build
COPY pom.xml .
RUN mvn -B dependency:go-offline      # ← 先只拷依赖清单
COPY src ./src
RUN mvn -B clean package -DskipTests

# ---------- 阶段二：运行 ----------
FROM eclipse-temurin:17-jre-alpine
COPY --from=build --chown=app:app /build/target/*.jar app.jar
USER app
ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar app.jar"]
```

## 3.1 为什么分两个阶段

构建阶段需要 Maven + JDK + 全部依赖源码，但这些东西在运行阶段**一点用都没有** ——
运行时只需要一个 JRE 和一个 jar。

以下是本项目**实际构建出来的**体积（`docker images` 实测）：

```
构建阶段基础镜像  maven:3.9-eclipse-temurin-17   775 MB
运行阶段基础镜像  eclipse-temurin:17-jre-alpine    257 MB
应用本身（jar + 日志 + 上传目录）                   53 MB

单阶段（直接基于 maven 镜像）  ≈ 830 MB
多阶段（JRE + 应用）            362 MB   ← 实测
```

前端镜像更小：`nginx:1.27-alpine` 74.5MB + 页面产物 ≈ **75.8 MB**。

**这还是个安全收益**：最终镜像里没有 Maven、没有源码、没有构建工具。可以验证：

```bash
$ docker compose exec backend which mvn
（无输出 —— 没有 Maven）
$ docker compose exec backend ls /build
ls: cannot access '/build': No such file or directory
（源码目录也不在运行镜像里）
```

## 3.2 为什么先 COPY pom.xml 再 COPY src

Docker 按层缓存：**某一层的输入没变，就直接复用缓存**。

```dockerfile
COPY pom.xml .                    # ← 依赖清单，很少变
RUN mvn dependency:go-offline     # ← 下载全部依赖，很慢
COPY src ./src                    # ← 业务代码，经常变
RUN mvn package                   # ← 编译打包，很快
```

如果写成 `COPY . .` 再 `mvn package`，那么**改一行代码就会导致依赖重新下载**
（因为 `COPY . .` 这一层的输入变了，后面的层全部失效）。

分开之后，改代码只触发最后两层重建。

**面试会问这个**：为什么 Dockerfile 里的 COPY 顺序有讲究？答"利用层缓存，
把变化频率低的放前面"。前端的 `COPY package*.json` 再 `npm ci` 是同一个道理。

## 3.3 两个容易忽略的细节

**① 不用 root 跑应用**

```dockerfile
RUN addgroup -S app && adduser -S app -G app && chown -R app:app /app
USER app
```

容器被攻破时，攻击者拿到的是普通用户权限，不能改文件、不能装东西。

**② 让 JVM 按容器内存算堆大小**

```dockerfile
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75.0"
```

Java 老版本的 `Runtime.availableProcessors()` 和内存感知是看**宿主机**的。
容器限了 512MB，JVM 却按宿主机 16GB 去算堆（默认 1/4 = 4GB），一跑就 OOM。
`MaxRAMPercentage` 让 JVM 按容器实际可用内存来算。

# 第四部分：docker compose 编排

## 4.1 启动顺序：不能只写 depends_on

**这是最容易出错的地方。** 下面这种写法是错的：

```yaml
backend:
  depends_on:
    - mysql       # ❌
```

`depends_on` 只保证「容器**启动**了」，不保证「数据库**能用了**」。
MySQL 容器启动后还要初始化数据目录，**要几十秒才能真正接受连接**。
这期间后端去连库，会直接报连接失败然后退出。

正确写法是配合健康检查：

```yaml
mysql:
  healthcheck:
    # mysqladmin ping 通了，才算真的能接受连接
    test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -uroot -p$$MYSQL_ROOT_PASSWORD --silent"]
    interval: 10s
    timeout: 5s
    retries: 10
    start_period: 40s     # ← 启动初期不健康不算失败，给足初始化时间

backend:
  depends_on:
    mysql:
      condition: service_healthy    # ✅ 等到 healthy 才启动
    redis:
      condition: service_healthy
```

**`start_period` 是必须的**。不加的话，MySQL 初始化那几十秒会被记为失败，
重试次数很快耗尽，容器被判为 unhealthy。

**`$$` 的转义**：compose 会把 `$MYSQL_ROOT_PASSWORD` 自己展开，
写成 `$$` 才是让**容器内的 shell** 去展开。

## 4.2 数据卷：哪些数据必须持久化

| 数据 | 挂载方式 | 不挂会怎样 |
| --- | --- | --- |
| MySQL 数据目录 | 命名卷 `mysql-data` | 容器重建后**所有业务数据没了** |
| Redis AOF | 命名卷 `redis-data` | 浏览量计数丢失（影响小） |
| 上传的图片 | 命名卷 `upload-data` | 用户上传的商品图全变裂图 |
| 日志 | **宿主机目录** `./logs` | 排查不了问题 |

**命名卷 vs 宿主机目录**的取舍：

- **命名卷**给数据库：读写性能好，由 Docker 管理，跨平台不用操心权限
- **宿主机目录**给日志：运维要能直接在宿主机上 `tail -f`，
  也能被外部日志采集工具扫到

### 一个真部署才暴露的坑：演示图片是空的

演示数据（`sql/demo-data.sql`）里商品封面写的是 `/uploads/demo/demo-01.png`，
而这些图片在仓库里（`backend/uploads/demo/`，24 张），**不在数据库里**。

容器第一次启动时，`upload-data` 是个**全新的空卷** —— 24 张演示图一张都不在，
结果就是所有商品卡片全是裂图：

```bash
$ docker compose exec backend ls /app/uploads/demo
ls: cannot access '/app/uploads/demo': No such file or directory
```

改法是把这个目录单独绑进去：

```yaml
volumes:
  - upload-data:/app/uploads                          # 用户上传的图片
  - ./backend/uploads/demo:/app/uploads/demo:ro       # ← 演示图，只读
```

**这种问题本地开发时完全看不到** —— 开发机上 `backend/uploads/demo/` 就在项目目录里，
直接就访问到了。只有真打包成镜像才会暴露。

### 为什么刻意不写 container_name

```yaml
services:
  backend:
    # container_name: udp-backend      ← 不要写
```

写死容器名有两个问题：

1. **`docker compose up --scale backend=2` 直接报名字冲突**，扩容不了
2. **容易和本机已有的同名容器撞车** —— 这个项目里就撞上了：
   之前手工 `docker run --name udp-redis` 建过一个 Redis，
   compose 再起 `udp-redis` 就报 `Conflict. The container name is already in use`

不写的话 compose 用 `项目名-服务名-序号` 自动命名，
而 `docker compose exec backend sh` / `logs -f backend` 照样按**服务名**用，不受影响。

## 4.3 只有 nginx 暴露端口

```yaml
frontend:
  ports:
    - "${WEB_PORT:-80}:80"
# backend 没有 ports，只有内网可达
```

后端不对外暴露有三个好处：
1. **减少攻击面** —— 外部扫不到 8080 端口
2. **避免端口冲突** —— 开发机上 8080 可能被别的服务占了
3. **统一入口** —— 所有流量都过 nginx，鉴权、限流、日志都在一处

# 第五部分：nginx 的四个关键配置

## 5.1 SPA history 回退（不加就 404）

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

Vue Router 用的是 **history 模式**，`/product/list` 这种路径在服务器上
**并不存在对应的文件**。用户访问 / 刷新这个地址时：

```
浏览器请求 /product/list
   ↓
nginx 去 /usr/share/nginx/html/product/list 找文件 → 找不到 → 404
```

`try_files` 的意思是：先找文件，再找目录，都没有就返回 `index.html`，
让**前端路由**去处理这个路径。

**这是部署 SPA 最常见的坑**，本地 `npm run dev` 时 Vite 的 dev server 帮你兜住了，
所以开发时完全看不出来。

## 5.2 静态资源强缓存，入口文件不缓存

```nginx
# 带内容哈希的资源：缓存一年
location /assets/ {
    expires    1y;
    add_header Cache-Control "public, immutable";
}

# 入口文件：绝不缓存
location = /index.html {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
    expires    off;
}
```

**为什么两者必须配对？**

Vite 产出的文件名带内容哈希：`index-Bta6tndf.js`。内容变了文件名就变，
所以可以放心让浏览器缓存一年 —— 反正发新版本时文件名不一样。

但 `index.html` 里写的正是这些文件名：

```html
<script type="module" crossorigin src="/assets/index-Bta6tndf.js"></script>
```

**如果入口文件也被缓存住，用户永远拿不到新的文件名，会一直加载旧版本。**
这就是"发版了但用户说没更新"的经典原因。

## 5.3 上传体积上限

```nginx
client_max_body_size 10m;
```

nginx 默认只允许 1MB。**不改的话，前端传超过 1MB 的图会拿到 413，
而后端根本收不到请求** —— 你会以为是自己代码的问题，其实请求被 nginx 拦在了前面。

项目里后端配的是 10MB（`spring.servlet.multipart.max-file-size`），
两边必须一致。

## 5.4 透传真实客户端 IP

```nginx
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

不加这三行，后端日志里看到的客户端 IP **全都是 nginx 容器的内网 IP**。
线上有人刷接口时，你根本定位不到是谁。

## 5.5 gzip

```nginx
gzip on;
gzip_min_length 1024;
gzip_types text/css application/javascript application/json image/svg+xml;
```

前端产物里 element chunk 未压缩有 800+ KB，开了 gzip 传输量能降到 1/3 左右。

`gzip_min_length 1024` 是为了不给小文件浪费 CPU —— 一个 200 字节的响应
压完可能更大。

# 第六部分：配置与密钥管理

## 6.1 三层配置的职责

| 位置 | 放什么 | 是否进版本库 |
| --- | --- | --- |
| `application.yml` | 默认值，全部写成 `${ENV:默认值}` | ✅ 提交 |
| `application-local.yml` | 本机数据库密码 | ❌ gitignore |
| `.env` | 容器部署的密码与密钥 | ❌ gitignore |
| `.env.example` | 同上，但填的是占位符 | ✅ 提交 |

## 6.2 所有会变的东西都要抽成环境变量

改造前的 `application.yml` 里数据库地址是写死的：

```yaml
url: jdbc:mysql://localhost:3306/used_digital_platform?...
```

**本机跑没问题，进容器就废了** —— 容器里的 `localhost` 指的是容器自己，
不是 MySQL 容器。改成：

```yaml
url: jdbc:mysql://${DB_HOST:localhost}:${DB_PORT:3306}/${DB_NAME:used_digital_platform}?...
```

compose 里传 `DB_HOST: mysql`（服务名，Docker 内网 DNS 能解析）。

> **`${DB_HOST:localhost}` 这个写法很关键**：冒号后面是默认值。
> 这样本地开发不设环境变量也能跑，容器里设了就覆盖 ——
> 一套配置同时满足两种环境，不需要维护两份。

## 6.3 JWT 密钥必须强制设置

```yaml
JWT_SECRET: ${JWT_SECRET:?JWT_SECRET 未设置，请先 cp .env.example .env 并填好}
```

`${VAR:?message}` 的语义是：**没设就报错退出，并把 message 打出来**。

**为什么不用 `${JWT_SECRET:默认值}`？**

`application.yml` 里有一个默认密钥（为了让本地开发方便）：

```yaml
secret: ${JWT_SECRET:used-digital-platform-jwt-secret-key-2026-graduation-project}
```

这个默认值**在公开仓库里**。HS256 是对称加密，拿到密钥就能签发任意用户的 token：

```
伪造一个 role=ADMIN 的 token → 直接拿到管理员权限
```

所以生产部署时**必须**覆盖，而且要用"不设置就启动失败"的方式强制，
不能给一个"看起来能用"的默认值 —— 那样大概率就一直用着默认值跑下去了。

生成方式：

```bash
openssl rand -base64 48
```

# 第七部分：日志规范

## 7.1 只用 logging.level 是不够的

原来的配置只有一行：

```yaml
logging:
  level:
    com.digital.platform: debug
```

**这只管级别，管不了**：日志写到哪、写多大、留多久、怎么压缩、错误怎么单独摘出来。

## 7.2 logback-spring.xml 解决的六件事

```xml
<appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>${LOG_DIR}/${APP_NAME}.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
        <fileNamePattern>${LOG_DIR}/history/${APP_NAME}.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
        <maxFileSize>50MB</maxFileSize>
        <maxHistory>30</maxHistory>
        <totalSizeCap>2GB</totalSizeCap>
    </rollingPolicy>
</appender>
```

| 配置 | 解决什么 |
| --- | --- |
| `SizeAndTimeBasedRollingPolicy` | 按天切 **且** 单文件超 50MB 再切 |
| `maxHistory=30` | 只留 30 天，自动删旧的 |
| `.gz` | 历史日志压缩，省磁盘 |
| `totalSizeCap=2GB` | 总量封顶，**防止日志写爆磁盘** |
| `ERROR_FILE` + `ThresholdFilter` | 错误日志单独一份 |
| `AsyncAppender` | 异步写，不阻塞业务线程 |

### 为什么按天+按大小两种都要

- **只按天切**：某天线上出问题刷了 10GB 日志，磁盘直接满
- **只按大小切**：日志文件叫 `app.1.log`、`app.2.log`，找"昨天下午三点的日志"要逐个翻

两个一起用：文件名里既有日期又有序号。

### 为什么错误日志要单独一个文件

运维侧可以**只对 `error.log` 配告警**，不用被海量 INFO 淹没；
也可以只把 `error.log` 接进日志平台，省存储和费用。

### AsyncAppender 的取舍

```xml
<queueSize>512</queueSize>
<discardingThreshold>0</discardingThreshold>   <!-- 队列满时也不丢 -->
<neverBlock>false</neverBlock>                  <!-- 宁可阻塞也不丢 -->
```

`discardingThreshold` 默认值是队列的 20%，也就是**队列快满时会主动丢弃
INFO 以下的日志**。排查线上问题时最怕"日志少了一段"，
所以设成 0 表示一条都不丢。

代价是队列真满时会阻塞业务线程 —— 但因为写文件本身很快，实际几乎不会发生。

### 控制台的颜色只在开发环境开

```xml
<springProfile name="local,dev,default">
    <root level="INFO">
        <appender-ref ref="CONSOLE_COLOR"/>
        ...
```

```xml
<springProfile name="prod,docker">
    <root level="INFO">
        <appender-ref ref="CONSOLE_PLAIN"/>    <!-- 不带颜色 -->
```

**ANSI 转义码会污染 `docker logs` 输出**，也会让日志采集工具解析出乱码。

## 7.3 生产环境关掉 SQL 日志

```yaml
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.nologging.NoLoggingImpl
```

两个原因：一是量大（每个请求都打一堆 SQL），
二是 **SQL 参数里带用户隐私**（手机号、邮箱、token）。

# 第八部分：健康检查

## 8.1 Actuator 只暴露 health

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health      # ← 不是 "*"
  endpoint:
    health:
      show-details: never    # ← 不返回数据库连接串等细节
```

**为什么不能图省事写 `include: "*"`？**

Actuator 的 `/env`、`/configprops`、`/beans` 端点会**把配置原样吐出来**，
包括：

```
spring.datasource.password = udb-pass-2026
platform.jwt.secret         = ZGV2LW9ubHkt...
```

**等于给攻击者开了一个"读取所有密钥"的接口。**

## 8.2 Redis 从健康检查里摘掉

```yaml
management:
  health:
    redis:
      enabled: false
```

项目里 Redis 挂了会**自动降级查库，业务完全可用**（见第 11 篇）。
如果把 Redis 算进健康检查，Redis 一挂整个服务就被标记为 unhealthy，
容器编排会不断重启它 —— **本来只是掉了缓存，结果变成了服务不可用**。

**健康检查的判据要和"服务能不能对外提供服务"对齐**，不是"所有依赖都正常"。

## 8.3 健康检查驱动启动顺序

```yaml
backend:
  healthcheck:
    test: ["CMD", "curl", "-fsS", "http://localhost:8080/actuator/health"]
    start_period: 60s      # Spring Boot 启动要时间
```

而且 `/actuator/health` 会**真的去 ping 数据库**，
比"端口通了"这种判据靠谱得多。

# 第九部分：CI 流水线

## 9.1 三个任务

```
push / PR
   │
   ├── backend     JDK 17 + Maven 缓存 → mvn test（15 个单测）
   │
   ├── frontend    Node 20 + npm 缓存 → lint → format:check → test:cov → build
   │
   └── smoke  ──▶ 依赖上面两个都通过
                  docker compose up -d --build --wait
                  curl 验证接口
```

## 9.2 `--wait` 是个好东西

```yaml
- run: docker compose up -d --build --wait
```

`--wait` 会**一直等到所有带 healthcheck 的服务变成 healthy**，
任何一个不健康就直接失败返回。

不用自己写 `sleep 30` 再轮询 —— 那种写法要么等太久拖慢 CI，
要么等太短导致偶发失败。

## 9.3 为什么必须有 smoke 这一步

**"单元测试全绿"不等于"部署起来能跑"。**

这个项目里就踩过：引入了 Prettier 之后，ESLint 通过、Prettier 通过、
单元测试通过，**但生产构建直接失败**（Prettier 把多语句内联事件处理器
拆行时丢掉了分号）。

只有真的把整套服务拉起来、真的打一次接口，才算验证完。

## 9.4 缓存

```yaml
- uses: actions/setup-java@v4
  with:
    cache: maven              # Maven 依赖缓存

- uses: actions/setup-node@v4
  with:
    cache: npm
    cache-dependency-path: frontend/package-lock.json
```

不缓存的话，每次 CI 都要重新下载几百 MB 依赖。

## 9.5 并发控制

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

同一个分支连续 push 时，取消上一次还没跑完的流水线，省 CI 额度。

# 第十一部分：常见故障排查

## 11.1 后端起不来，日志报连不上数据库

```
Communications link failure
```

**按顺序查**：

```bash
# ① MySQL 健康吗？
docker compose ps
# STATUS 里带 "(healthy)" 才说明能连

# ② 是不是 depends_on 写成了列表形式（没有 condition）？
#    那后端会在 MySQL 初始化完成前就去连库
```

## 11.2 前端页面 404

```
刷新 /product/list 出现 404
```

**nginx 少了 SPA 回退**：

```nginx
location / {
    try_files $uri $uri/ /index.html;   # ← 少这一行
}
```

## 11.3 图片上传报 413

```
413 Request Entity Too Large
```

**nginx 的 `client_max_body_size` 比后端小。** nginx 默认 1MB，
后端配的是 10MB，请求在 nginx 就被拦下了，后端日志里什么都看不到。

## 11.4 发版后用户说还是旧页面

**`index.html` 被缓存了。**

检查 nginx 配置：

```nginx
location = /index.html {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
}
```

## 11.5 改了 sql/init.sql 但没生效

`docker-entrypoint-initdb.d` **只在数据目录为空时执行**，
也就是只在**第一次创建容器**时跑。之后改了脚本也不会重跑。

```bash
docker compose down -v      # 删掉数据卷
docker compose up -d --build
```

**注意这会清空数据库。**

## 11.6 容器时间差 8 小时

镜像里没装 tzdata，或者 `TZ` 环境变量没传。

```dockerfile
RUN apk add --no-cache tzdata \
    && cp /usr/share/zoneinfo/Asia/Shanghai /etc/localtime
```

```yaml
environment:
  TZ: Asia/Shanghai
```

**影响不只是日志时间戳**：项目的浏览量回写是每 5 分钟一次的定时任务，
时区错乱会让"5 分钟"变成"8 小时 5 分钟"。

## 11.7 中文全变成乱码（最隐蔽的一个，实际踩到了）

**现象**：部署后页面上所有中文变成 `æ‰‹æœº` 这种样子，
但 Java 代码里写死的字符串（比如"操作成功"）却是正常的。

**这个对比就是定位的突破口** —— 常量正常、数据库读出来的乱码，
说明问题既不在 HTTP 层也不在前端，而在**数据落库时的字符集**。

### 第一步：看数据库里存的原始字节，别看字符串

```sql
SELECT id, name, HEX(name) FROM sys_category WHERE id = 1;
```

```
本机 MySQL：E6898BE69CBA                     ← 正确
容器 MySQL：C3A6E280B0E280B9C3A6C593C2BA     ← 乱码
```

「手机」的正确 UTF-8 是 `E6 89 8B E6 9C BA`。坏掉的那串把每个字节重新编码了一遍：

```
E6 -> C3A6    (æ)
89 -> E280B0  (‰)
8B -> E280B9  (‹)
9C -> C593    (œ)
BA -> C2BA    (º)
```

`0x89 -> ‰`、`0x8B -> ‹`、`0x9C -> œ` —— 这是 **CP1252** 的映射表。
UTF-8 的字节被按 CP1252 解码、再存成 UTF-8，这就是"双重编码"。

### 第二步：为什么偏偏是 CP1252

因为 **MySQL 的 `latin1` 并不是 ISO-8859-1，它实际是 CP1252**。
这是 MySQL 一个很老的兼容性包袱。

### 第三步：谁在用 latin1 读文件

官方镜像的 entrypoint 首次启动时会执行 `/docker-entrypoint-initdb.d/` 下的
SQL 文件，但它调用的客户端**没有指定字符集**：

```bash
# /usr/local/bin/docker-entrypoint.sh 第 258 行
mysql --defaults-extra-file=<(...) --protocol=socket -uroot -hlocalhost --comments "$@"
#                                                                ↑ 没有 --default-character-set
```

客户端的默认字符集是从 **locale** 推导的。容器里不设 locale 就退回 latin1：

```bash
$ docker compose exec mysql mysql -uroot -p*** -N -B -e "SELECT @@character_set_client"
latin1          ← 就是它
```

### 修法：给 MySQL 容器设 UTF-8 locale

```yaml
mysql:
  environment:
    LANG: C.UTF-8        # ← 这一行
```

实测对比：

| 设置 | `character_set_client` |
| --- | --- |
| 不设 | `latin1` ❌ |
| `LANG=C.UTF-8` | `utf8mb4` ✅ |
| `LANG=en_US.UTF-8` | `utf8mb4` ✅ |

**改完必须删卷重来**，因为 `docker-entrypoint-initdb.d` 只在数据目录为空时执行：

```bash
docker compose down -v
docker compose up -d --wait

# 验证存进去的字节对不对
docker compose exec mysql mysql -uroot -p*** -N -B \
  -e "SELECT HEX(name) FROM used_digital_platform.sys_category WHERE id=1;"
# 应该输出 E6898BE69CBA
```

### 一个走不通的方案（记下来免得再踩）

第一反应是挂一个 `.cnf` 配置文件：

```yaml
volumes:
  - ./mysql/my.cnf:/etc/mysql/conf.d/charset.cnf:ro
```

**在 Windows 上无效** —— MySQL 会直接忽略它：

```
[Warning] World-writable config file '/etc/mysql/conf.d/charset.cnf' is ignored.
```

原因是 Windows 绑定挂载进来的文件权限是 `0777`，MySQL 出于安全拒绝加载
"所有人可写"的配置文件。**加 `:ro` 也没用** —— 只读挂载不改变权限位。

这个方案在 Linux 上是可行的，但既然 `LANG` 两边都能用，就没必要多挂一个文件。

### 排查这类问题的通用思路

1. **对比"代码里的常量"和"数据库里的数据"** —— 一眼就能区分是传输层还是存储层
2. **看 HEX，别看字符串** —— 终端自己的编码会把水搅浑；
   `E6898BE69CBA` 和 `C3A6E280B0...` 的区别一目了然
3. **认出字节到字符的映射表** —— 认得出 CP1252 / GBK 的特征映射，
   就能反推是哪一步用了什么编码

> 这个坑本地开发时**根本不会遇到** —— 本机 MySQL 是按 README 里的
> `--default-character-set=utf8mb4` 导入的，一直是好的。
> 只有走容器初始化这条路径才会触发。

# 第十二部分：面试怎么讲

## 12.1 30 秒版本

> 我把整个项目做成了容器化部署。原来要装 MySQL、Redis、JDK、Maven、Node
> 五个环境、敲七条命令，现在是 `cp .env.example .env` 加
> `docker compose up -d --build` 两条命令。
>
> 后端和前端都用多阶段构建，镜像从 750MB 降到 190MB 左右；
> 启动顺序靠 healthcheck 保证，不是靠 depends_on；
> nginx 做静态托管和反向代理，只有它对外暴露端口。

## 12.2 常见追问

| 问题 | 怎么答 |
| --- | --- |
| **为什么用多阶段构建？** | 构建要 Maven + JDK + 源码（750MB），运行只要 JRE + jar（190MB）。顺带还有个安全收益：最终镜像里没有源码和构建工具。 |
| **Dockerfile 里 COPY 顺序为什么有讲究？** | 利用层缓存。依赖清单很少变、代码经常变，先 COPY pom.xml 跑一次依赖下载，之后改代码就不会重新下载依赖了。前端先 COPY package*.json 再 npm ci 是同一个道理。 |
| **depends_on 为什么不够？** | 它只保证容器启动了，不保证服务能用了。MySQL 启动后还要初始化数据目录，几十秒内连不上。所以要用 healthcheck + condition: service_healthy，而且必须配 start_period。 |
| **健康检查为什么要摘掉 Redis？** | Redis 挂了业务会自动降级查库，功能完全可用。把它算进健康检查，Redis 一挂整个服务被判定为不健康、被反复重启，本来是掉缓存，结果变成服务不可用。**判据要和"能不能提供服务"对齐。** |
| **index.html 为什么不能缓存？** | 它里面写的是带哈希的资源文件名。缓存住它，用户永远拿不到新的文件名，发版后一直加载旧版本。 |
| **静态资源为什么能缓存一年？** | Vite 产物带内容哈希，内容变文件名就变，不存在"拿到旧内容"的问题。 |
| **Actuator 为什么要限制端点？** | `/env` 和 `/configprops` 会把数据库密码、JWT 密钥原样吐出来，等于开了个读密钥的接口。只暴露 health，而且 `show-details: never`。 |
| **JWT 密钥为什么用 `${VAR:?}`？** | 不设置就启动失败，避免生产环境一直用着仓库里的默认值 —— 那个默认值是公开的，拿到就能伪造管理员 token。 |

## 12.3 简历句式

> 基于 Docker Compose 完成 MySQL / Redis / 后端 / Nginx 四服务编排，
> 一键部署替代原先 5 个前置环境与 7 条手工命令；采用多阶段构建将后端镜像
> 由约 830MB 降至 362MB（实测），前端镜像 75.8MB，均以非 root 用户运行；
> 通过 healthcheck + `condition: service_healthy` 保证启动顺序，
> 用命名卷持久化数据库与上传文件；
> Nginx 配置 SPA history 回退、静态资源强缓存与入口文件不缓存、
> 反向代理及 gzip；
> 接入 GitHub Actions 流水线，包含前后端测试与 `docker compose up --wait`
> 冒烟验证；配置 Actuator 健康检查与 logback 分级滚动日志。
