# 第一部分：需求从一个真实场景说起

用户的描述是：

> 我看到一个专门做商品售卖的人，然后我需要点进他的主页查看有没有发布我心仪的商品。

**这句话里藏了三个信息：**

| 信息 | 说明 |
| --- | --- |
| "专门做商品售卖的人" | 有些卖家不是偶尔出闲置，而是在这个平台上持续卖东西 |
| "点进他的主页" | **需要一个可访问的卖家主页** |
| "有没有我心仪的商品" | 主页的核心内容是**他在卖什么**，不是"他是谁" |

## 1.1 这个功能为什么有价值

**从买家角度：**

```
看到一件心仪的相机
   ↓ 但价格/成色不太合适
   ↓ 点进卖家主页
   ↓ 发现他还有 5 台相机、12 个镜头
   ↓ 一次逛完，不用来回搜
```

**从平台角度：**

一个"有主页"的卖家，比一个只出现在商品详情角落里的昵称，**可信度高得多** ——
买家能看到他卖过多少东西、信誉如何、在哪个学院。

## 1.2 和"个人中心"的区别

项目里已经有 `/user/profile`（个人中心）了，为什么还要做一个卖家主页？

| | 个人中心 `/user/profile` | 卖家主页 `/seller/:id` |
| --- | --- | --- |
| 看的是谁 | **我自己** | **别人** |
| 能看到什么 | 全部资料（含手机、邮箱、账号） | 只看到公开部分 |
| 能做什么 | 改资料、改密码、传头像 | 只读 |
| 数据 | `UserVO` | `UserPublicVO` |

**这是两个完全不同的页面，不是同一个页面的不同入口。** 混在一起是很多项目出隐私事故的根源。

# 第二部分：接口设计

## 2.1 两个公开接口

```
GET /api/seller/{id}            → 卖家公开资料 + 在售/已成交数量
GET /api/seller/{id}/products   → 卖家的在售商品（分页）
```

**为什么拆成两个接口，而不是一个返回全部？**

| 方案 | 问题 |
| --- | --- |
| 一个接口同时返回资料 + 商品列表 | 商品要分页，翻页时会重复返回不变的资料 |
| **两个接口** | ✅ 资料只请求一次，商品翻页只请求列表 |

**为什么是 `/api/seller` 而不是 `/api/user/{id}`？**

`/api/user/**` 现在全是"当前登录用户"的接口（`/api/user/profile`、`/api/user/password`），
**语义是"我的"**。如果混进一个 `GET /api/user/{id}` 看别人的资料，
以后维护的人很容易搞混哪一个是"我"、哪一个是"别人"。

**用一个独立的前缀 `/api/seller`，语义是"卖家"**，和 `/api/user` 彻底分开。

> 路径本身就是一种文档。**`/api/seller/102` 比 `/api/user/102` 更能说明"这是在看别人的公开信息"。**

## 2.2 为什么是公开接口

```java
@PublicApi
@GetMapping("/{id}")
public Result<UserPublicVO> profile(@PathVariable Long id) { ... }
```

**因为"这个卖家靠不靠谱"是浏览阶段的判断，不是交易阶段的判断。**

如果必须登录才能看卖家主页，等于逼着用户在还不确定要不要买的时候先注册 ——
**这是典型的"用注册门槛把自己用户挡在门外"。**

对比一下项目里其他公开接口：

| 接口 | 为什么公开 |
| --- | --- |
| `/api/product/page` | 不登录也能浏览商品 |
| `/api/product/{id}` | 不登录也能看详情 |
| `/api/comment/list` | 不登录也能看别人怎么问的 |
| **`/api/seller/{id}`** | **不登录也能判断卖家是否可信** |

**它们属于同一类：都是"做决定之前需要的信息"。**

# 第三部分：核心问题 —— 公开资料不能等于用户资料

## 3.1 直接复用 `UserVO` 会发生什么

`UserVO` 长这样（节选）：

```java
public class UserVO {
    private Long id;
    private String username;    // ← 登录账号
    private String nickname;
    private String avatar;
    private String phone;       // ← 手机号
    private String email;       // ← 邮箱
    private String role;
    private Integer status;     // ← 账号是否被禁用
    private Integer creditScore;
    private LocalDateTime lastLoginTime;   // ← 最后登录时间
    ...
}
```

**如果直接把 `UserVO` 作为卖家主页的返回值：**

```
GET /api/seller/102
{
  "id": 102,
  "username": "wangba",           ← 登录账号泄漏
  "phone": "13800000102",         ← 手机号泄漏
  "email": "wangba@example.com",  ← 邮箱泄漏
  "status": 1,
  "lastLoginTime": "2026-10-19 ..."
}
```

**后果有多严重？**

| 泄漏字段 | 后果 |
| --- | --- |
| `username` | 有了账号名，下一步就是**撞库**（拿常见密码去试） |
| `phone` | **爬虫扫一遍全站卖家主页，就能收集整个平台的手机号** |
| `email` | 同上，而且会收到大量垃圾邮件 |
| `lastLoginTime` | 能推断出用户的活跃习惯，属于行为数据 |
| `status` | 泄漏平台的封禁情况 |

**最危险的是 `phone` 和 `email`：**

```
写个脚本：for (id = 1; id < 100000; id++) { GET /api/seller/{id} }
       → 几分钟就拿到全站用户的手机号和邮箱
```

**这不是"理论上可能"，这是"只要有这个接口就能做到"。**

## 3.2 解法：为"别人能看的"单独定义一个类型

```java
/**
 * 卖家的公开资料。
 * <p>
 * 和 UserVO 的区别是什么？**UserVO 是"我看我自己"，这个是"我看别人"。**
 * <p>
 * 所以这里刻意**不包含**任何隐私字段：
 * - username —— 登录账号，暴露了就能被拿去撞库/枚举
 * - phone / email —— 联系方式应该由卖家在交易时主动给出，而不是挂在主页上任人采集
 * - status / lastLoginTime —— 账号状态和登录时间属于平台运营数据
 * <p>
 * 只暴露"别的用户需要知道的"：他是谁、信誉如何、在卖什么。
 */
public class UserPublicVO {
    private Long id;
    private String nickname;
    private String avatar;
    private Integer gender;
    private String campus;
    private String intro;
    private Integer creditScore;
    private LocalDateTime createTime;
    private Long onSaleCount;
    private Long soldCount;
}
```

### 为什么用"白名单"而不是"黑名单"

| 思路 | 做法 | 问题 |
| --- | --- | --- |
| 黑名单 | 复用 `UserVO`，用 `@JsonIgnore` 把敏感字段排除 | **新增字段时默认会暴露**，忘记加注解就泄漏 |
| **白名单** | **定义一个新类型，只写要暴露的字段** | **新增字段时默认不会暴露**，忘记加就只是少显示一个 |

**这个区别是本质性的：**

```
黑名单的默认值是"暴露"  → 犯错 = 泄漏
白名单的默认值是"不暴露" → 犯错 = 少显示
```

**安全设计要让"默认行为"是安全的那一个。**

> 这和第一阶段讲的"用 VO 隔离 password"是同一个思路的延伸：
> 当时是"防止密码泄漏"，现在是"防止手机号泄漏"。
> **只要一个类型是面向外部的，它就应该自己定义自己的字段，而不是继承内部类型。**

## 3.3 一个反例：`AdminUserVO` 为什么可以继承

项目里 `AdminUserVO extends UserVO`，看起来违反了上面说的原则。它为什么可以？

```java
public class AdminUserVO extends UserVO {
    private Long productCount;
}
```

**因为 `AdminUserVO` 的使用者是管理员** ——`AdminUserController` 上有 `@RequireRole(ADMIN)`，
**只有管理员能访问**。管理员本来就该看到手机号、邮箱、最后登录时间（否则没法做用户管理）。

**判断标准不是"这个类有没有继承"，而是"谁能访问使用它的接口"。**

| 类 | 使用者 | 能看到隐私吗 |
| --- | --- | --- |
| `UserVO` | 用户本人 | ✅ 自己的数据，可以 |
| `AdminUserVO` | 管理员 | ✅ 管理需要 |
| **`UserPublicVO`** | **任何人（含游客）** | ❌ **绝对不行** |

# 第四部分：三行代码复用整个商品查询

## 4.1 实现

```java
@PublicApi
@Operation(summary = "卖家在售商品列表")
@GetMapping("/{id}/products")
public Result<PageResult<ProductListVO>> products(@PathVariable Long id, ProductQuery query) {
    // 下面三个条件由后端强制覆盖，前端传什么都不算数：
    // 防止有人用 ?sellerId=别人 或 ?status=0 把待审核商品翻出来
    query.setSellerId(id);
    query.setOnlyOnSale(true);
    query.setStatus(null);
    return Result.success(productService.page(query));
}
```

**`ProductMapper.xml` 里那段查询本来就支持 `sellerId` 和 `onlyOnSale` 参数** ——
它们在 [03-商品模块](03-商品模块实现讲解.md) 里是为「我的发布」准备的：

```xml
<where>
    p.deleted = 0
    <choose>
        <when test="query.onlyOnSale != null and query.onlyOnSale">
            AND p.status = 1
        </when>
        <when test="query.status != null">
            AND p.status = #{query.status}
        </when>
    </choose>
    <if test="query.sellerId != null">
        AND p.user_id = #{query.sellerId}
    </if>
    ...
</where>
```

**所以卖家主页的商品列表，一行新 SQL 都没写。**

## 4.2 白拿的筛选能力

因为复用了 `ProductQuery`，卖家主页**顺便就有了**品牌、价格区间、成色、排序这些能力：

```
GET /api/seller/101/products?minPrice=1000&maxPrice=3000&sort=priceAsc
```

**现在前端还没用到，但它已经在那儿了。** 如果以后想在卖家主页加一个"价格筛选"，
改前端就行，后端不用动。

> **好的复用不只是"少写代码"，而是"白拿了未来的扩展能力"。**

## 4.3 三个 `set` 是"覆盖"不是"合并"

**这段代码最关键的地方不是它调用了什么，而是它覆盖了什么。**

```java
query.setSellerId(id);      // 覆盖：不管前端传 ?sellerId=999
query.setOnlyOnSale(true);  // 覆盖：不管前端传 ?onlyOnSale=false
query.setStatus(null);      // 覆盖：不管前端传 ?status=0
```

**如果不覆盖会怎样？**

```
攻击者：GET /api/seller/101/products?status=0
   ↓
如果不覆盖 status：
   ↓
返回 101 的【待审核】商品
   ↓
别人商品还没过审的内容被提前看到了
```

**而这正是不允许的** ——在 [03-商品模块](03-商品模块实现讲解.md) 里我们已经确定：
待审核商品只有发布者本人和管理员能看。

实测验证：

```
=== 参数注入尝试 ===
GET /api/seller/109/products?status=0&onlyOnSale=false
  total = 2
  status=1 华为手环 8 NFC 版
  status=1 iPad Air 5 64G 紫色 WiFi版
```

黄敏（109）有 2 件在售 + **1 件待审核**，返回 2 条、全是 `status=1` ——
**那件待审核的商品没有被翻出来。**

## 4.4 一条通用规则

> **当控制器接收一个"前端可控制的查询对象"，又需要强制某些条件时，必须用"覆盖"而不是"合并"。**

项目里同一个模式出现过两次：

| 位置 | 覆盖了什么 | 防什么 |
| --- | --- | --- |
| `ProductController.page()` | `setSellerId(null)`、`setStatus(null)`、`setOnlyOnSale(true)` | 前端翻出待审核/别人的商品 |
| `AdminReportService.page()` | `setUserId(null)` | 前端把管理员列表筛成别人的 |
| **`SellerController.products()`** | 三个都覆盖 | 同上 |

**共同点：这些字段的"权威来源"是服务端（token 或路径参数），不是请求参数。**

**一旦某个字段的值由服务端决定，就必须显式覆盖它，不能指望前端不传。**

# 第五部分：前端三个入口与事件冒泡

## 5.1 入口一：商品详情页的卖家卡片

```vue
<!-- 卖家卡片：点击进入卖家主页，看他还有没有别的闲置 -->
<div class="seller app-card" @click="goSeller">
  <el-avatar :size="48" :src="product.sellerAvatar">...</el-avatar>
  <div class="seller-info">
    <div class="seller-name">
      {{ product.sellerNickname }}
      <el-tag size="small" type="success" effect="plain">信誉 {{ product.sellerCreditScore }}</el-tag>
    </div>
    <div class="text-secondary seller-campus">{{ product.sellerCampus }}</div>
  </div>
  <span class="seller-more">
    查看 TA 的闲置
    <el-icon><ArrowRight /></el-icon>
  </span>
</div>
```

**加了"查看 TA 的闲置 →"这个提示，是因为"卡片可点"本身是不可见的。**

用户看到一张卡片，不知道它能点。一个右箭头 + 一句"查看 TA 的闲置"，
**把"可点击"变成了"看起来可点击"**。

配合 hover 效果：

```css
.seller {
  cursor: pointer;
  transition: all 0.2s;
}

.seller:hover {
  box-shadow: var(--app-shadow-hover);
}

.seller:hover .seller-more {
  color: var(--el-color-primary);
}
```

**鼠标移上去卡片浮起来、提示文字变蓝** ——三个信号叠加，用户不会错过。

> **可点击的元素必须看起来可点击。** 这是交互设计最基本的一条，
> 而"整块 div 绑了 click"恰恰是最容易违反它的一种实现。

## 5.2 入口二：商品列表里的卖家昵称

```vue
<div class="meta">
  <span class="seller-link text-ellipsis" @click.stop="goSeller">
    {{ product.sellerNickname || '未知卖家' }}
  </span>
  <span class="text-secondary">{{ fromNow(product.createTime) }}</span>
</div>
```

### 必须的 `@click.stop`

**整张商品卡片本身是"点进商品详情"：**

```vue
<div class="product-card app-card" @click="goDetail">
```

**所以点卖家昵称时，事件会冒泡到卡片上，两个跳转同时触发** ——
用户点了一下，页面可能跳到商品详情、也可能跳到卖家主页，**取决于哪个后执行**。

`@click.stop` 阻止冒泡，只保留卖家主页的跳转。

> **在"可点击的容器里放可点击的元素"，必须处理事件冒泡。**
> 这个坑在本项目里出现过两次：
> - [06-收藏与留言](06-收藏与留言模块实现讲解.md)：`ProductCard` 的 actions 插槽里，取消收藏按钮要 `.stop`
> - 本功能：卖家昵称要 `.stop`
>
> **只要卡片整体可点，里面任何独立按钮都要 `.stop`。**

## 5.3 入口三：路由

```js
{
  path: 'seller/:id(\\d+)',
  name: 'SellerHome',
  component: () => import('@/views/user/SellerHome.vue'),
  meta: { title: '卖家主页' }
}
```

**`:id(\\d+)` 的正则约束很重要** ——如果没有它，`/seller/abc` 也会匹配进来，
然后后端拿到一个非数字参数报 400。加了约束之后，**非法路径直接走 404**，
错误更早、更明确。

（这个模式在 `/product/:id(\\d+)` 上已经用过一次。）

**放在 `UserLayout` 下面**，因为卖家主页和商品页一样，是**前台的浏览页面**，
需要顶部导航栏，而不是后台的侧边栏。

# 第六部分：页面上的几个细节

## 6.1 "已成交"这个数字

```
┌──────────────────────────────────┐
│  [头像]  王八  [信誉 96]          │
│          电子信息学院 · 2026-07-26 加入
│          2 在售商品    1 已成交    │
└──────────────────────────────────┘
```

**为什么要有"已成交"这个数字？**

因为**信誉分是平台给的，"成交过多少"是他自己做的。**

| 数据 | 性质 | 买家怎么理解 |
| --- | --- | --- |
| 信誉分 96 | 平台评分 | "平台觉得他还行" |
| 在售 2 件 | 当前状态 | "他现在有 2 样东西卖" |
| **已成交 1 件** | **历史行为** | **"他确实卖出过东西，不是空账号"** |

**一个新注册、从没成交过的账号，和一个成交过 12 单的账号，可信度完全不同。**
而这个信息只有卖家主页能给。

代码里这两个数字是**两次 `COUNT` 查询**，而不是把商品全查出来数：

```java
vo.setOnSaleCount(productMapper.selectCount(Wrappers.<Product>lambdaQuery()
        .eq(Product::getUserId, userId)
        .eq(Product::getStatus, ProductStatus.ON_SALE.getCode())));
vo.setSoldCount(productMapper.selectCount(Wrappers.<Product>lambdaQuery()
        .eq(Product::getUserId, userId)
        .eq(Product::getStatus, ProductStatus.SOLD.getCode())));
```

**这就是 [07-订单模块](07-订单模块实现讲解.md) 里讲过的"聚合交给数据库"** ——
`COUNT` 只扫索引，不搬数据。

## 6.2 只显示在售商品

```java
query.setOnlyOnSale(true);
```

**卖家的待审核、已下架、已驳回商品都不显示。** 理由很简单：

**主页是给买家看的，买家只能买在售的东西。** 把待审核的商品列出来，
买家点进去发现"商品不存在"（详情接口会拦住），体验更差。

**已售出的也不显示** ——它已经不是"可以买的东西"了。但它通过"已成交 N"这个数字被体现了。

> **主页展示的是"他现在能卖什么"，而不是"他所有发过的东西"。**
> 后者是卖家自己该在「我的发布」里看的（那里五种状态都有）。

## 6.3 看自己的主页

```js
const isSelf = computed(
  () => userStore.isLogin && String(userStore.userInfo?.id) === String(route.params.id)
)
```

**为什么要处理这个情况？**

用户可能在商品详情页点自己商品的卖家卡片，进到自己的主页。这时：

| 元素 | 对自己的处理 |
| --- | --- |
| 昵称旁的标签 | 显示「这是你」 |
| 右侧按钮 | 「管理我的商品」→ 跳到 `/user/products` |
| 区块标题 | 「**我**在售的商品」 |
| 空状态 | 「**你**还没有在售的商品」+ 去发布链接 |

**如果不区分，用户看到的是"TA 在售的商品"** ——而 TA 就是他自己，很奇怪。

**注意用的是 `String()` 转换后比较**：

```js
String(userStore.userInfo?.id) === String(route.params.id)
```

因为 `route.params.id` 是**字符串**，而 `userStore.userInfo.id` 是**数字**。
直接 `===` 永远是 `false`。这是前端比较路由参数时最常见的坑。

## 6.4 用户不存在时

```js
async function loadProfile() {
  loadingProfile.value = true
  try {
    seller.value = await getSellerProfile(route.params.id)
  } catch {
    // 用户不存在时后端返回 2003，这里退化成"该用户不存在"的空状态
    seller.value = null
  } finally {
    loadingProfile.value = false
  }
}
```

后端返回 `2003 用户不存在`，前端**不弹错误提示，而是渲染一个空状态**：

```vue
<el-empty v-if="!loadingProfile && !seller" description="该用户不存在">
  <el-button type="primary" @click="router.push('/product/list')">去逛逛商品</el-button>
</el-empty>
```

**为什么不用 `ElMessage.error` 弹一下就算了？**

因为那样页面会剩一片空白 ——用户看到"用户不存在"的提示消失后，不知道自己在哪。
**空状态 + 一个出口（去逛逛商品）**，页面就不会变成死胡同。

> **错误页也要有"下一步"。** 这是本项目一直在贯彻的原则
> （参见 08 篇的"报错信息里要给替代方案"）。

## 6.5 页面切换时重新加载

```js
onMounted(reloadAll)

// 从一个卖家主页直接跳到另一个卖家主页时（比如从商品详情再点进去），要重新加载
watch(() => route.params.id, reloadAll)
```

**为什么需要 `watch`？**

如果用户在卖家 A 的主页 → 点进一件商品 → 又点了另一个卖家 B，
Vue 会**复用同一个组件实例**（路由不变，只是参数变了），`onMounted` 不会再次触发。

**不加 watch，用户会看到 A 的资料 + B 的商品** ——或者更糟，什么都不更新。

这个坑在 `Detail.vue` 里也处理过（`watch(() => route.params.id, loadDetail)`）。

# 第七部分：验收

## 7.1 安全设计

| 攻击手法 | 后果 | 防护 | 代码位置 |
| --- | --- | --- | --- |
| 遍历 `/api/seller/{id}` 采集手机号 | **全站用户联系方式泄漏** | `UserPublicVO` 白名单，只暴露公开字段 | `UserPublicVO` |
| 遍历采集登录账号 | 撞库 | 同上，不含 `username` | `UserPublicVO` |
| 通过 `?sellerId=别人` 看别人主页 | 无实质危害（主页本来就公开） | 路径参数覆盖 | `SellerController` |
| **通过 `?status=0` 翻出待审核商品** | **未过审内容提前曝光** | `setStatus(null)` + `setOnlyOnSale(true)` 覆盖 | `SellerController` |
| 通过 `?onlyOnSale=false` 同上 | 同上 | 同上 | `SellerController` |
| 非法 id（`/seller/abc`） | 400 错误页 | 路由正则 `\\d+` 拦截 | `router/index.js` |
