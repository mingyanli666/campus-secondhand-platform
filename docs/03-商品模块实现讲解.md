# 第二部分：分类模块 —— 最简单的完整闭环

分类是整个项目里最简单的模块，**正好用来把"一个模块要写哪些文件"这件事讲清楚**。

## 2.1 一个标准模块的六件套

| 文件 | 职责 | 类比 |
| --- | --- | --- |
| `entity/Category.java` | 数据库表的 Java 映射 | 表格的"行" |
| `mapper/CategoryMapper.java` | 数据库操作接口 | 仓库管理员 |
| `service/CategoryService.java` | 业务接口 | 需求说明书 |
| `service/impl/CategoryServiceImpl.java` | 业务实现 | 干活的人 |
| `vo/CategoryVO.java` | 返回给前端的数据 | 前台窗口 |
| `controller/CategoryController.java` | HTTP 接口 | 接待员 |

**以后每加一个业务模块，都是这六件套。** 记住这个模板，你就能自己开新模块了。

## 2.2 `@TableLogic` —— 逻辑删除的开关

```java
@TableLogic
private Integer deleted;
```

上一阶段在 `application.yml` 里配置的是**全局**逻辑删除规则：

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: deleted
```

那为什么实体上还要再加 `@TableLogic`？两者是"全局默认"和"显式声明"的关系：加上注解后，代码里一眼就能看出这个字段是逻辑删除标记，而不是一个普通字段。**可读性 > 少写几个字。**

加了之后自动发生什么：

```java
categoryMapper.deleteById(7);
// 实际执行：UPDATE sys_category SET deleted = 1 WHERE id = 7 AND deleted = 0

categoryMapper.selectList(null);
// 实际执行：SELECT ... FROM sys_category WHERE deleted = 0
```

## 2.3 查询条件构造器：`LambdaQueryWrapper`

```java
List<Category> list = categoryMapper.selectList(
        Wrappers.<Category>lambdaQuery()
                .eq(Category::getStatus, Constants.STATUS_ENABLED)
                .orderByAsc(Category::getSort));
```

等价于 `SELECT * FROM sys_category WHERE status = 1 AND deleted = 0 ORDER BY sort ASC`。

**`Category::getStatus` 这种写法叫方法引用**，好处是：

```java
.eq(Category::getStatus, 1)     // ✅ 写成字符串 "status"，字段名打错了编译期不报错
.eq("status", 1)                // ❌ 拼错成 "stauts"，运行时才报错
```

用方法引用，**字段改名时 IDE 能一键重构**，拼错直接编译不过。

## 2.4 VO 的必要性

`Category` 实体有 `deleted`、`createTime`、`updateTime` 这些字段，前端一个都用不上。用 `CategoryVO` 只暴露 `id / name / icon / sort` 四个字段：

```java
return list.stream()
        .map(c -> BeanUtil.copyProperties(c, CategoryVO.class))
        .toList();
```

`stream().map().toList()` 是 Java 8 的**流式编程**：把"遍历 + 转换"写成一条链，比 for 循环 + `list.add()` 更清晰。

## 2.5 `@PublicApi`

```java
@PublicApi
@Operation(summary = "查询启用的分类列表")
@GetMapping("/list")
public Result<List<CategoryVO>> list() { ... }
```

分类是纯字典数据，**不登录也要能看**（首页就得展示分类）。上一阶段设计的 `@PublicApi` 注解在这里第一次真正派上用场——注意拦截器仍然会尝试解析 token，只是解析失败也不拦截。这一点后面在商品详情页会用到（未登录也能看详情，但登录了要多判断"是不是我自己的商品"）。

# 第三部分：文件上传 —— 安全是第一位的

这是整份文档里**最该认真看**的一节。文件上传是 Web 系统最常见的攻击入口之一。

## 3.1 `MultipartFile` 是什么

浏览器上传文件时，HTTP 请求体的编码方式会变成 `multipart/form-data`：

```
------WebKitFormBoundaryXXX
Content-Disposition: form-data; name="file"; filename="phone.png"
Content-Type: image/png

<这里是 PNG 的二进制数据>
------WebKitFormBoundaryXXX--
```

Spring MVC 把这段解析成一个 `MultipartFile` 对象给你：

```java
@PostMapping("/image")
public Result<String> uploadImage(@RequestParam("file") MultipartFile file) {
```

`@RequestParam("file")` 里的 `"file"` 必须和前端 `formData.append('file', file)` 的名字一致——**对不上就是 400**。

## 3.2 五道校验，缺一不可

打开 `service/impl/FileServiceImpl.java`，校验是逐层递进的：

### 第 1 道：非空

```java
if (file == null || file.isEmpty()) {
    throw new BusinessException(ResultCode.FILE_EMPTY);
}
```

### 第 2 道：原始文件名存在

```java
String originalName = file.getOriginalFilename();
if (StrUtil.isBlank(originalName)) {
    throw new BusinessException(ResultCode.FILE_TYPE_NOT_ALLOWED);
}
```

### 第 3 道：后缀白名单（最关键）

```java
String ext = FileUtil.extName(originalName).toLowerCase(Locale.ROOT);
List<String> allowExt = Arrays.asList(properties.getFile().getAllowExt().split(","));
if (!allowExt.contains(ext)) {
    throw new BusinessException(ResultCode.FILE_TYPE_NOT_ALLOWED,
            "仅支持 " + String.join("/", allowExt) + " 格式的图片");
}
```

**为什么要用白名单而不是黑名单？** 因为"禁止的可执行后缀"是列举不完的：

```
.jsp  .jspx  .php  .php5  .phtml  .asp  .aspx  .ashx  .exe  .sh  .bat  .cmd ...
```

而且攻击者可以用 `.jsp.`、`.jsp;`、`.jsp%00.png` 这类变形绕过黑名单。**只允许已知安全的格式**才是可靠做法。

> `toLowerCase(Locale.ROOT)` 是为了防止 `.PNG`、`.Png` 绕过。用 `Locale.ROOT` 而不是默认 Locale，是因为土耳其语环境下 `"I".toLowerCase()` 会得到 `ı`（无点 i），可能造成意外的比较失败。

### 第 4 道：大小限制

```java
if (file.getSize() > properties.getFile().getMaxSize()) {
    throw new BusinessException(ResultCode.FILE_TOO_LARGE, ...);
}
```

这是**第二道防线**。第一道在 `application.yml`：

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB        # 单个文件
      max-request-size: 50MB     # 整个请求（多文件上传时用）
```

Spring 那一层在解析请求体时就挡住了，根本没进到你的代码；这一层是兜底。

### 第 5 道：UUID 重命名（防路径穿越）

```java
String datePath = DateUtil.format(new Date(), "yyyy/MM");
String fileName = IdUtil.fastSimpleUUID() + "." + ext;
String relativePath = subDir + "/" + datePath + "/" + fileName;
```

假设不做重命名，直接用用户传来的文件名，攻击者可以把文件名设成：

```
../../../application.yml
```

结果就是**文件被写到项目目录外面**，覆盖配置文件——这叫**路径穿越攻击（Path Traversal）**。

用 UUID 重命名后，文件名完全由服务器生成，用户的输入只影响一个字母：后缀（而且后缀已经被白名单校验过了）。

## 3.3 为什么要按年月分目录

```
uploads/product/2026/10/0fbbaa2e8381422397b2bb5b3fc4221d.png
        ↑子业务  ↑年 ↑月  ↑UUID
```

如果把 10 万张图片全放一个目录，`ls` 一次都要好几秒，部分文件系统（尤其 ext3 的目录项上限）性能会急剧下降。按年月分目录后，每个目录最多几千个文件，**这是一条很实用的工程经验**。

## 3.4 `transferTo` 的一个坑

```java
File target = new File(properties.getFile().getUploadPath(), relativePath);
...
file.transferTo(target.getAbsoluteFile());
```

注意这里用的是 `target.getAbsoluteFile()` 而**不是** `target`。

因为 `upload-path` 配置的是 `./uploads/`（相对路径），而 `MultipartFile.transferTo` 在某些容器实现下，对**相对路径的 File 对象**处理有问题——它可能相对于临时目录去解析，导致文件不知道存到哪去了。**转成绝对路径是最稳妥的做法。**

## 3.5 上传接口为什么不能公开

```java
// UploadController 上故意没有 @PublicApi
@Operation(summary = "上传商品图片")
@PostMapping("/image")
public Result<String> uploadImage(@RequestParam("file") MultipartFile file) {
```

**因为上传要占磁盘空间。** 如果匿名用户就能上传，别人写个脚本循环上传，你的服务器磁盘几分钟就满了，整个系统瘫痪。这是很直接的拒绝服务（DoS）风险。

实测也验证了：不带 token 上传返回 `401`。

## 3.6 图片怎么被访问到

`FileServiceImpl` 只负责**存**，还差一步"怎么让浏览器取到"。

上一阶段 `config/WebMvcConfig.java` 里已经配好了：

```java
String location = "file:" + dir.getAbsolutePath() + File.separator;
registry.addResourceHandler("/uploads/**").addResourceLocations(location);
```

意思是：浏览器请求 `/uploads/xxx/yyy.png`，Spring 就去本地磁盘目录找这个文件返回。

所以 `FileServiceImpl` 返回的是 `/uploads/product/2026/10/xxx.png` 这样一个**相对地址**——它既是数据库里存的值，也是前端 `<el-image :src="...">` 直接能用的 URL。

> 实测确认：`GET /uploads/product/2026/10/0fbbaa...png` 返回 `200`。

# 第四部分：商品数据模型 —— 三种数据形态

## 4.1 `biz_product` 表的字段分区

打开 `entity/Product.java`，字段是分三组设计的：

### 第一组：基本信息

`title` / `description` / `price` / `originalPrice` / `coverImage` / `categoryId` / `userId`

### 第二组：数码专属字段（本项目的"行业针对性"）

| 字段 | 为什么需要 |
| --- | --- |
| `brand` 品牌 | 手机要看 Apple/华为/小米，这是最重要的筛选维度 |
| `model` 型号 | 决定二手价格的直接因素，iPhone 14 和 14 Pro 差很多钱 |
| `conditionLevel` 成色 | 二手商品的核心定价依据 |
| `spec` 参数配置 | 内存/存储/电池健康/快门次数…不同品类完全不同 |
| `warranty` 质保 | 在保的商品能卖更贵，买家也需要知道 |
| `purchaseDate` 购入时间 | 买家据此推算剩余保修期 |

**这就是"通用二手平台"和"二手数码平台"的区别。** 一个卖书的平台不需要"电池健康度"，一个卖家具的平台不需要"快门次数"。

### 第三组：状态与统计

`status` / `rejectReason` / `viewCount` / `favoriteCount` / `publishTime` / `auditTime` / `auditorId`

## 4.2 为什么价格用 `BigDecimal` 而不是 `double`

```java
private BigDecimal price;
```

这是**必须记住的一条**。看这个 Java 例子：

```java
System.out.println(0.1 + 0.2);        // 输出 0.30000000000000004
```

因为 `double` 用二进制表示小数，0.1 无法被精确表示（就像十进制表示不了 1/3）。

后果有多严重？如果价格用 `double`：

```
商品A：19.9 元 × 3 件 = 59.699999999999996 元
买家付款 59.70，对不上账
```

**钱不能用浮点数。** `BigDecimal` 用十进制精确表示，是金融计算的唯一正确选择。数据库里对应 `DECIMAL(10,2)`。

## 4.3 为什么 `spec` 存 JSON 字符串

```java
/** ★ 参数配置，存 JSON 字符串，如 {"内存":"8G","存储":"256G"} */
private String spec;
```

为什么不像品牌型号那样，把"内存""存储""电池健康"各建一个字段？

因为**不同品类的参数完全不同，而字段是全表共享的**：

| 品类 | 需要的参数 |
| --- | --- |
| 手机 | 内存、存储、电池健康、版本 |
| 相机 | 有效像素、快门次数、镜头 |
| 笔记本 | 处理器、显卡、硬盘、屏幕 |
| 耳机 | 类型、降噪、续航、连接方式 |

如果都建成字段，`biz_product` 表会有几十个字段，而且每个商品 90% 的字段是空的——这叫**稀疏表**，是典型的坏设计。

JSON 字符串的好处：**结构灵活，任何品类都能装下**。

**代价是什么？** 不能直接 `WHERE spec->>'$.内存' = '8G'` 高效查询（虽然 MySQL 8 支持 JSON 类型和函数，但索引麻烦）。所以 `spec` 只做**展示**，不做**筛选**。需要筛选的维度（品牌、成色、价格）都单独建了字段和索引。

> **这就是"设计取舍"**：把"要搜索的"抽成字段，"只展示的"塞进 JSON。答辩时讲这个点很有说服力。

## 4.4 为什么图片单独一张表

考虑两种方案：

**方案 A：商品表加字段** `image1, image2, image3, ...` → 最多几张？第 4 张怎么办？加字段？

**方案 B：`biz_product_image` 独立表，一个商品对应多行** → 想存几张存几张

一对多用**方案 B**，这是关系数据库的基本功。表上建了 `KEY idx_product (product_id)`，查某商品的图片时走索引，很快。

## 4.5 为什么不存"哪张是封面"字段

`ProductSaveDTO` 里我写了这样一段注释：

```java
/**
 * 图片地址列表。
 * 约定：第一张就是封面图。这样前端只要拖拽排序就能换封面，
 * 不用额外维护一个"哪张是封面"的字段。
 */
private List<String> images;
```

对应 `ProductServiceImpl`：

```java
product.setCoverImage(CollUtil.isEmpty(dto.getImages()) ? null : dto.getImages().get(0));
```

**用一个"约定"（第一张即封面）替代一个"字段"。** 好处是：

- 不用维护 `is_cover` 字段和它的一致性
- 前端只要调整数组顺序就能换封面，逻辑天然统一
- 数据库不用加唯一性约束来保证"每个商品只有一个封面"

代价是 `cover_image` 字段对 `images` 有冗余（封面地址存了两份）。但这是**有意为之的冗余**：列表页需要高频读取封面，冗余一份能避免每次都去 `JOIN` 图片表。**读性能 > 存储空间**，这是很常见的取舍。

## 4.6 为什么同一个商品要两个 VO

```java
ProductListVO    // 列表用
ProductDetailVO  // 详情用
```

对比一下就知道为什么不能共用一个：

| 字段 | ListVO | DetailVO | 原因 |
| --- | --- | --- | --- |
| `description` 描述 | ❌ | ✅ | 描述可能 2000 字，列表 20 条就是 4 万字，纯浪费带宽 |
| `images` 全部图片 | ❌ | ✅ | 列表只显示封面，不需要所有图 |
| `spec` 参数 | ❌ | ✅ | 列表不展开参数 |
| `contact` 联系方式 | ❌ | ✅ | **价格敏感信息，列表页不暴露** |
| `owner` 是否本人 | ❌ | ✅ | 只有详情页要按钮 |
| `categoryName` | ✅ | ✅ | 两边都显示 |

**核心原则：接口只返回前端真正需要的字段。**

这跟需求里"页面加载迅速"直接相关。假设 20 条商品，每条描述 1000 字，用 DetailVO 做列表会多传 20KB 无用数据——用户在网络差的时候就是多等一秒。

## 4.7 DTO 上的校验注解

```java
@NotNull(message = "请选择商品分类")
private Long categoryId;

@NotBlank(message = "请填写商品标题")
@Size(min = 2, max = 100, message = "标题长度为 2-100 个字符")
private String title;

@NotNull(message = "请填写出售价格")
@DecimalMin(value = "0.01", message = "价格必须大于 0")
@DecimalMax(value = "9999999.99", message = "价格超出合理范围")
private BigDecimal price;
```

常用的几个：

| 注解 | 用途 |
| --- | --- |
| `@NotNull` | 不能为 null（数字、日期用） |
| `@NotBlank` | 不能为 null 且不能是空白字符串（字符串用） |
| `@Size` | 长度范围 |
| `@DecimalMin/Max` | 数字范围（对 BigDecimal 用） |
| `@Pattern` | 正则 |
| `@Email` | 邮箱格式 |

**这些注解在 `@Valid` 触发后生效**，Controller 里写的是：

```java
public Result<Long> publish(@Valid @RequestBody ProductSaveDTO dto) {
```

`@Valid` 是开关，没有它注解全部不生效——这是新手常犯的错误。

校验失败会抛 `MethodArgumentNotValidException`，被上一阶段写的 `GlobalExceptionHandler` 接住，把所有字段的错误拼起来返回。实测结果：

```
{"code":400,"message":"邮箱格式不正确；手机号格式不正确"}
```

**注意前端也要做一遍校验**（`Publish.vue` 的 `rules`）。为什么两边都要？

- **前端校验**：为了体验，用户不用等一个来回就知道填错了
- **后端校验**：为了安全，因为前端可以被绕过（用 Postman 直接调接口）

**记住：前端校验永远只是体验，后端校验才是安全。**

# 第五部分：商品写入 —— 发布、编辑、状态机

## 5.1 发布：一个事务里做两件事

```java
@Override
@Transactional(rollbackFor = Exception.class)
public Long publish(Long userId, ProductSaveDTO dto) {
    checkCategory(dto.getCategoryId());

    Product product = new Product();
    copyFields(product, dto);
    product.setUserId(userId);
    product.setStatus(ProductStatus.PENDING.getCode());
    product.setViewCount(0);
    product.setFavoriteCount(0);
    product.setCoverImage(CollUtil.isEmpty(dto.getImages()) ? null : dto.getImages().get(0));
    productMapper.insert(product);

    saveImages(product.getId(), dto.getImages());   // ← 第二件事

    return product.getId();
}
```

### `@Transactional` 到底保证了什么

发布操作实际要**写两张表**：

1. `INSERT INTO biz_product ...`（商品主记录）
2. `INSERT INTO biz_product_image ...` × N（图片记录）

如果第 1 步成功、第 2 步失败（比如数据库连接断了），会发生什么？

- 没有 `@Transactional`：商品记录留在库里，但一张图片都没有 → **脏数据**，用户刷新后看到一个没有图的商品
- 有 `@Transactional`：两步在同一个事务里，**第 2 步失败会自动回滚第 1 步**，两张表都干净

`rollbackFor = Exception.class` 是什么意思？

默认情况下，Spring 只对 `RuntimeException` 回滚，**对受检异常（Checked Exception）不回滚**。写上 `rollbackFor = Exception.class` 表示"任何异常都回滚"，避免踩坑。**这是最安全的写法，建议每个写操作都加上。**

### `product.setStatus(PENDING)` —— 业务闭环的起点

```java
product.setStatus(ProductStatus.PENDING.getCode());   // 0 待审核
```

新发布的商品**不是直接上架的**，而是进入待审核状态。这直接对应需求里的"后台审核管理"和"杜绝虚假违规信息随意传播"。

实测验证：发布后查询公开列表，`total = 0`；只有把状态改成 `1` 之后才出现。

## 5.2 编辑：一个"防作弊"设计

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void update(Long userId, Long productId, ProductSaveDTO dto) {
    Product exist = requireOwner(userId, productId);
    checkCategory(dto.getCategoryId());

    if (ProductStatus.SOLD.getCode().equals(exist.getStatus())) {
        throw new BusinessException(ResultCode.PRODUCT_STATUS_ILLEGAL, "已售出的商品不能编辑");
    }

    copyFields(exist, dto);
    exist.setCoverImage(...);
    // 内容变了就要重新审核，防止"先发合格内容过审，再改成违规内容"
    exist.setStatus(ProductStatus.PENDING.getCode());
    exist.setRejectReason(null);
    productMapper.updateById(exist);

    productImageMapper.delete(...);   // 图片整体替换
    saveImages(productId, dto.getImages());
}
```

### 为什么编辑后要回到"待审核"

设想没有这个设计会发生什么：

1. 张三发布"iPhone 14 Pro"，内容合规 → 管理员审核通过 → 上架
2. 张三再点"编辑"，把标题改成"代开发票 加微信 xxx"，把图片换成违禁品
3. **商品已经在上架状态，改完直接生效，管理员完全不知情**

**审核就形同虚设了。** 所以只要内容变了，就必须重新过一遍审核。

这条规则在需求里对应"业务逻辑严谨""杜绝虚假违规信息随意传播"。

### 图片为什么"整体替换"

```java
// 图片是"整体替换"语义：先清掉旧的再插新的，比逐个比对简单可靠
productImageMapper.delete(
        Wrappers.<ProductImage>lambdaQuery().eq(ProductImage::getProductId, productId));
saveImages(productId, dto.getImages());
```

另一种做法是"差异比对"：找出新增的、删掉的、保持不变的三类，分别处理。但那要写不少代码，还容易出错（比如把还在用的图片删了）。

**"全删重建"虽然多写几条 SQL，但逻辑绝对简单、绝不会错。** 图片数量最多 9 张，性能完全不是问题。

> 这类"用一点点性能换大量正确性和可维护性"的取舍，在实际项目里非常常见。

## 5.3 `requireOwner` —— 防越权的核心

```java
private Product requireOwner(Long userId, Long productId) {
    Product product = productMapper.selectById(productId);
    if (product == null) {
        throw new BusinessException(ResultCode.PRODUCT_NOT_FOUND);
    }
    if (!product.getUserId().equals(userId)) {
        throw new BusinessException(ResultCode.NOT_PRODUCT_OWNER);
    }
    return product;
}
```

**为什么这个检查至关重要？**

`productId` 是前端传上来的参数，**可以随便改**。如果不校验归属，攻击者只要在浏览器控制台里改一下 ID，就能：

- 把别人的商品下架（恶意竞争）
- 把别人的商品删掉
- 把别人的商品内容改成违规信息（让别人被封号）

实测验证：

```
=== 13. lisi 下架 zhangsan 的商品 ===
{"code":3003,"message":"只能操作自己发布的商品"}       ✅

=== 14. lisi 删除 zhangsan 的商品 ===
{"code":3003,"message":"只能操作自己发布的商品"}       ✅
```

**判断用户身份靠 `UserContext.userId()`（来自 token），而不是前端传的 userId。** 这是"角色权限清晰、杜绝越权操作"的技术落地。

## 5.4 状态机：为什么不能随便改状态

`common/enums/ProductStatus.java` 定义了所有合法状态：

```java
PENDING(0, "待审核"),  ON_SALE(1, "已上架"),  OFF_SHELF(2, "已下架"),
SOLD(3, "已售出"),     REJECTED(4, "审核驳回");
```

**为什么不直接在代码里写 `status = 1` 这种数字？** 因为：

```java
update.setStatus(1);                        // ❌ 1 是什么？三个月后你自己都忘了
update.setStatus(ProductStatus.ON_SALE.getCode());   // ✅ 一眼看懂
```

这叫**消除魔法值**。而且以后要加状态（比如"锁定中"），只改枚举一处。

每个操作都校验**前置状态**：

```java
// 下架：只有在售的能下架
if (!ProductStatus.ON_SALE.getCode().equals(exist.getStatus())) {
    throw new BusinessException(ResultCode.PRODUCT_STATUS_ILLEGAL, "只有在售商品才能下架");
}

// 重新提交：只有已下架 / 被驳回的能重新提交
boolean canResubmit = ProductStatus.OFF_SHELF.getCode().equals(status)
        || ProductStatus.REJECTED.getCode().equals(status);
if (!canResubmit) {
    throw new BusinessException(ResultCode.PRODUCT_STATUS_ILLEGAL, "当前状态不能重新提交审核");
}
```

**如果不校验会怎样？**

- 一个"已售出"的商品被下架 → 数据矛盾（到底是卖了还是没卖？）
- 一个"待审核"的商品点"重新提交" → 无意义操作，还可能把 `rejectReason` 清掉

完整的合法流转：

```
                  ┌──────────── 编辑 ────────────┐
                  ▼                              │
  发布 ──► 待审核(0) ──管理员通过──► 已上架(1) ──卖家下架──► 已下架(2)
              │                        │                      │
              │                    买家下单                    │
              │                        ▼                      │
              │                     已售出(3)                  │
              │                                               │
              └──管理员驳回──► 审核驳回(4) ──重新提交──────────┘
                                    │                          │
                                    └──────────────────────────┘
```

## 5.5 销量计数为什么必须先判断状态

`offShelf` 只改 `status`，但它是**单独 update 一个字段**：

```java
Product update = new Product();
update.setId(productId);
update.setStatus(ProductStatus.OFF_SHELF.getCode());
productMapper.updateById(update);
```

MyBatis-Plus 的 `updateById` 只会更新**非 null 的字段**。所以这条 SQL 实际是：

```sql
UPDATE biz_product SET status = 2 WHERE id = ? AND deleted = 0
```

而不是把整个对象覆盖一遍。**这个特性很重要**：如果我想只改一个字段，就不用先把整行查出来再存回去（那样既慢，又有并发覆盖风险）。

# 第六部分：商品查询 —— 手写 SQL 的地方

前面的增删改都是 `BaseMapper` 一把梭，但**列表检索必须手写 SQL**，这是本阶段最大的技术点。

## 6.1 为什么不能只用 `BaseMapper`

需求要的效果是：

```
列表里要显示：商品标题、封面、价格…… 还要显示「分类名称」和「卖家昵称」
```

而 `biz_product` 表里只有 `category_id` 和 `user_id`，**没有分类名和卖家昵称**。

三种解法：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A | 分页查商品，然后循环查每个分类和卖家 | ❌ 20 条商品要发 40 次查询，**N+1 查询问题** |
| B | 分页查商品，再用 `IN` 批量查分类和卖家，在 Java 里拼装 | 🟡 可行，3 次查询，但要写不少拼装代码 |
| C | 一条 SQL `LEFT JOIN` 把三张表连起来 | ✅ **数据库最擅长的事，交给数据库** |

我们选 C。

## 6.2 Mapper 接口：`IPage` 参数

```java
IPage<ProductListVO> selectProductPage(IPage<ProductListVO> page, @Param("query") ProductQuery query);
```

两个关键点：

**① 第一个参数是 `IPage` 时，MyBatis-Plus 分页插件自动生效。**

它会做两件事：
1. 在 SQL 后面自动追加 `LIMIT`（比如 `LIMIT 0, 12`）
2. **额外执行一条 `COUNT` 查询**算出总数，填进 `page.getTotal()`

你完全不用自己写 `COUNT(*)`——这是分页插件最大的价值。

**② `@Param("query")` 让 XML 里能用 `query.xxx` 访问。**

```java
selectProductPage(page, query)
    ↓ @Param("query") 起别名
XML 里写成 #{query.categoryId} / query.keyword
```

如果方法有多个参数而不加 `@Param`，XML 里只能用 `arg0`/`param1` 这种难懂的名字。

## 6.3 XML 里的动态 SQL

`resources/mapper/ProductMapper.xml` 是整个后端最值得反复看的一个文件。

### `<where>` 标签：自动处理 AND

```xml
<where>
    p.deleted = 0
    <if test="query.categoryId != null">
        AND p.category_id = #{query.categoryId}
    </if>
</where>
```

`<where>` 的作用是：**如果里面有内容，就生成 `WHERE`；并且自动去掉开头多余的 `AND` / `OR`。**

为什么需要它？看这个条件组合——如果用户没选分类，`<if>` 不生效，SQL 会变成：

```sql
WHERE AND p.price >= 100      -- ❌ 语法错误
```

`<where>` 会自动把开头那个 `AND` 去掉。**这是 MyBatis 动态 SQL 最经典的价值。**

### `<if>` 标签：条件成立才拼进去

```xml
<if test="query.minPrice != null">
    AND p.price &gt;= #{query.minPrice}
</if>
```

`&gt;` 是 `>` 的 XML 转义（XML 里 `<` `>` 是特殊字符，必须转义）。等价：

| 符号 | XML 写法 |
| --- | --- |
| `>` | `&gt;` |
| `<` | `&lt;` |
| `&&` | `&amp;&amp;` |

### `<choose>` 标签：排序白名单（防 SQL 注入）

```xml
<choose>
    <when test="query.sort == 'priceAsc'">
        ORDER BY p.price ASC, p.id DESC
    </when>
    <when test="query.sort == 'priceDesc'">
        ORDER BY p.price DESC, p.id DESC
    </when>
    <when test="query.sort == 'hot'">
        ORDER BY p.view_count DESC, p.id DESC
    </when>
    <otherwise>
        ORDER BY p.create_time DESC, p.id DESC
    </otherwise>
</choose>
```

**这是本模块最需要理解的安全设计。**

为什么所有值都用 `#{}` 预编译，唯独 ORDER BY 要特殊处理？

因为 `#{}` 的预编译原理是**把它变成 `?` 占位符**：

```sql
... WHERE title LIKE ? ORDER BY ?      -- ❌ ORDER BY 后面不能是占位符！
```

`ORDER BY ?` 在 SQL 语法上是非法的——数据库要**先知道按哪个列排序，才能生成执行计划**，这个信息不能延迟到参数绑定阶段。

所以排序字段只能用字符串拼接 `${}`。而 `${}` 是**直接替换**，如果直接把用户输入拼进去：

```xml
ORDER BY ${query.sort}     -- ❌ 危险！
```

攻击者传 `sort = "id; DROP TABLE sys_user"`，SQL 就变成：

```sql
ORDER BY id; DROP TABLE sys_user
```

**用户表就没了。**

我们的做法是用 `<choose>` 把可选项**限定成 4 个固定字符串**，用户传什么都不会进入 SQL——只能在这 4 个里选一个。

> 实测验证：传 `sort=id; DROP TABLE sys_user`，接口正常返回 200，回退到默认排序，
> 查询 `sys_user` 表确认完好无损。

### `<choose>` 决定"看谁的"

```xml
<choose>
    <when test="query.onlyOnSale != null and query.onlyOnSale">
        AND p.status = 1
    </when>
    <when test="query.status != null">
        AND p.status = #{query.status}
    </when>
</choose>
```

- 公开列表 → `onlyOnSale = true` → 只查已上架
- "我的发布" → `onlyOnSale = false` + `status = 0/1/2/...` → 按状态筛选
- 一个 SQL 同时服务两个场景

## 6.4 手写 SQL 必须自己写 `deleted = 0`

```xml
FROM biz_product p
LEFT JOIN sys_category c ON c.id = p.category_id AND c.deleted = 0
LEFT JOIN sys_user u ON u.id = p.user_id
<where>
    p.deleted = 0
```

**这是最容易漏的地方。** 上一阶段说 MyBatis-Plus 的逻辑删除会自动追加 `deleted = 0`——但那个机制**只作用于它自己生成的方法**（`selectById`、`selectList` 等）。

**手写的 SQL 它管不着，必须自己写。**

漏了会怎样？被卖家"删除"过的商品（`deleted = 1`）依然会出现在列表里——用户明明删了却还能看到，就是 bug。

## 6.5 `LEFT JOIN` 而不是 `INNER JOIN`

```xml
LEFT JOIN sys_category c ON c.id = p.category_id
```

`INNER JOIN` 只返回两边都匹配的行。如果某个分类被管理员删了（`deleted = 1`），用 `INNER JOIN` 的话，**这个分类下的所有商品都会从列表里消失**。

`LEFT JOIN` 保证"以商品为主"，分类查不到就显示为 `null`（前端显示"未分类"）。**数据不会因为关联表的问题而丢失。**

## 6.6 `PageQuery` 基类 —— 防止"分页攻击"

```java
public <T> Page<T> toPage() {
    long pageNum = (current == null || current < 1) ? Constants.DEFAULT_PAGE_NUM : current;
    long pageSize = (size == null || size < 1) ? Constants.DEFAULT_PAGE_SIZE : size;
    pageSize = Math.min(pageSize, Constants.MAX_PAGE_SIZE);   // ← 关键
    return new Page<>(pageNum, pageSize);
}
```

**如果不在后端限制 `size` 会发生什么？**

前端传 `size=1000000`，SQL 就变成：

```sql
SELECT ... FROM biz_product LIMIT 0, 1000000
```

结果：
1. MySQL 要把**整张表**读出来，可能几秒钟
2. 结果全部加载进 JVM 内存 → **OutOfMemoryError**
3. 同时几个这样的请求，服务直接崩

**这不需要攻击者，一个手滑或者一个前端 bug 就能触发。**

所以后端强制 `Math.min(size, 100)`。**永远不要相信前端传来的分页参数。**

实测：

```
=== 26. size=99999 (期望被限制为 100) ===
size=100     ✅

=== 27. current=-5 (期望当作第 1 页) ===
current=1    ✅
```

`MybatisPlusConfig` 里还配了一层：

```java
pagination.setMaxLimit(100L);   // 插件层面也设上限
```

**双重保险**——即使有人绕过 `PageQuery` 直接用 `new Page<>()`，插件也会兜住。

## 6.7 详情页：权限判断 + 原子自增

### 未上架商品的可见性规则

```java
boolean owner = currentUserId != null && currentUserId.equals(product.getUserId());

if (!ProductStatus.ON_SALE.getCode().equals(product.getStatus()) && !owner) {
    if (currentUserId == null || !isAdmin(currentUserId)) {
        throw new BusinessException(ResultCode.PRODUCT_NOT_FOUND);
    }
}
```

规则：**只有上架商品对所有人可见；未上架的只有发布者本人和管理员能看。**

为什么？如果不判断，任何人拿到商品 ID 就能看到**还没过审的内容**——包括那些马上要被驳回的违规信息。

注意这里有个细节：抛的是 `PRODUCT_NOT_FOUND`（查不到）而不是 `FORBIDDEN`（没权限）。

**为什么？** 如果是"没权限"，攻击者就能通过报错信息**判断出这个 ID 确实存在**，从而枚举出所有商品的 ID 和数量。统一返回"不存在"，就不会泄漏任何信息。**这叫"不泄漏存在性"。**

### `isAdmin` 的懒加载优化

```java
// 注意 isAdmin 会查一次库，所以只在确实需要时才调用，
// 避免每次浏览详情都多一次查询
```

`isAdmin()` 内部要查一次 `sys_user` 表。如果把判断写在前面：

```java
boolean admin = currentUserId != null && isAdmin(currentUserId);   // ❌ 每次详情都多查一次库
```

那么**每一次正常的商品浏览**（占绝大多数流量）都会白白多一次数据库查询。放在 `if` 里面，只有"看未上架商品"这条冷路径才会触发。**这类优化在高并发下差别很明显。**

### 浏览量为什么必须用 SQL 原子自增

```java
if (!owner) {
    productMapper.update(null, Wrappers.<Product>lambdaUpdate()
            .setSql("view_count = view_count + 1")
            .eq(Product::getId, productId));
    vo.setViewCount(product.getViewCount() + 1);
}
```

**如果按直觉写成"查询 - 加 1 - 保存"会怎样？**

```
时刻 T1: 用户A 读到 view_count = 100
时刻 T2: 用户B 读到 view_count = 100
时刻 T3: 用户A 写回 101
时刻 T4: 用户B 写回 101     ← B 的写覆盖了 A 的，两次浏览只增加了 1
```

浏览量越热门越失真。**这叫"丢失更新"（Lost Update）。**

正确做法是让数据库自己算：

```sql
UPDATE biz_product SET view_count = view_count + 1 WHERE id = ?
```

数据库执行这条语句时会加行锁，两个请求会**串行执行**：100 → 101 → 102，一次都不会丢。

实测：

```
=== 16. 匿名查看详情 ===  viewCount=1
=== 17. 再看一次     ===  viewCount=2   ✅
```

另外注意 `if (!owner)`——**卖家自己看自己的商品不计数**，否则卖家反复刷新就能把浏览量刷上去。

### 详情 VO 的组装

详情需要的数据来自三张表：

```java
// 1. 商品本体
Product product = productMapper.selectById(productId);

// 2. 图片列表
List<ProductImage> images = productImageMapper.selectList(
        Wrappers.<ProductImage>lambdaQuery()
                .eq(ProductImage::getProductId, productId)
                .orderByAsc(ProductImage::getSort));

// 3. 分类名
Category category = categoryMapper.selectById(product.getCategoryId());

// 4. 卖家信息
User seller = userMapper.selectById(product.getUserId());
```

**这里用了 4 次单表查询而不是一条 JOIN**。为什么和列表页的写法不一样？

因为**详情页只查一条记录**，4 次主键查询（都是 `WHERE id = ?`，走聚簇索引，极快）比写一条复杂的 JOIN 更清晰、更容易维护。而列表页一次要查 20 条，JOIN 才有明显优势。

**同一份代码里两种写法并存并不是不一致，而是"根据场景选最合适的方案"。**

# 第七部分：前端页面实现

## 7.1 `ProductCard.vue`：为什么要抽组件

首页（8 个商品）和列表页（12 个商品）都要显示商品卡片，样式完全一样。如果各写一遍：

- 想改卡片样式，要改两个文件
- 两处写得不一样，页面风格就不统一

抽成组件后，**一处修改，处处生效**：

```vue
<ProductCard v-for="item in products" :key="item.id" :product="item" />
```

### `defineProps` 定义对外接口

```javascript
const props = defineProps({
  product: { type: Object, required: true },
  showStatus: { type: Boolean, default: false },       // 「我的发布」需要显示状态标签
  showOriginalPrice: { type: Boolean, default: true }  // 弹窗场景可能不需要
})
```

`props` 是**父组件传给子组件的数据**，在子组件里是**只读**的（子组件不能改 props，这是 Vue 的单向数据流规则）。

组件内部还做了一层业务判断：

```javascript
/** 原价低于售价时不展示，避免出现"原价 100 现价 200"的尴尬 */
const showOriginalPrice = computed(() => {
  const { originalPrice, price } = props.product
  if (!props.showOriginalPrice || !originalPrice) return false
  return Number(originalPrice) > Number(price)
})
```

## 7.2 首页：数据驱动的渲染 + 一个真实的坑

分类图标是从数据库读的字符串（`Iphone`、`Monitor`…），要动态渲染成组件：

```vue
<component :is="iconOf(c.icon)" />
```

`<component :is="...">` 是 Vue 的动态组件语法。

**这里的坑**：`is` 接字符串时，Vue 只在**全局注册的组件**里查找。我们在 `main.js` 里注册了全部 Element Plus 图标，所以能解析。

**但真正的坑是：如果图标名不存在，不会报错。**

我在测试时发现数据库里「游戏设备」用的是 `Gamepad`，而 Element Plus 的 293 个图标里**根本没有这个名字**。`vite build` 不会报错，控制台只有一行警告，页面上那一格就是空白。

修复分两步：

**① 改数据**（`init.sql` + 现有数据库）：

```sql
('游戏设备', 'VideoPlay', 7, 1),
```

**② 加代码兜底**：

```javascript
import * as ElIcons from '@element-plus/icons-vue'

/**
 * 分类图标是后台可编辑的数据，管理员万一填了不存在的图标名，
 * 这里兜底成默认图标，避免整块渲染失败。
 */
function iconOf(name) {
  return name && ElIcons[name] ? name : 'Goods'
}
```

**为什么要加兜底而不只是改数据？** 因为**图标名是管理员在后台填的数据**，不是写死在代码里的。以后管理员填错一个名字，页面不该整个坏掉。

> **这是"数据驱动的界面"必须考虑的问题**：只要渲染内容来自数据，就要考虑数据异常时的降级方案。

## 7.3 列表页：筛选状态管理

筛选条件是集中管理的一个响应式对象：

```javascript
const query = reactive({
  current: 1,
  size: 12,
  categoryId: null,
  keyword: '',
  conditionLevel: '',
  minPrice: null,
  maxPrice: null,
  sort: ''
})
```

这个对象**直接就是后端接口的参数**，不用来回转换：

```javascript
const data = await pageProducts(query)   // axios 自动把对象转成 ?current=1&size=12&...
```

### 为什么切筛选必须回到第 1 页

```javascript
/** 切换筛选条件时都要回到第 1 页，否则会出现"第 5 页没数据"的困惑 */
function reload() {
  query.current = 1
  loadList()
}
```

场景：用户在第 5 页（共 8 页），然后点了"只看手机"——手机只有 12 件，一共就 1 页。如果还去请求第 5 页，结果是**空白页**，用户以为系统坏了。

**所有筛选条件的变更都必须重置页码**，这是一个很容易漏掉的交互细节。

### 从首页跳转过来带参数

```javascript
onMounted(async () => {
  // 支持从首页分类跳转过来：/product/list?categoryId=1
  if (route.query.categoryId) {
    query.categoryId = Number(route.query.categoryId)
  }
  ...
})
```

首页点"手机"分类，跳转到 `/product/list?categoryId=1`，列表页读取 `route.query` 初始化筛选条件——**页面之间通过 URL 传参**，用户还能把这个 URL 复制给别人，对方打开就是同样的筛选结果。

## 7.4 发布页：三个技术点

### ① 表单校验：`rules` + `validate()`

```javascript
const rules = {
  categoryId: [{ required: true, message: '请选择商品分类', trigger: 'change' }],
  title: [
    { required: true, message: '请填写商品标题', trigger: 'blur' },
    { min: 2, max: 100, message: '标题长度为 2-100 个字符', trigger: 'blur' }
  ],
  price: [{ required: true, message: '请填写出售价格', trigger: 'change' }]
}
```

`trigger` 决定什么时候校验：

- `blur`：光标离开输入框时（适合文本）
- `change`：值变化时（适合下拉框、数字框）

提交时手动触发全量校验：

```javascript
const valid = await formRef.value.validate().catch(() => false)
if (!valid) return
```

`.catch(() => false)` 是必需的——`validate()` 校验失败会 **reject**，不 catch 就会抛出未处理的 Promise 异常。

### ② `el-upload` 自定义上传

```vue
<el-upload
  v-model:file-list="fileList"
  list-type="picture-card"
  :limit="9"
  accept="image/jpeg,image/png,image/gif,image/webp,image/bmp"
  :http-request="handleUpload"
  :before-upload="beforeUpload"
  :on-exceed="onExceed"
>
```

**为什么不直接用 `action` 属性指定上传地址？**

```vue
<!-- ❌ el-upload 默认自己发请求，不走我们的 axios -->
<el-upload action="/api/upload/image">
```

这样会绕开 `utils/request.js`，导致：

- **不会自动带 token** → 401
- **错误提示不统一** → 上传失败只会在控制台报错，用户看不到提示
- **结果结构不一样**

用 `:http-request` 把上传交给我们自己：

```javascript
function handleUpload(options) {
  return uploadImage(options.file)   // 走我们封装的 axios，直接返回 Promise
}
```

> ⚠️ **这里有个大坑，我实际踩过**：不能写成 `async` 函数 + 手动调 `options.onSuccess(url)`。
> el-upload 内部有 `if (request instanceof Promise) request.then(options.onSuccess, options.onError)`，
> 两者都做会让回调触发两次，第二次传的是 async 函数返回的 `undefined`，把结果覆盖掉。
> 完整排查过程见 [04-管理后台与商品审核实现讲解](04-管理后台与商品审核实现讲解.md#第九部分实战排查--图片上传成功却不显示)。

因为 el-upload 会把 Promise 的 resolve 值写进 `file.response`，所以取地址时：

```javascript
function collectImageUrls() {
  return fileList.value
    .map((f) => (typeof f.response === 'string' ? f.response : f.url))
    // 过滤掉 blob:/data: —— 浏览器本地预览地址，存进数据库就永远显示不出来
    .filter((url) => typeof url === 'string' && !url.startsWith('blob:') && !url.startsWith('data:'))
}
```

- **新上传的图片**：地址在 `f.response`（el-upload 上传成功后写入）
- **编辑时回填的图片**：地址在 `f.url`（从接口数据构造的）

**两种来源要分别处理**，这是编辑功能容易出 bug 的地方。

### ③ 参数编辑器的序列化

界面是一个"参数名 + 参数值"的动态行列表：

```javascript
const specList = ref([
  { key: '内存', value: '8GB' },
  { key: '存储', value: '256GB' }
])
```

提交时转成后端要的 JSON 字符串：

```javascript
function buildSpec() {
  const entries = specList.value
    .filter((row) => row.key && row.value)
    .map((row) => [row.key, row.value])
  return entries.length ? JSON.stringify(Object.fromEntries(entries)) : null
}
// 结果：'{"内存":"8GB","存储":"256GB"}'
```

`Object.fromEntries()` 把 `[['内存','8GB'], ['存储','256GB']]` 转成 `{内存: '8GB', 存储: '256GB'}`，`JSON.stringify` 再转成字符串。

编辑时反向操作：

```javascript
function parseSpec(spec) {
  if (!spec) return []
  try {
    return Object.entries(JSON.parse(spec)).map(([key, value]) => ({ key, value }))
  } catch {
    return []
  }
}
```

`catch` 不能省——如果数据库里的 spec 因为历史原因不是合法 JSON，`JSON.parse` 会抛异常，整个表单都渲染不出来。

### ④ 分类专属参数提示

```javascript
const SPEC_PRESETS = {
  手机: ['内存', '存储', '电池健康', '版本', '是否拆修'],
  笔记本电脑: ['处理器', '内存', '硬盘', '显卡', '屏幕'],
  相机/摄像机: ['有效像素', '快门次数', '镜头', '配件'],
  ...
}

const presets = computed(() => {
  const category = categories.value.find((c) => c.id === form.categoryId)
  if (!category) return []
  const all = SPEC_PRESETS[category.name] || []
  const used = new Set(specList.value.map((r) => r.key))
  return all.filter((p) => !used.has(p))   // 已经加过的不再提示
})
```

用户选了"手机"分类，下面就出现"内存 / 存储 / 电池健康"这些快捷标签，点一下自动加一行。

**这就是需求里"行业针对性强"在交互层的体现**——用户不用自己想该填什么参数，平台已经按品类给好了引导。

### ⑤ 一个页面同时支持新增和编辑

```javascript
const productId = computed(() => route.params.id)
const isEdit = computed(() => !!productId.value)
```

路由 `/publish` 和 `/publish/:id` 指向**同一个组件**。有 `id` 就是编辑，没 `id` 就是新增。

```javascript
if (isEdit.value) {
  await updateProduct(productId.value, payload)
} else {
  await createProduct(payload)
}
```

**为什么合并？** 因为两种情况下的表单**完全一样**，拆成两个组件意味着 95% 的代码重复。合并后用 `isEdit` 控制少数几处差异（标题文案、提交接口、是否回填数据）。

## 7.5 详情页：按身份渲染不同按钮

```vue
<div class="actions">
  <template v-if="product.owner">
    <el-button type="primary" @click="router.push(`/publish/${product.id}`)">编辑商品</el-button>
    <el-button v-if="product.status === 1" @click="handleOffShelf">下架</el-button>
    <el-button v-if="product.status === 2 || product.status === 4" @click="handleResubmit">
      重新提交审核
    </el-button>
    <el-button type="danger" plain @click="handleDelete">删除</el-button>
  </template>
  <template v-else>
    <el-button type="primary" disabled>收藏</el-button>
    <el-button disabled>联系卖家</el-button>
  </template>
</div>
```

`product.owner` 是后端算好返回的（`currentUserId.equals(product.getUserId())`）。

**为什么不让前端自己判断"当前用户ID 是否等于 sellerId"？** 因为那需要前端也维护一份"当前用户ID"，多一个可能不一致的数据源。**后端已经知道你是谁了，顺手算好返回更可靠。**

按钮的显示条件直接对应状态机的合法流转：

| 状态 | 显示的操作 |
| --- | --- |
| 待审核(0) | 编辑、删除 |
| 已上架(1) | 编辑、下架、删除 |
| 已下架(2) | 编辑、重新提交、删除 |
| 已售出(3) | 查看（不能编辑/删除） |
| 驳回(4) | 编辑、重新提交、删除 |

> 前端控制的只是"按钮显不显示"，**真正的规则校验在后端**。就算用户手动调接口，后端照样拦截。

驳回原因用 `el-alert` 突出显示，让卖家一眼看到问题：

```vue
<el-alert v-if="product.status === 4" type="error" show-icon :closable="false">
  <template #title>审核未通过：{{ product.rejectReason || '未填写原因' }}</template>
  修改商品信息后可以重新提交审核。
</el-alert>
```

## 7.6 我的发布：Tab 与服务端筛选

```javascript
function handleTabChange() {
  query.status = activeTab.value === 'all' ? null : Number(activeTab.value)
  query.current = 1
  loadList()
}
```

切换 Tab 就是**改变查询参数重新请求后端**，而不是把所有数据拉到前端再过滤。

**为什么要服务端筛选？** 如果用户有 500 件商品，前端过滤就意味着要一次性拉 500 条数据。服务端筛选每次只传 10 条，**数据量再大也不影响**。

待审核数量用一个小徽标提示：

```javascript
async function loadPendingCount() {
  const data = await myProducts({ current: 1, size: 1, status: 0 })
  pendingCount.value = Number(data.total)
}
```

注意 `size: 1`——我们**只要 `total` 这个数字**，不需要具体数据，传 1 条就够了。比拉全量再 `length` 高效得多。

## 7.7 路由设计：为什么要加 `\d+`

```javascript
{
  path: 'product/:id(\\d+)',
  name: 'ProductDetail',
  component: () => import('@/views/product/Detail.vue')
}
```

`:id(\\d+)` 是**正则约束**，意思是这个参数必须是一个或多个数字。

如果不加约束会怎样？路由 `/product/list` 和 `/product/:id` 都会匹配 `/product/xxx`，产生歧义。加上 `\d+` 之后：

- `/product/list` → 只能匹配到列表路由
- `/product/123` → 只能匹配到详情路由

**用规则消除歧义，比靠匹配顺序更可靠。**

## 7.8 个人中心：两个表单 + 头像上传

资料表单提交后要**同步更新全局登录态**：

```javascript
const data = await updateProfile(profileForm)
userStore.setUserInfo(data)     // ← 关键
ElMessage.success('资料已更新')
```

**为什么必须调 `setUserInfo`？** 因为导航栏右上角显示的是 `userStore.nickname`，它读的是 Pinia 里的数据。只更新后端数据库而不更新本地 store，导航栏会一直显示旧昵称，**必须刷新页面才变**。

改密码后的处理：

```javascript
await changePassword({ oldPassword, newPassword })
ElMessage.success('密码修改成功，请重新登录')
userStore.clearLogin()      // 密码变了，旧 token 继续用有隐患
router.push('/login')
```

**为什么强制重新登录？** 因为当前这个 JWT 是用旧密码签发的，仍然有效。如果密码是因为"账号被盗"而修改的，攻击者手里的旧 token 还能继续用 72 小时——**改密码就失去意义了**。

（更彻底的做法是把旧 token 加入黑名单，那需要引入 Redis，本项目作为毕业设计暂时从简，但要知道这个点。）

# 第八部分：安全清单与自查

把这一阶段所有安全设计集中列出来，**答辩时可以直接讲这张表**：

| 攻击手法 | 后果 | 本项目的防护 | 代码位置 |
| --- | --- | --- | --- |
| 上传可执行文件 | 服务器被植入后门 | 后缀白名单，只允许 6 种图片格式 | `FileServiceImpl` |
| 路径穿越 `../../x.jsp` | 文件写到任意目录、覆盖配置 | UUID 重命名，用户输入不参与路径 | `FileServiceImpl` |
| 超大文件上传 | 磁盘写满 | 大小双重限制（Spring + 业务层） | `application.yml` + `FileServiceImpl` |
| 匿名刷上传 | 磁盘被占满（DoS） | 上传接口必须登录 | `UploadController` |
| 改 ID 操作别人商品 | 恶意下架/删除他人商品 | `requireOwner()` 校验归属 | `ProductServiceImpl` |
| 改 ID 看未过审内容 | 违规信息提前扩散 | 非上架商品仅本人/管理员可见 | `ProductServiceImpl.detail()` |
| ORDER BY 注入 | 拖库、删表 | `<choose>` 白名单，仅 4 个固定值 | `ProductMapper.xml` |
| LIKE 注入 | 数据泄漏 | `#{}` 预编译 + `CONCAT` | `ProductMapper.xml` |
| 分页攻击 `size=1000000` | 内存溢出、服务崩溃 | 上限 100（业务层 + 插件双重） | `PageQuery` / `MybatisPlusConfig` |
| 先过审再改违规内容 | 审核形同虚设 | 编辑后状态回到待审核 | `ProductServiceImpl.update()` |
| 状态机被绕过 | 数据矛盾 | 每个操作校验前置状态 | `ProductServiceImpl` |
| 前端绕过提交非法数据 | 脏数据入库 | `@Valid` 注解校验 | `ProductSaveDTO` |
| 用报错枚举商品 ID | 泄漏数据量 | 统一返回"商品不存在" | `ProductServiceImpl.detail()` |
| 浏览量并发丢失 | 统计失真 | SQL 原子自增 `view_count + 1` | `ProductServiceImpl.detail()` |
