# 第二部分：收藏 —— 计数一致性是核心

## 2.1 表结构回顾：为什么没有 deleted

```java
/**
 * 注意这张表**没有 deleted 字段**，取消收藏就是物理删除。
 * 这是第一阶段特意做的设计：如果收藏也用逻辑删除，
 * (user_id, product_id) 这个唯一索引会和它打架 ——
 * 取消收藏后置 deleted=1，再收藏一次插入新行就会撞唯一键。
 */
@TableName("biz_favorite")
public class Favorite { ... }
```

这是第一阶段那个"逻辑删除 + 唯一索引"问题**第三次**体现它的影响：

| 表 | 处理方式 | 原因 |
| --- | --- | --- |
| `sys_user` | 不做逻辑删除 | `username` 唯一索引 |
| `sys_category` | 不建唯一索引，服务层校验 | 分类名要唯一但又要能逻辑删除 |
| `biz_favorite` | **物理删除** | `(user_id, product_id)` 唯一索引 |

**同一张"逻辑删除"的牌，在三张表上打出了三种不同的结果。** 这就是为什么数据库设计不能套模板。

## 2.2 收藏：靠唯一索引兜并发

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void add(Long userId, Long productId) {
    Product product = requireProduct(productId);

    // 不能收藏自己的商品 —— 否则卖家可以自己给自己刷收藏数，制造"很抢手"的假象
    if (product.getUserId().equals(userId)) {
        throw new BusinessException(ResultCode.FAVORITE_SELF);
    }
    // 只在售的商品才能收藏。已下架/已售出/待审核的收藏了也没意义
    if (!ProductStatus.ON_SALE.getCode().equals(product.getStatus())) {
        throw new BusinessException(ResultCode.PRODUCT_NOT_ON_SALE,
                "该商品当前状态为「" + ProductStatus.descOf(product.getStatus()) + "」，暂时无法收藏");
    }

    Favorite favorite = new Favorite();
    favorite.setUserId(userId);
    favorite.setProductId(productId);
    favorite.setCreateTime(LocalDateTime.now());

    try {
        favoriteMapper.insert(favorite);
    } catch (DuplicateKeyException e) {
        // 靠 (user_id, product_id) 唯一索引兜并发。
        // 比"先查有没有再插入"可靠：两个请求同时点收藏，先查后插会双双通过检查。
        throw new BusinessException(ResultCode.ALREADY_FAVORITE);
    }

    // 用 SQL 原子自增，理由和浏览量一样：先查再改会丢计数
    productMapper.update(null, Wrappers.<Product>lambdaUpdate()
            .setSql("favorite_count = favorite_count + 1")
            .eq(Product::getId, productId));
}
```

### 为什么"先查后插"不可靠

```
时刻 T1: 请求A 检查 "用户1 收藏了商品1 吗？" → 没有
时刻 T2: 请求B 检查 "用户1 收藏了商品1 吗？" → 没有
时刻 T3: 请求A 插入成功
时刻 T4: 请求B 插入成功          ← 同一个人对同一件商品有两条收藏记录
```

用户快速双击收藏按钮就能触发。**`favorite_count` 会变成 2，而收藏列表里有两条一模一样的记录。**

用唯一索引 + 捕获 `DuplicateKeyException`，第二条插入会被数据库直接拒绝。**这是"让数据库帮你保证一致性"的典型用法。**

> 这个模式在项目里已经用过一次：用户注册时的 `username` 唯一索引
> （`UserServiceImpl.register()` 里也捕获了 `DuplicateKeyException`）。
> **凡是"某个组合不能重复"的业务，第一反应都应该是建唯一索引。**

### 顺带修正的提示文案

原来直接抛 `ResultCode.PRODUCT_NOT_ON_SALE`，提示是"商品已下架或已售出"。

但用户可能在看一个**待审核**的商品（比如他自己的另一个商品刚通过、或者别人分享的链接），提示"已下架或已售出"就对不上他眼前的画面。

改成带上真实状态：

```
{"code":5004,"message":"该商品当前状态为「待审核」，暂时无法收藏"}
```

> **错误提示要能对应用户当前看到的东西。**
> 用户在页面上看到"待审核"，你却告诉他"已下架"，他只会更困惑。

## 2.3 取消收藏：两级保护

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void remove(Long userId, Long productId) {
    // 带 userId 条件删除：只能取消自己的收藏
    int rows = favoriteMapper.delete(Wrappers.<Favorite>lambdaQuery()
            .eq(Favorite::getUserId, userId)
            .eq(Favorite::getProductId, productId));
    if (rows == 0) {
        throw new BusinessException(ResultCode.NOT_FAVORITE);
    }

    // GREATEST(..., 0) 保证计数不会被减成负数
    productMapper.update(null, Wrappers.<Product>lambdaUpdate()
            .setSql("favorite_count = GREATEST(favorite_count - 1, 0)")
            .eq(Product::getId, productId));
}
```

### 第一层：`userId` 条件不能省

删除语句里必须带 `user_id`。如果只按 `product_id` 删：

```
用户A 点"取消收藏商品1" → DELETE FROM biz_favorite WHERE product_id = 1
                        → 把【所有人】对商品1的收藏全删了
```

**这是灾难性的。** 而且因为"取消收藏"是个不起眼的操作，这种 bug 可能上线很久才被发现。

> **写删除/更新语句时，问自己一句："这个条件够不够限定到我想操作的那一条？"**
> 更新比查询更需要小心：查询带错条件最多是"看到别人的数据"，更新带错条件是"改了别人的数据"。

### 第二层：`GREATEST(..., 0)` 加下限

```sql
SET favorite_count = GREATEST(favorite_count - 1, 0)
```

正常流程下 `favorite_count` 不会被减成负数（因为 `rows == 0` 时已经抛异常了）。那为什么还要加？

因为**数据可能因为别的原因不一致**：
- 手工改过数据库
- 迁移脚本出错
- 将来某个新功能忘了同步这个计数

一旦变成负数，页面上会出现"收藏 -1"，用户截图发到群里，你就得去数据库里翻。**加一个 `GREATEST` 的成本接近于零，但它让"计数出问题"这个类别里少了一种可能。**

## 2.4 详情页的 favorite 字段从哪来

```java
vo.setOwner(owner);
// 是否已收藏：只有登录用户才有意义，游客一律 false。
// 这里直接问 FavoriteService，而不是自己再写一遍收藏表的查询 ——
// "怎么判断收藏"这件事只应该有一处实现。
vo.setFavorite(currentUserId != null
        && favoriteService.isFavorite(currentUserId, productId));
```

**为什么调 `FavoriteService` 而不是自己写查询？** 因为"如何判断一个用户是否收藏了某商品"这个知识应该只有一个出处。将来如果改成"缓存在 Redis 里"，只需要改 `FavoriteServiceImpl`。

这是**服务之间的复用**——`ProductServiceImpl` 依赖 `FavoriteService`，没有循环依赖（`FavoriteService` 不反向依赖 `ProductService`）。

> 对比一下：如果每次遇到"判断收藏"都在各自的服务里写一遍 SQL，
> 三处之后你就会忘记哪一处的逻辑才是对的。

## 2.5 我的收藏列表：JOIN 查询

```xml
<!--
  我的收藏列表：收藏记录 JOIN 商品。
  注意 biz_favorite 没有 deleted 字段（取消收藏是物理删除），
  但 biz_product 有，所以这里必须写 p.deleted = 0 —— 否则已删除的商品
  还会出现在别人的收藏夹里，点进去却是"商品不存在"。
-->
<select id="selectFavoriteProductPage" resultType="com.digital.platform.vo.ProductListVO">
    SELECT p.id, p.title, p.cover_image AS coverImage, ...
    FROM biz_favorite f
    INNER JOIN biz_product p ON p.id = f.product_id AND p.deleted = 0
    LEFT JOIN sys_category c ON c.id = p.category_id AND c.deleted = 0
    LEFT JOIN sys_user u ON u.id = p.user_id
    WHERE f.user_id = #{userId}
    ORDER BY f.create_time DESC, f.id DESC
</select>
```

### 这里 JOIN 类型的选择是有讲究的

```sql
INNER JOIN biz_product p       -- 商品不存在就整条不显示
LEFT JOIN sys_category c       -- 分类没了还是要显示商品
LEFT JOIN sys_user u           -- 用户异常也要显示商品
```

**主表用 `INNER JOIN`，附属表用 `LEFT JOIN`。**

- 商品被删了 → 这条收藏记录没有展示价值 → **不显示（INNER）**
- 分类被停了 → 商品还是要展示的，只是分类名显示为空 → **显示（LEFT）**
- 卖家账号异常 → 商品还是要展示的 → **显示（LEFT）**

**这条规则可以套用到项目里所有列表查询**：主实体用 INNER，装饰性关联用 LEFT。

# 第三部分：留言 —— 两级结构怎么设计

## 3.1 为什么只做两级

表结构里用了 `parent_id`：

```java
/**
 * 用 parent_id 实现两级结构：
 *   parent_id = 0  → 对商品的一级留言（咨询）
 *   parent_id = X  → 回复第 X 条留言
 * 只做两级而不是无限嵌套，是因为二手交易的留言场景就是"买家问、卖家答"，
 * 无限嵌套的树在界面上反而难用。**够用就好。**
 */
private Long parentId;
```

**无限嵌套听起来更强大，实际上更难用。** 三层以上的留言在窄屏上缩进到没地方放文字，而且很少有人真的会看完 5 层对话。知乎、B站、GitHub 的评论都是两到三层就封顶了。

**需求是"在线交流咨询"，不是"论坛"。** 两级完全够。

## 3.2 ⚠️ 最关键的坑：第三层会永远消失

假设用户点的是**一条回复**下面的"回复"按钮，前端老老实实把那条回复的 id 传上来了。如果后端直接 `parent_id = 那条回复的id`：

```
留言1 (parent_id = 0)  ← 一级留言
  └─ 留言2 (parent_id = 1)  ← 卖家回复
       └─ 留言3 (parent_id = 2)  ← 买家回复，指向的是【回复】而不是【一级留言】
```

而查询回复时是这样写的：

```java
.in(Comment::getParentId, parentIds)   // parentIds 只包含一级留言的 id
```

`留言3` 的 `parent_id` 是 `2`，不在 `parentIds`（只含 `1`）里，**所以它永远不会被查出来**。

用户在页面上打了字、点了发送、看到"回复成功"，刷新之后——**那条留言不见了。**

### 解法：在后端归并

```java
// 被回复的人是这条留言的作者
replyUserId = target.getUserId();
notifyUserId = target.getUserId();

// 关键：把"回复某条回复"归并到同一条一级留言下。
// 本项目只做两级，如果允许 parent_id 指向一条回复，就会产生第三层，
// 而查询时只取 parent_id IN (一级留言ID) 的回复 —— 那条留言会永远显示不出来。
// 归并之后，"被回复人"仍然是那条回复的作者，对话读起来是连贯的。
rootParentId = target.getParentId() == 0L ? target.getId() : target.getParentId();
```

一行代码做两件事：

| 存储字段 | 值 | 作用 |
| --- | --- | --- |
| `parentId` | 归并到一级留言的 id | **保证能被查出来** |
| `replyUserId` | 被点击那条留言的作者 | **保证"回复谁"是对的** |

**用一个字段表达"归到哪条线程"，用另一个字段表达"答复谁"。** 两个信息分开存，就不会互相牵制。

实测验证（C8）：

```
threads = 1
  thread[3] 李四: 请问还能小刀吗？配件齐全吗？可以当面验机吗？
      reply[4] parentId=3 张三 replyTo=李四      ← 卖家回复
      reply[5] parentId=3 李四 replyTo=张三      ← 买家回复"回复4"，parentId 被归并成 3
```

`reply[5]` 的 `parentId=3`（不是 4），同时 `replyTo=张三` 保留了正确性。**两个目标同时达成。**

> **做树形结构时，"数据怎么存"和"用户看到了什么"要分开想。**
> 用户表达的是"我在回复这一条"，而存储需要的是"这条属于哪个线程"。
> **在边界处做转换，而不是强迫前端理解你的存储结构。**

## 3.3 查询：三次请求，避免 N+1

```java
@Override
public List<CommentVO> listByProduct(Long productId, Long currentUserId, boolean isAdmin) {
    Product product = requireProduct(productId);

    // 第 1 次查询：所有一级留言（新的在前）
    List<Comment> topLevel = commentMapper.selectList(Wrappers.<Comment>lambdaQuery()
            .eq(Comment::getProductId, productId)
            .eq(Comment::getParentId, 0L)
            .eq(Comment::getStatus, Constants.STATUS_ENABLED)
            .orderByDesc(Comment::getCreateTime)
            .orderByDesc(Comment::getId));

    if (topLevel.isEmpty()) {
        return List.of();     // ← 提前返回，一个回复都没有的常见情况不用再查
    }

    // 第 2 次查询：这些留言下的所有回复
    List<Long> parentIds = topLevel.stream().map(Comment::getId).toList();
    List<Comment> replies = commentMapper.selectList(Wrappers.<Comment>lambdaQuery()
            .eq(Comment::getProductId, productId)
            .in(Comment::getParentId, parentIds)
            .eq(Comment::getStatus, Constants.STATUS_ENABLED)
            .orderByAsc(Comment::getCreateTime)
            .orderByAsc(Comment::getId));

    // 第 3 次查询：批量把用到的用户一次查出来
    Map<Long, User> userMap = loadUsers(topLevel, replies);
    ...
}
```

### N+1 问题是什么

如果偷懒，很容易写成这样：

```java
for (Comment c : comments) {
    User u = userMapper.selectById(c.getUserId());    // ❌ 每条留言查一次用户
    vo.setUserNickname(u.getNickname());
}
```

20 条留言 = 1 次查留言 + 20 次查用户 = **21 次数据库往返**。

**这就是 N+1 问题**：1 次主查询，N 次关联查询。数据量小时看不出来，一旦某个商品的留言多起来，这个接口就会明显变慢。

### 正确做法：批量查一次

```java
/**
 * 一次性把所有相关用户查出来，返回 id -> User 的映射。
 * 这就是解决 N+1 问题的标准做法：把"每条记录查一次"变成"一次查一批"。
 */
private Map<Long, User> loadUsers(List<Comment> topLevel, List<Comment> replies) {
    Set<Long> userIds = new HashSet<>();
    topLevel.forEach(c -> userIds.add(c.getUserId()));
    replies.forEach(c -> {
        userIds.add(c.getUserId());
        if (c.getReplyUserId() != null) {
            userIds.add(c.getReplyUserId());      // 被回复人也要查出来显示昵称
        }
    });

    if (userIds.isEmpty()) {
        return Map.of();
    }
    return userMapper.selectBatchIds(userIds).stream()
            .collect(Collectors.toMap(User::getId, Function.identity()));
}
```

**21 次往返变成 3 次，而且留言数量再多也是 3 次。**

注意 `userIds` 用 `Set` 而不是 `List`：同一个人可能发了好几条留言，用 `Set` 自动去重，`selectBatchIds` 不会重复查同一个人。

> **凡是"循环里查数据库"的写法，都要停下来想一想。**
> 几乎总能改成"先收集 ID，再批量查一次"。

### 组装：用 `groupingBy` 一次分组

```java
// 按 parentId 把回复分组，再挂到对应的一级留言上
Map<Long, List<CommentVO>> replyGroup = replies.stream()
        .map(c -> toVO(c, userMap, currentUserId, isProductOwner, isAdmin))
        .collect(Collectors.groupingBy(CommentVO::getParentId));

return topLevel.stream()
        .map(c -> {
            CommentVO vo = toVO(c, userMap, currentUserId, isProductOwner, isAdmin);
            vo.setReplies(replyGroup.getOrDefault(c.getId(), List.of()));
            return vo;
        })
        .toList();
```

`Collectors.groupingBy` 把回复列表按 `parentId` 分组，然后每条一级留言直接从 map 里取自己的回复。

**如果不用它，就要写两层嵌套循环，复杂度从 O(n) 变成 O(n²)。**

## 3.4 删除：连带隐藏，避免"孤儿回复"

```java
// 软删除：保留记录，状态置为已删除
commentMapper.update(null, Wrappers.<Comment>lambdaUpdate()
        .set(Comment::getStatus, Constants.STATUS_DISABLED)
        .eq(Comment::getId, commentId));

// 一级留言被删时，它下面的回复也一起隐藏。
// 否则列表里会只剩一堆"回复某某"的孤儿，读者完全看不懂在说什么。
if (0L == comment.getParentId()) {
    commentMapper.update(null, Wrappers.<Comment>lambdaUpdate()
            .set(Comment::getStatus, Constants.STATUS_DISABLED)
            .eq(Comment::getParentId, commentId));
}
```

**只删父不删子会怎样？** 列表里会出现：

```
（问题不见了）

     回复 李四：好的，那明天见
     回复 张三：没问题
```

读者完全不知道他们在聊什么。**这两句回复比不显示更让人困惑。**

两个 `update` 在同一个事务里，要么都成功要么都不做。

> 注意删除用的是 `status = 0` 而不是物理删除 ——
> `biz_comment` 里没有 `deleted` 字段，但这个问题**留了可追溯性**：
> 被删除的留言仍然在数据库里，出问题能查。

# 第四部分：权限边界 —— 谁能在什么商品下说什么话

## 4.1 一级留言不能让发布者自己发

```java
if (isReply) {
    ...
} else {
    // 一级留言（咨询）不能由商品发布者自己发。
    // 否则卖家可以自问自答刷热度，看起来"很受欢迎"。
    if (product.getUserId().equals(userId)) {
        throw new BusinessException(ResultCode.CANNOT_COMMENT_SELF);
    }
    notifyUserId = product.getUserId();
}
```

**为什么？** 如果允许，卖家可以：

```
卖家：这台手机成色怎么样？
卖家：非常新，9成新，无拆无修！
卖家：能便宜点吗？
卖家：已经是最低价了，很划算的！
```

**一场自导自演的对话**，让商品看起来很受关注。这是典型的刷热度手段，和其他平台刷评价是一个性质。

**但发布者**回复**别人**的留言是必须允许的**——这正是卖家答疑的主要方式。

实测：

```
=== C2. zhangsan comments on his OWN product 1 ===
{"code":7002","message":"不能给自己的商品留言"}
```

## 4.2 商品状态限制

```java
/** 待审核 / 已下架 / 被驳回的商品不该有留言入口 */
private void checkProductCommentable(Product product) {
    Integer status = product.getStatus();
    boolean ok = ProductStatus.ON_SALE.getCode().equals(status)
            || ProductStatus.SOLD.getCode().equals(status);
    if (!ok) {
        throw new BusinessException(ResultCode.PRODUCT_STATUS_ILLEGAL, "该商品当前不支持留言咨询");
    }
}
```

**允许"已售出"的商品留言**，是因为交易后双方可能还要沟通（什么时候面交、地址在哪）。而待审核/已下架的商品根本不该有留言入口。

## 4.3 `canDelete` 由后端算好

```java
// 删除权限由后端算好直接告诉前端，前端不用（也无法）自己判断。
// 三种人可以删：留言作者本人、商品发布者、平台管理员。
vo.setCanDelete(currentUserId != null
        && (isAdmin || isProductOwner || currentUserId.equals(c.getUserId())));
```

**为什么不让前端自己判断？**

前端要判断就得知道三件事：当前用户 id、留言作者 id、商品发布者 id。前两个好办，但"商品发布者 id"前端也有——**看起来能算。但这是错的思路。**

因为：
1. **前端算出来的只是"按钮显不显示"**，后端删除接口里必须再校验一遍（前端可以被绕过）
2. **两处实现同一套规则，一定会有对不上的一天**
3. 后端顺手算好只有一行代码

实测：

```
=== C4. anonymous reads list ===   canDelete=False    ← 游客不能删
=== C5. owner reads list ===       canDelete=True     ← 发布者可以删
```

同一份数据，不同身份看到不同的 `canDelete`——**这正是"服务端按身份定制响应"的价值。**

## 4.4 删除的三方权限

```java
Product product = productMapper.selectById(comment.getProductId());
boolean isAuthor = comment.getUserId().equals(userId);
// 商品发布者可以删除自己商品下的留言（比如广告、人身攻击）
boolean isProductOwner = product != null && product.getUserId().equals(userId);

if (!isAdmin && !isAuthor && !isProductOwner) {
    throw new BusinessException(ResultCode.NOT_COMMENT_OWNER);
}
```

| 谁 | 能删什么 | 为什么 |
| --- | --- | --- |
| 留言作者 | 自己的留言 | 说错话了想删掉 |
| **商品发布者** | **自己商品下的任何留言** | 要去掉广告、辱骂、无关内容 |
| 平台管理员 | 任何留言 | 违规处置 |

**给发布者"删除自己商品下留言"的权限很关键。** 没有它，有人到你商品下面发广告，你只能举报等管理员处理——**而他换个商品继续发**。

实测：

```
=== C12. lisi deletes zhangsans reply ===
{"code":7004","message":"只能删除自己的留言"}      ← 既不是作者也不是发布者

=== C13. owner zhangsan deletes lisis thread ===
{"code":200","message":"已删除"}
threads on product 1 after delete = 0              ← 整个线程（含回复）都隐藏了
```

## 4.5 跨商品的回复

```java
// 防止回复到别的商品下面的留言上，那样前端组装两级结构会乱掉
if (!target.getProductId().equals(product.getId())) {
    throw new BusinessException(ResultCode.COMMENT_PRODUCT_MISMATCH);
}
```

用户完全可以在浏览器控制台里构造请求：`productId = 1`（我能看的商品）但 `parentId` 指向商品 2 的留言。

**不校验的话，商品 1 的留言区里会挂上商品 2 的对话**，前端按 `parentId` 分组时找不到对应的父留言，那几条回复直接消失。

实测：

```
=== C11. reply to a comment of ANOTHER product ===
{"code":7003","message":"回复的留言不属于该商品"}
```

> **凡是前端传来的"关联 ID"，都要校验"这些 ID 之间的关系是否成立"。**
> 只校验 `productId` 存在、`parentId` 存在是不够的，**还要校验它们属于同一条业务链路。**

## 4.6 通知：只通知相关的人

```java
// 通知对方。自己回复自己就不必通知了，否则会收到一堆自己的消息
if (!notifyUserId.equals(userId)) {
    String title = isReply ? "你的留言收到回复" : "你的商品收到新留言";
    ...
    notificationService.send(notifyUserId, NotificationType.COMMENT, title, content, product.getId());
}
```

**通知对象：**

| 场景 | 通知谁 |
| --- | --- |
| 一级留言 | 商品发布者（有人来咨询了） |
| 回复 | 被回复留言的作者 |

**通知的 `bizId` 存的是商品 ID**，这样前端点击通知能直接跳到商品详情页去看完整对话：

```js
// 审核结果(type=1)和留言回复(type=3)的 bizId 存的都是商品ID，
// 点击直接跳到对应商品详情，用户不用自己去搜

```

实测通知内容：

```
[你的商品收到新留言] 有人咨询了你发布的「iPhone 14 Pro 256G 暗紫色」：请问还能小刀吗？...
[你的留言收到回复]   李四 回复了你在「iPhone 14 Pro 256G 暗紫色」下的留言：好的，那我明天下午...
```

### 内容要截断

```java
/** 通知正文里截断留言内容，避免超出 sys_notification.content 的 500 字符上限 */
private static final int NOTIFY_CONTENT_MAX = 200;

... + StrUtil.maxLength(dto.getContent(), NOTIFY_CONTENT_MAX)
```

留言最长 500 字符，加上"某某 回复了你在「很长很长的商品标题」下的留言："这段前缀，很容易**超过 `sys_notification.content` 的 500 字符上限**。

不截断的话，MySQL 在严格模式下会直接报错，导致整个留言功能失败——**用户只是想留个言，结果因为写太长了而报服务器错误。**

> **拼接字符串写入有长度限制的字段时，一定要先算一下上限。**
> 这是"看起来没问题、实际上有隐患"的典型场景。

# 第五部分：三个异常处理补丁

这一轮测试时顺手发现了三个"不是功能 bug、但会误导排查"的问题。**都是同一个主题：错误的类型要正确表达。**

## 5.1 发现过程

我在测试脚本里写错了一个变量，导致请求路径变成 `/api/comment/`（ID 为空）。结果：

```
=== 删除别人的留言 ===
{"code":500,"message":"服务器开小差了，请稍后重试"}
```

**返回了 500。** 但这个问题明明是客户端的（地址写错了），不该报"服务器故障"。

顺着这条线索查下去，发现了三处：

## 5.2 补丁一：参数类型转换失败应该是 400

`/api/comment/` 这种路径，Spring 会尝试把空字符串转成 `Long`（Controller 的参数是 `@PathVariable Long id`），转换失败抛 `MethodArgumentTypeMismatchException`。

**我们的 `GlobalExceptionHandler` 没有单独处理它，于是落到了最后的 `Exception` 兜底 → 500。**

```java
/**
 * 路径参数 / 查询参数类型转换失败。
 * <p>
 * 比如 GET /api/comment/ 这样的空 ID，或者 ?id=abc 传了个非数字给 Long 参数。
 * 这类问题在客户端，属于 400，不该落到兜底处理器变成 500 ——
 * 500 会让排查的人以为是服务端故障，白跑一趟。
 */
@ExceptionHandler(MethodArgumentTypeMismatchException.class)
public Result<Void> handleTypeMismatch(MethodArgumentTypeMismatchException e) {
    return Result.fail(ResultCode.PARAM_ERROR, "参数 " + e.getName() + " 格式不正确");
}
```

实测：

```
=== V2. non-numeric id ===
{"code":400,"message":"参数 id 格式不正确"}
```

## 5.3 补丁二：找不到接口应该是 404

修完上面那个之后，`/api/comment/` 还是 500。因为**带尾斜杠的路径根本匹配不到任何接口**——Spring Boot 3 默认关闭了尾斜杠匹配。

Spring Boot 3.2 起，匹配不到接口会抛 `NoHandlerFoundException`，同样落到了兜底处理器。

```java
/**
 * 找不到对应的接口（URL 打错了、路径多了个斜杠等）。
 * <p>
 * Spring Boot 3.2 起默认会抛这个异常，如果不单独接住就会落到兜底处理器变成 500。
 * 地址写错是客户端问题，必须是 404。
 */
@ExceptionHandler(NoHandlerFoundException.class)
public Result<Void> handleNotFound(NoHandlerFoundException e) {
    return Result.fail(ResultCode.NOT_FOUND, "接口不存在：" + e.getHttpMethod() + " " + e.getRequestURL());
}

/**
 * 静态资源不存在（比如访问了一个不存在的图片地址）。
 */
@ExceptionHandler(NoResourceFoundException.class)
public Result<Void> handleNoResourceFound(NoResourceFoundException e) {
    return Result.fail(ResultCode.NOT_FOUND, "资源不存在：" + e.getResourcePath());
}
```

实测：

```
=== V1. bad path param ===
{"code":404,"message":"资源不存在：api/comment"}
```

### 为什么这件事值得较真

有人可能会想："不就是个状态码吗，能用就行。"

**但状态码是给"下一个人"看的。** 场景：

1. 前端调接口报错了，提示"服务器开小差了"
2. 前端开发者去找后端："你们服务是不是挂了？"
3. 后端去看日志，发现是前端把 URL 拼错了一个斜杠
4. **两个人白花半小时**

如果返回 404 + "接口不存在：DELETE /api/comment"，**前端开发者自己一眼就能定位。**

> **错误处理的本质是"把问题准确传递给下一个人"。**
> 500 的含义是"服务端出了预料之外的故障"，用它来掩盖一个拼错的 URL，是信息的损失。

## 5.4 关于"错误码分类"的一点小结

修复后，各类错误的语义变得清晰：

| 情况 | 状态码 | 谁的问题 |
| --- | --- | --- |
| 参数格式错（`?id=abc`、空 ID） | 400 | 客户端 |
| 参数校验失败（必填没填、超长） | 400 + 具体字段提示 | 客户端 |
| **接口不存在**（URL 打错） | **404** | 客户端 |
| 请求方法不对（用 GET 调 POST 接口） | 405 | 客户端 |
| 没登录 / token 失效 | 401 | 客户端（需重新登录） |
| 登录了但没权限 | 403 | 客户端（权限不足） |
| 业务规则不满足（不能收藏自己的） | 2xxx / 3xxx / 7xxx | 业务 |
| **真正的服务端故障** | 500 | 服务端 |

**这张表本身就是一份"排查指南"**：看到 4xx 先检查自己的请求，看到 5xx 才去查服务端。

# 第六部分：前端实现

## 6.1 收藏按钮：本地状态更新，不重新请求

```js
/**
 * 收藏 / 取消收藏。
 * 只改本地那一份数据、不发第二次请求 —— 因为收藏接口本身就返回了成功，
 * 再拉一次详情是多余的往返。
 */
async function toggleFavorite() {
  if (!userStore.isLogin) {
    ElMessage.warning('登录后才能收藏商品')
    router.push({ path: '/login', query: { redirect: route.fullPath } })
    return
  }

  favoriteLoading.value = true
  try {
    if (product.value.favorite) {
      await removeFavorite(product.value.id)
      product.value.favorite = false
      product.value.favoriteCount = Math.max(0, (product.value.favoriteCount || 1) - 1)
      ElMessage.success('已取消收藏')
    } else {
      await addFavorite(product.value.id)
      product.value.favorite = true
      product.value.favoriteCount = (product.value.favoriteCount || 0) + 1
      ElMessage.success('收藏成功')
    }
  } finally {
    favoriteLoading.value = false
  }
}
```

三个细节：

**① 未登录时给明确引导，而不是让按钮点了没反应。**

```js
router.push({ path: '/login', query: { redirect: route.fullPath } })
```

`redirect` 参数让用户登录后**回到当前这个商品页**，而不是跳到首页重新找。

**② 同步更新 `favoriteCount`，不用等后端返回。**

后端已经改了这个数，但前端这份 `product` 对象还是旧的。手动 `+1/-1` 让界面立刻正确，省掉一次请求。

`Math.max(0, ...)` 是前端侧的边界保护——和后端 SQL 里的 `GREATEST` 呼应，**两端都防一次。**

**③ `favoriteLoading` 防止连点。**

不加的话，用户快速点两下会发出两个请求，第二个可能返回"已经收藏过了"的错误提示——**用户明明操作成功了却看到报错。**

## 6.2 留言组件：独立出去

`Detail.vue` 本来就有 400 多行，留言功能再加进去会到 600 行以上。

**所以抽成了 `components/ProductComments.vue`。**

```vue
<!-- 留言咨询：独立组件，逻辑不混在详情页里 -->
<div ref="commentsRef">
  <ProductComments
    :product-id="product.id"
    :is-owner="!!product.owner"
    :commentable="product.status === 1 || product.status === 3"
  />
</div>
```

**接口设计得很窄**：三个 props，没有 emit。

| prop | 作用 |
| --- | --- |
| `productId` | 拉哪件商品的留言 |
| `isOwner` | 决定显示"留言输入框"还是"直接回复买家"的提示 |
| `commentable` | 商品状态允许不允许留言 |

**组件自己管自己的加载、提交、删除，对外零耦合。** 这是好组件的标准：**输入少、副作用少、能独立理解。**

## 6.4 ProductCard 加一个 actions 插槽

「我的收藏」页需要在每张卡片上加一个"取消收藏"按钮，但卡片是复用组件。

**用插槽让它可扩展：**

```vue
<!-- 调用方可以塞额外的操作按钮（如「我的收藏」页的取消收藏） -->
<div v-if="$slots.actions" class="actions">
  <slot name="actions" />
</div>
```

```vue
<ProductCard v-for="item in list" :key="item.id" :product="item">
  <template #actions>
    <el-button link type="danger" size="small" @click.stop="handleRemove(item)">
      取消收藏
    </el-button>
  </template>
</ProductCard>
```

**注意 `@click.stop`** —— 卡片本身有 `@click="goDetail"`，不阻止冒泡的话，点"取消收藏"会同时触发跳转详情页。

> **在可点击的容器里放按钮，一定要处理事件冒泡。**
> 这是前端最容易漏的交互细节之一。

`v-if="$slots.actions"` 保证不传插槽时不会渲染一个空的带边框的 div。

## 6.5 我的收藏：翻页边界

```js
await removeFavorite(item.id)
ElMessage.success('已取消收藏')
// 当前页只剩这一条时，删完要往前退一页，否则会停在空白页
if (list.value.length === 1 && query.current > 1) {
  query.current -= 1
}
await loadList()
```

**这是分页列表里"删除最后一条"的经典问题：**

```
第 2 页只有 1 条 → 删掉 → 重新请求第 2 页 → 返回空列表
```

用户看到"还没有收藏任何商品"，以为收藏全没了——**其实第 1 页还有 11 条。**

往前退一页就解决了。

> 这个细节在**每个"列表 + 删除"的功能里都存在**。后台的商品管理、
> 用户管理页也都有类似的分页删除操作，写的时候都该想一遍。

# 第七部分：安全清单与验收

## 7.1 本阶段的安全设计

| 攻击手法 | 后果 | 防护 | 代码位置 |
| --- | --- | --- | --- |
| 收藏自己的商品刷热度 | 制造"很抢手"假象 | `FAVORITE_SELF` 校验 | `FavoriteServiceImpl` |
| 并发双击收藏 | 重复记录 + 计数失真 | 唯一索引 + 捕获 `DuplicateKeyException` | `FavoriteServiceImpl` |
| 取消收藏时不带 userId | **删掉所有人的收藏** | 删除条件同时带 `userId` 和 `productId` | `FavoriteServiceImpl` |
| 计数被减成负数 | 页面显示"收藏 -1" | SQL `GREATEST(..., 0)` | `FavoriteServiceImpl` |
| 自问自答刷留言热度 | 商品看起来很受关注 | 发布者不能发一级留言 | `CommentServiceImpl` |
| **回复别的商品的留言** | 留言树错乱、回复消失 | 校验 `parentId` 与 `productId` 匹配 | `CommentServiceImpl` |
| 删除他人留言 | 破坏他人数据 | 三方权限校验（作者/发布者/管理员） | `CommentServiceImpl` |
| **回复回复导致第三层** | **留言保存成功但永远看不见** | 归并到同一条一级留言下 | `CommentServiceImpl` |
| 留言内容撑爆通知字段 | 留言功能整体失败 | `StrUtil.maxLength` 截断 | `CommentServiceImpl` |
| 参数格式错返回 500 | 误导排查方向 | 400 / 404 分类处理 | `GlobalExceptionHandler` |
| 用户 ID 靠前端传 | 操作他人收藏 | 全部从 token 取 | `FavoriteController` |
