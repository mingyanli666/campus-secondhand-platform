# 第一部分：为什么需要演示数据

功能做完了不等于"能演示"。这两件事之间差着三个问题：

| 问题 | 后果 |
| --- | --- |
| **页面是空的** | 首页只显示"暂无商品"，看不出这是个什么系统 |
| **只有一种状态** | 老师问"审核驳回长什么样"，你现场造数据 |
| **数据不真实** | "商品1 / 测试商品 / 价格 1 元"——一眼看出是凑数的 |

**演示数据不是"为了好看"，它是在回答一个问题：**
> **这个系统在真实使用中是什么样子？**

一条数据证明不了任何事。**要让每个页面都有内容、每种状态都能看到、每个数字都有意义**，才算把系统"讲清楚"。

## 1.1 覆盖矩阵 —— 演示数据真正的设计目标

与其想"我要造多少条"，不如先列一张**状态覆盖表**：

| 实体 | 需要覆盖的状态 | 为什么 |
| --- | --- | --- |
| 商品 | 在售 / 待审核 / 已售出 / 已下架 / 审核驳回 | 5 种状态都要能在页面上看到 |
| 订单 | 待确认 / 已确认 / 已完成 / 已取消 / 已关闭 | 5 种状态对应 5 组不同按钮 |
| 举报 | 待处理 / 已处理 / 已驳回 | 管理员一登录就得有活干 |
| 用户 | 正常 / 禁用 | 演示"禁用后无法登录" |
| 分类 | 全部启用 | （停用会在演示中现场操作） |

**这张表决定了数据怎么造**——不是"随便加 30 条商品"，而是"每一格都要有数据"。

# 第二部分：数据设计的六个决定

## 2.1 决定一：独立 SQL 脚本，不塞进 DataInitializer

**方案 A**：在 `DataInitializer` 里用 Java 代码插入演示数据

```java
// ❌ 不推荐
if (productMapper.selectCount(null) == 0) {
    for (int i = 0; i < 30; i++) { ... 插入商品 ... }
}
```

**方案 B**：独立的 `sql/demo-data.sql`（本项目采用）

```bash
mysql -uroot -p --default-character-set=utf8mb4 used_digital_platform < sql/demo-data.sql
```

**为什么选 B？**

| 维度 | Java 初始化 | SQL 脚本 |
| --- | --- | --- |
| **生产环境** | 每次启动都要判断"要不要插" | 不执行就不会有 |
| **修改数据** | 改代码 → 重启 → 等生效 | 改 SQL → 重跑，几秒 |
| **数据可读性** | 散在循环和随机数里 | 一眼看清每一行是什么 |
| **新人理解** | 要读代码才知道造了什么 | 打开文件就是一份数据清单 |
| **业务代码污染** | 演示逻辑混进启动流程 | 完全分离 |

**核心问题：演示数据是"开发/演示期的一次性配置"，不是"应用的业务逻辑"。** 把它放进启动流程，等于让生产环境永远背着一个它不需要的东西。

`DataInitializer` 保留的角色是"**创建必需账号**"（没有 admin 系统根本没法用），而不是"填充演示内容"。

## 2.2 决定二：id 从 100 开始，脚本可重复执行

```sql
-- 清理旧的演示数据（只删 id >= 100 的记录，不影响你自己创建的数据）
DELETE FROM `biz_report`        WHERE `product_id` >= 100;
DELETE FROM `biz_product`       WHERE `id` >= 100;
DELETE FROM `sys_user`          WHERE `id` >= 100;
```

**为什么把演示数据的 id 定在 100 以上？**

因为开发过程中你已经在数据库里造了一些真实数据（id 1~6 的商品、id 1~5 的用户）。如果演示数据从 id 7 开始，就和这些数据**混在一起，分不开了**——重跑脚本时无法安全地只删演示数据。

**id 分段带来的好处：**

| 好处 | 说明 |
| --- | --- |
| **可重复执行** | 先删 id ≥ 100 再插入，跑一百次结果都一样 |
| **不误伤** | 你手动创建的数据（id < 100）永远安全 |
| **可回滚** | 不想要演示数据了，删掉 id ≥ 100 就行 |

> **这是"给测试数据划分命名空间"的思路。** 生产环境的种子数据、测试数据、
> 演示数据都应该有各自的区间或标识，否则迟早会互相污染。

## 2.3 决定三：密码复用同一个 BCrypt 密文

```sql
(101, 'chenqi', '$2a$10$w/gYB1/D00MDDw0YLg.D6e6HQi/OTVeInb011TFXI7LuYKFKYJqdG', ...)
```

**这个密文是从哪来的？** 不是算出来的，是**直接抄 `admin` 账号在数据库里的那一条**——它本来就是 `123456` 的 BCrypt 密文。

**为什么可以复用？**

BCrypt 每次加密都会生成随机盐，所以同一密码每次的密文都不同。**但校验时只需要密文本身**——一个密文能对应一个明文，用几次都没关系。

| 做法 | 说明 |
| --- | --- |
| 每个用户生成不同的盐 | 更标准，但在 SQL 里做不到（需要 Java 代码） |
| **所有演示账号共用一个密文** | ✅ 简单、可读、能用 |

**代价**：所有演示账号的密码哈希完全相同，如果其中一个被破解（实际上 BCrypt 也破不了），其余账号同样暴露。

**但这是演示数据**——密码本来就是公开写在 README 里的 `123456`，谈不上"泄漏"。

> **这是一个"在演示场景下完全合理，在生产场景下不可接受"的决定。**
> 判断标准不是"哪种做法更标准"，而是"这个场景下最坏后果是什么"。

## 2.4 决定四：时间用相对时间，不用固定日期

```sql
create_time = DATE_SUB(NOW(), INTERVAL 12 DAY)
```

**为什么不用 `'2026-01-01 10:00:00'` 这种固定日期？**

因为前端有一个 `fromNow()` 的相对时间显示：

```js
if (diff < minute) return '刚刚'
if (diff < hour) return `${Math.floor(diff / minute)}分钟前`
if (diff < day) return `${Math.floor(diff / hour)}小时前`
if (diff < 7 * day) return `${Math.floor(diff / day)}天前`
return formatTime(value)
```

如果用固定日期，**三个月后再演示时，所有商品都会显示"3个月前发布"** ——用户会觉得这个平台早就没人用了。

用 `DATE_SUB(NOW(), INTERVAL n DAY)`，**无论什么时候运行脚本，数据都"看起来是最近发布的"**。

> **演示数据的"新鲜度"是可维护性的一部分。** 一份三个月后就会露馅的演示数据，
> 只解决了一半问题。

## 2.5 决定五：订单里的商品信息写死，不用子查询

```sql
INSERT INTO `biz_order`
    (`order_no`, `product_id`, `product_title`, `product_cover`, ...)
VALUES
('OD202609100930001001', 102, '小米13 12+256 远山蓝', '/uploads/demo/demo-02.png', ...);
```

**商品标题、封面、价格在订单表里是冗余的**——完全可以 `JOIN biz_product` 拿到。

**为什么还是写死？**

因为这不是"冗余"，**这是订单快照**（见 [07-订单模块](07-订单模块实现讲解.md) 第二部分）：

> 订单存的是**下单那一刻**的商品信息。商品后来被改了标题、换了价格，订单里显示的必须还是"当时约定的内容"。

**演示数据也一样。** 如果演示订单里用 JOIN 拿标题，那么当我修改演示商品的标题时，历史订单会跟着变——**这个行为本身就是错的**，演示数据也不该示范错误的行为。

> **演示数据要"演"出正确的业务语义，而不只是把表填满。**

## 2.6 决定六：图片在本地生成，不用网络图

```powershell
# 生成 24 张 480x360 的渐变占位图
$bmp = New-Object System.Drawing.Bitmap 480, 360
$brush = New-Object System.Drawing.Drawing2D.LinearGradientBrush(...)
$g.FillRectangle($brush, 0, 0, 480, 360)
$g.DrawString('IPHONE 13', $fontBig, $white, ...)
```

**为什么不用网图？**

| 做法 | 问题 |
| --- | --- |
| 引用外部图片链接 | 断网就全裂；图片来源有版权风险；答辩电脑可能连不上外网 |
| 找一堆真实商品图 | 版权问题；而且"别人的商品图"容易引起误解 |
| 用纯色块 | 视觉上太假，一眼看出是凑数 |
| **本地生成带文字的渐变图** | ✅ 可控、离线可用、无版权风险、视觉上像正经占位图 |

**生成图放在 `backend/uploads/demo/`** ——和真实上传的图片在同一个目录下，走同一套静态资源映射（`/uploads/**`）。

**这样做的好处**：演示数据和真实数据的访问路径完全一致，不会出现"演示图能显示、真图不能显示"的诡异情况。

# 第三部分：一次真实的演示效果修正

自检时发现一个问题：

```
=== keyword search ===
  'MacBook' -> 0        ← 明明有一件 MacBook Air，为什么搜不到？
```

**排查：**

```sql
select id, title, status from biz_product where title like '%MacBook%';
-- 105 | MacBook Air M2 8+256 午夜色 | 3   ← 已售出
```

**原因找到了。** 我给商品 105 挂了一笔"已完成"的订单，于是把它设成了**已售出**。而公开列表只显示在售商品，所以搜不到。

**逻辑上完全正确** —— 已售出的商品不该出现在搜索结果里。**但演示效果很差**：老师搜一个常见关键词，什么都搜不到，会怀疑搜索功能坏了。

**修正：把这笔完成订单挪到另一件已经售出的商品（小米平板 6 Pro）上，让 MacBook 回到在售。**

```
修正前：'MacBook' -> 0
修正后：'MacBook' -> 1  ✅
```

## 3.1 这个修正的启示

**"数据正确"和"演示效果好"是两个维度。**

| 维度 | 判断标准 |
| --- | --- |
| 数据正确 | 状态机、引用关系、业务规则都成立 |
| 演示效果 | 每个页面上都有内容，每个功能都能被触发 |

**用一件"已售出"的商品挂订单，数据上完全正确**，但它让一个常用搜索词变成了空结果。

> **设计演示数据时，要站在"第一次打开这个网站的人"的角度想：**
> 他会搜什么？他会点哪里？他期望看到什么？
> **如果某个常用操作会得到空结果，那就是演示设计的问题，不是功能的问题。**

## 3.2 顺带发现的小问题：通知全是测试噪音

清理数据时发现 `zhangsan` 有 24 条未读通知，全是自动化测试产生的（"有人咨询了你发布的..."重复出现）。

**通知是业务动作的副作用，没有独立的主键区间**，所以不能像商品那样"删 id ≥ 100"来区分。

**做法**：整体清空，然后按演示数据的状态**重建一套配套通知**：

```sql
DELETE FROM `sys_notification`;

INSERT INTO `sys_notification` (...) VALUES
(101, 1, '商品审核通过', '你发布的「iPhone 13...」已通过审核...', 101, 1, ...),
(102, 2, '你有一笔新的订单', '有买家想买你的「索尼 A6400...」...', ..., 0, ...),
...
```

**13 条通知覆盖四种类型**（审核 1 / 订单 2 / 留言 3 / 系统 4），让铃铛有内容、点击能跳转、未读数正确。

> **"没有主键区间"的数据，就用"整体重置"的策略。**
> 关键是让演示状态可复现——每次跑脚本，结果都一样。

# 第四部分：系统自检的 38 项清单

功能做完了，怎么知道它真的能用？

**方法：把所有对外接口按模块过一遍，逐项断言。**

## 4.1 自检脚本的结构

```powershell
function Check($name, $ok, $detail) {
  if ($ok) {
    $script:pass++
    Write-Output ("[PASS] " + $name + ...)
  } else {
    $script:fail++
    Write-Output ("[FAIL] " + $name + "  -> " + $detail)
  }
}

function GetJson($url, $token) {
  if ($token) { return (curl.exe -s "$url" -H "Authorization: Bearer $token" | ConvertFrom-Json) }
  return (curl.exe -s "$url" | ConvertFrom-Json)
}
```

**为什么用脚本而不是手动点？**

| 手动点 | 脚本 |
| --- | --- |
| 30 个页面点一遍要半小时 | 几秒跑完 |
| 容易漏 | 每次跑的都是同一套 |
| 改完代码要重来 | 一条命令重跑 |
| 说不清"测了什么" | 输出就是一份测试报告 |

**这份自检清单稍加整理，可以直接作为论文"系统测试"章节的内容。**

## 4.2 五个分组的设计理由

**A. 公共接口（11 项）** —— 游客能用的功能
- 因为这是**用户第一眼看到的东西**。首页打不开，后面全白搭。

**B. 认证（4 项）** —— 登录的各种情况
- 不只测"登录成功"，还要测**错误密码、无 token、篡改 token**。
- **正常路径谁都会测，异常路径才是质量的体现。**

**C. 用户功能（8 项）** —— 登录后的个人中心
- 覆盖我的发布/收藏/订单/举报/通知，**每个入口都要有数据**。

**D. 管理后台（8 项）** —— 管理员能力
- 除了列表，专门测了**普通用户访问管理接口返回 403**。

**E. 边界与异常（7 项）** —— 最容易出问题的地方
- 分页攻击、非法参数、不存在的资源、越权操作。

## 4.3 几条断言的设计思路

### 不只是看 `code == 200`，还要看数据

```powershell
# ❌ 弱断言：只确认接口没报错
Check 'product page' ($list.code -eq 200)

# ✅ 强断言：确认返回了有意义的数据
Check 'product page' ($list.code -eq 200 -and $list.data.total -gt 0) "total=$($list.data.total)"
```

**只测 `code=200` 会漏掉"接口通了但返回空列表"这类问题**——而这恰恰是最常见的演示事故。

### 排序要逐个比较，不能只看第一条

```powershell
$ascOk = $true
for ($i = 1; $i -lt $sorted.data.records.Count; $i++) {
  if ($sorted.data.records[$i].price -lt $sorted.data.records[$i-1].price) { $ascOk = $false }
}
Check 'sort by price asc' $ascOk "first=$($sorted.data.records[0].price)"
```

**只看第一条是不是最小值，不能证明整个列表有序。** 必须两两比较。

### 筛选要验证边界，不能只看总数

```powershell
$priceOk = $true
foreach ($r in $price.data.records) {
  if ($r.price -lt 1000 -or $r.price -gt 3000) { $priceOk = $false }
}
Check 'price range filter' ($priceOk -and $price.data.total -gt 0) "total=$($price.data.total)"
```

**"返回了 9 条"不代表这 9 条都在 1000-3000 区间内。** 要检查每一条。

### 中文搜索要用 URL 编码

```powershell
# PowerShell 脚本文件里的中文会被按 GBK 解码，直接用 '索尼' 会变成乱码
$kw2 = GetJson "$base/api/product/page?keyword=%E7%B4%A2%E5%B0%BC"   # 索尼
Check 'keyword (chinese) 索尼' ($kw2.data.total -ge 2) "hits=$($kw2.data.total)"
```

**这是脚本层面的问题，不是系统的问题**——但如果不处理，就会误判成"中文搜索不支持"。

# 第五部分：工程坑 —— PowerShell 与中文路径

**这一节记录一个在本次开发中踩了三次的坑。它的价值在于"知道它存在"，而不是"学会怎么绕"。**

## 5.1 现象

写入 `F:\毕业设计\...` 的脚本执行后，文件出现在了 `F:\姣曚笟璁捐\...` 这个诡异的目录里。

## 5.2 原因

**Windows PowerShell 5.1 读取 `.ps1` 文件时，如果没有 BOM，会按系统 ANSI 代码页（简体中文环境是 GBK）解码。**

而我的脚本文件是 **UTF-8 无 BOM** 保存的：

```
"毕业设计" 的 UTF-8 字节：   E6 AF 95 E4 B8 9A E8 AE BE E8 AE A1
按 GBK 解码后：              姣     曚     笟     璁           捐
```

**"毕业设计" 被当成了 "姣曚笟璁捐"。** 于是脚本里的路径全部指向了这个不存在的乱码目录。

## 5.3 三次踩坑的过程

| 第几次 | 场景 | 表现 |
| --- | --- | --- |
| 第 1 次 | 测试脚本里有中文输出 | 中文变成乱码，甚至导致语法解析失败 |
| 第 2 次 | 脚本里写中文路径 | 文件写到了乱码目录 |
| 第 3 次 | 生成演示图片 | 24 张图全写进了乱码目录 |

**这就是"已知的坑不会自动扩散到该修的地方"** ——和 [04-商品审核](04-管理后台与商品审核实现讲解.md) 里 `updateById` 的坑是同一个道理。

## 5.4 三种解法

| 解法 | 做法 | 适用场景 |
| --- | --- | --- |
| **① 脚本里不放中文** | 输出标签用英文，数据放独立的 UTF-8 JSON/文件 | ✅ 最可靠，本项目最终采用 |
| **② 用 BOM 保存** | `.ps1` 存成 UTF-8 with BOM | 需要脚本里有中文时 |
| **③ 用目录对象代替字符串** | 遍历 `Get-ChildItem` 拿 `DirectoryInfo.FullName`，不做字符串拼接 | 需要操作含中文的路径时 |
| ④ 用内联命令 | 通过 `powershell -Command "..."` 直接执行 | 短命令，且工具层面对中文处理正确 |

**最终采用的组合是 ① + ③**：

```powershell
# 不写死中文路径，而是遍历目录找目标
foreach ($d in (Get-ChildItem 'F:\' -Directory)) {
  $probe = Join-Path $d.FullName 'used-digital-platform\backend\uploads\demo'
  if (Test-Path $probe) { $found = $probe }
}
```

**`$d.FullName` 是文件系统返回的原始字符串，不经过编码转换**，所以路径是准确的。

## 5.5 更根本的建议

> **项目路径不要用中文。**
>
> 这次是 PowerShell，下次可能是某个构建工具、某个 CI 脚本、某个 Docker 挂载路径。
> **"路径只含 ASCII" 是一条几乎零成本、却能规避一整类问题的工程约定。**

如果当初把项目放在 `F:\graduation\used-digital-platform`，这三次坑一次都不会遇到。

## 6.3 三个"准备好的答案"

老师大概率会问这几个问题，提前想好：

| 问题 | 回答要点 |
| --- | --- |
| **"并发怎么办？"** | 分页有上限防攻击；计数用 SQL 原子自增；靠唯一索引防重复收藏。下单的并发窗口我评估过：概率低、影响小（卖家挑一个确认），加锁不值 |
| **"为什么不用 Redis / 消息队列？"** | 当前量级不需要；JWT 是无状态的，通知是同步写库。真要扩，拦截器里的用户状态查询是最该先加缓存的地方 |
| **"这个功能为什么这么设计？"** | 每个决策在 docs 里都有记录——比如"为什么订单只让买家确认完成""为什么举报分已处理和已驳回" |
