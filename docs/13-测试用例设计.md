# 第一部分：测试策略

## 1.1 四层结构

```
        ┌─────────────────────────────────────┐
   ④    │  容器冒烟：docker compose up --wait  │  4 项
        │  真的把服务拉起来，打接口验证         │
        ├─────────────────────────────────────┤
   ③    │  接口层：MockMvc / PowerShell 自检   │  38 项
        │  权限、参数校验、错误码、边界         │
        ├─────────────────────────────────────┤
   ②    │  业务层单元测试（JUnit 5 + Mockito） │  58 个
        │  状态机、权限、业务规则               │
        ├─────────────────────────────────────┤
   ①    │  前端单元测试（Vitest）              │  39 个
        │  请求层、状态存储、格式化             │
        └─────────────────────────────────────┘
```

**为什么是这个形状？**

- **越往下越快越便宜**：单元测试毫秒级，容器冒烟要几分钟
- **越往上越接近真实**：单元测试证明"逻辑对"，冒烟证明"部署起来能用"
- **层与层之间不是替代关系**：58 个单元测试全绿也可能构建失败
  （本项目就踩过：Prettier 拆分内联事件处理器导致生产构建挂掉，
  ESLint、Prettier、单测全过，只有真的 build 一次才发现）

## 1.2 各层测什么

| 层 | 测什么 | 不测什么 |
| --- | --- | --- |
| 前端单元 | 请求拦截器的剥壳/401/竞态取消、Pinia 持久化、格式化函数 | 页面渲染细节 |
| 业务单元 | 状态机、权限矩阵、业务规则、缓存一致性 | SQL 是否正确、事务是否生效 |
| 接口层 | 权限拦截、参数校验、错误码、分页边界 | 业务细节（已被下层覆盖） |
| 容器冒烟 | 编排、健康检查、nginx 反代、前后端联通 | 具体业务规则 |

**这个划分本身就是一个结论：单元测试用 Mockito 隔离了数据库，所以它测不到 SQL。**
这一点在 [第七部分](#第七部分这套用例的不足) 会再说明。

# 第二部分：五种用例设计方法（含本项目实例）

面试里问"你怎么设计用例"，能说出方法的名字只是及格；
**能说出"在这个场景为什么选这个方法"才是关键**。下面每条都配了项目里的真实例子。

## 2.1 等价类划分

> **适用场景**：输入域很大、不可能穷举时，把输入分成若干"处理方式相同"的类，
> 每类取一个代表。

### 实例：商品价格

价格是 `BigDecimal`，理论上有无限种取值。但代码对它们的处理只有三类：

| 等价类 | 取值 | 预期 | 有效/无效 |
| --- | --- | --- | --- |
| 正常区间 | `2999.00` | 通过 | 有效 |
| 下边界之上 | `0.01` | 通过 | 有效（边界值） |
| **等于 0** | `0` | 拒绝：价格必须大于 0 | 无效 |
| **负数** | `-1` | 拒绝 | 无效 |
| 超大值 | `10000000` | 拒绝：价格超出合理范围 | 无效 |
| 非数字 | `"abc"` | 拒绝：类型不匹配 | 无效 |

**只测 6 个值就覆盖了全部处理分支**，而不是测 100 个价格。

### 实例：订单状态

订单有 5 个状态，但"能不能取消"这个问题只关心三类：

| 等价类 | 状态 | 预期 |
| --- | --- | --- |
| 未开始履约 | 待确认(0) | 可取消 |
| 履约中 | 已确认(1) | 不可取消，需双方协商 |
| 已终结 | 已完成(2) / 已取消(3) / 已关闭(4) | 不可取消 |

## 2.2 边界值分析

> **适用场景**：有明确数值边界的地方。经验上 **边界上下的错误率最高**——
> 写 `>` 还是 `>=` 是最常见的 off-by-one。

### 实例：商品标题长度（2-100）

```
长度 1    → 拒绝（低于下限）
长度 2    → 通过（下边界）
长度 3    → 通过（下边界内）
长度 99   → 通过（上边界内）
长度 100  → 通过（上边界）
长度 101  → 拒绝（超过上限）
```

**6 个用例，其中 2 个是边界本身**。只测"正常标题"和"超长标题"会漏掉
`min=2` 写成 `min=3` 这种错误。

### 实例：分页 size

```java
// PageQuery.toPage() 里强制上限
page.setSize(Math.min(Math.max(size, 1), 100));
```

| 输入 | 预期 | 依据 |
| --- | --- | --- |
| `size=0` | 归到 1 | 下限 |
| `size=1` | 1 | 下边界 |
| `size=100` | 100 | 上边界 |
| `size=101` | **限制为 100** | 超上限 |
| `size=99999` | **限制为 100** | 防止一次拉全表 |

**这条不是"边界值练习"，是安全防护**：不限制的话，前端传 `size=100000`
就能把整张表拉进 JVM，一个请求打挂服务。

### 实例：图片数量上限 9 张

`@Size(max = 9, message = "最多上传 9 张图片")`

| 张数 | 预期 |
| --- | --- |
| 0 | 通过（允许无图，封面为空） |
| 1 | 通过 |
| 9 | 通过（边界） |
| 10 | 拒绝 |

**0 张也要测**——因为发布时 `coverImage` 的赋值是
`CollUtil.isEmpty(images) ? null : images.get(0)`，空列表如果不处理会 NPE。

## 2.3 状态迁移法

> **适用场景**：对象有明确的状态机。要覆盖的是**状态 × 事件**的组合，
> 而不是每条路径。

### 实例：商品状态机

```
                ┌──────────┐
     发布 ────▶ │ 待审核 0 │
                └────┬─────┘
              通过 │  │ 驳回
            ┌──────┘  └──────┐
            ▼                ▼
      ┌──────────┐     ┌──────────┐
      │ 在售 1   │     │ 驳回 4   │──┐
      └────┬─────┘     └──────────┘  │重新提交
     下架  │ 售出                  ▲ │
           ▼                       │ │
      ┌──────────┐   重新提交      │ │
      │ 下架 2   │─────────────────┘ │
      └──────────┘                   │
           │                          │
           ▼                          │
      ┌──────────┐                    │
      │ 已售出 3 │  终态（不可流转）  │
      └──────────┘                    │
```

**状态迁移表**：

| 当前状态 | 事件 | 预期 |
| --- | --- | --- |
| 待审核 | 审核通过 | → 在售 |
| 待审核 | 审核驳回（填原因） | → 驳回 |
| 待审核 | 审核驳回（不填原因） | ✗ 参数错误 |
| 待审核 | 下架 | ✗ 只有在售才能下架 |
| 待审核 | 重新提交 | ✗ 不允许 |
| 在售 | 编辑 | → **待审核**（重新审核） |
| 在售 | 下架 | → 下架 |
| 在售 | 审核 | ✗ 状态不允许 |
| 在售 | 删除 | ✓ |
| 下架 | 重新提交 | → 待审核，**并清空驳回原因** |
| 驳回 | 重新提交 | → 待审核，**并清空驳回原因** |
| 已售出 | 编辑 | ✗ 已售出不能编辑 |
| 已售出 | 删除 | ✗ |
| 已售出 | 审核 | ✗ |
| 已售出 | 下架 | ✗ |

**这张表里最有价值的两行**：

1. **「在售 → 编辑 → 待审核」**：防止"先发合格内容过审，再改成违规内容"。
   如果没有这条规则，审核就形同虚设。
2. **「下架/驳回 → 重新提交 → 清空驳回原因」**：这是踩过坑才加的
   （见 [14-缺陷报告](14-缺陷报告.md) 的 DEF-002）。

### 实例：订单状态机（5 状态 × 双角色）

比商品复杂，因为**同一个事件对不同角色结果不同**：

| 当前 | 事件 | 买家 | 卖家 | 管理员 |
| --- | --- | --- | --- | --- |
| 待确认 | 确认 | ✗ | ✓ → 已确认 | ✗ |
| 待确认 | 取消 | ✓ → 已取消 | ✓ → 已取消 | ✗ |
| 已确认 | 完成 | ✓ → 已完成 | ✗ | ✗ |
| 已确认 | 取消 | ✗ | ✗ | ✗（只能协商） |
| 已完成 | 任意 | ✗ 终态 | ✗ | ✗ |

**"已确认 → 完成"只能买家点**，因为"东西到手了"只有买家知道。
让卖家能单方面结束，等于给了他单方面宣布交易完成的权力。

## 2.4 场景法

> **适用场景**：跨模块的端到端流程。把用户的操作串成一条路径，
> 验证模块之间的衔接。

### 实例：完整交易闭环

| 步骤 | 角色 | 操作 | 预期 |
| --- | --- | --- | --- |
| 1 | 卖家 | 发布商品 | 状态=待审核，不出现在公开列表 |
| 2 | 卖家 | 直接搜索自己的商品 | **搜不到**（未过审不该可见） |
| 3 | 管理员 | 审核通过 | 状态=在售，卖家收到通知 |
| 4 | 卖家 | 再搜索 | 搜得到 |
| 5 | 买家 | 收藏 + 留言 | 收藏数 +1，卖家收到留言通知 |
| 6 | 买家 | 下单 | 订单=待确认，卖家收到订单通知 |
| 7 | 买家 | **再下一单** | ✗ 该商品已有进行中订单 |
| 8 | 卖家 | 确认接单 | 订单=已确认 |
| 9 | 卖家 | 点"确认完成" | ✗ 无此按钮（权限矩阵） |
| 10 | 买家 | 确认完成 | 订单=已完成，**商品自动变为已售出** |
| 11 | 其他人 | 搜索该商品 | 搜不到（已售出不在公开列表） |

**第 2 步和第 7 步是这条场景里最有价值的**——它们验证的是"状态对可见性/可用性的影响"，
单看任何单个接口都发现不了。

### 实例：举报处置联动

| 步骤 | 角色 | 操作 | 预期 |
| --- | --- | --- | --- |
| 1 | 买家 | 举报商品 | 举报状态=待处理 |
| 2 | 管理员 | 处理（核实成立 + 同时下架） | 商品变下架 + 订单被关闭 + 卖家收到通知 |
| 3 | 卖家 | 尝试重新上架 | 需重新提交审核 |
| 4 | 管理员 | 处理一个**已售出**商品的举报 | 记录照常写，跳过下架步骤（不该报错） |

**第 4 步来自一次真实 bug**（DEF-003）：复用了 `forceOffShelf`，
而它要求"只有在售商品能下架"，导致商品已售出时整个举报处理失败。

## 2.5 错误推测法

> **适用场景**：靠经验猜"哪里容易出错"。这类用例往往最有效——
> 它们测的不是需求，而是**开发者可能没想到的地方**。

### 本项目的错误推测清单

| 猜测 | 用例 | 实际发现 |
| --- | --- | --- |
| token 被篡改会怎样 | 改一个字符后请求 | 验签失败 → 401 ✓ |
| **禁用用户后旧 token 还能用吗** | 管理员禁用 → 用旧 token 请求 | **能！** → 修复（DEF-001） |
| 用别人的商品 ID 能操作吗 | 传别人的 productId 下架 | 被 `requireOwner` 拦住 ✓ |
| 收藏自己发布的商品 | 点收藏 | 拒绝，理由合理 ✓ |
| 买自己的商品 | 下单 | 拒绝 ✓ |
| 并发点两次收藏 | 快速双击 | 唯一索引兜底，第二次翻译成友好提示 ✓ |
| 不存在的商品 ID 反复请求 | 循环请求 999999 | 空值哨兵兜住，不打库 ✓ |
| 详情页能注入 ORDER BY 吗 | `sort=id;drop` | 白名单外 → 回落到默认排序 ✓ |
| 前面有空格的关键词 | 搜 `" iPhone"` | trim 后正常匹配 ✓ |
| 管理员能替用户完成订单吗 | admin 调用 finish | ✗ 只有买家能 ✓ |

**注意第一条**：那条用例是**错误推测出来的**，而它恰好发现了本项目最严重的安全缺陷。
这不是运气——"JWT 是无状态的"这个特性本身就暗示了"签发后的状态变化服务器不知道"。

## 2.6 判定表（补充）

> 商品详情页"能不能看"取决于两个条件：**商品状态** × **访问者身份**。
> 二维组合最适合用判定表。

| 商品状态 | 游客 | 其他用户 | 发布者本人 | 管理员 |
| --- | --- | --- | --- | --- |
| 在售 | ✓ | ✓ | ✓ | ✓ |
| 待审核 | ✗ 404 | ✗ 404 | ✓ | ✓ |
| 已下架 | ✗ 404 | ✗ 404 | ✓ | ✓ |
| 驳回 | ✗ 404 | ✗ 404 | ✓ | ✓ |
| 已售出 | ✗ 404 | ✗ 404 | ✓ | ✓ |

**注意"拒绝"用的是 404「商品不存在」而不是 403「无权限」**——
用 403 等于告诉探测者"这个 ID 确实存在，只是你看不了"，可以拿来枚举商品。

# 第三部分：用例编号与优先级

## 3.1 编号规则

```
TC-<模块>-<序号>

TC-PROD-001     商品
TC-ORDER-003    订单
TC-AUTH-002     认证
TC-ADMIN-005    管理端
TC-CACHE-001    缓存
```

**模块化编号的价值**：出问题时能立刻知道该找谁、该看哪块代码；
用例和代码模块一一对应，改代码时能反查受影响的用例。

## 3.2 优先级

| 级别 | 含义 | 举例 |
| --- | --- | --- |
| **P0** | 主流程中断 / 安全漏洞 | 登录失败、越权、数据错乱 |
| **P1** | 主流程可用的前提 | 状态机规则、权限矩阵 |
| **P2** | 边界与异常 | 参数校验、空状态 |
| **P3** | 体验与提示 | 错误文案、空页面提示 |

**回归时先跑 P0/P1**。时间不够就只跑这两级——这也是自动化该优先覆盖的部分。

## 4.5 缓存 TC-CACHE

| 编号 | 用例 | 前置 | 步骤 | 预期 | 设计方法 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- |
| TC-CACHE-001 | 缓存命中 | 已请求过一次 | 再请求详情 | 秒回（8.79ms / 38.08ms） | 等价类 | P1 |
| TC-CACHE-002 | **改库后仍返回旧值** | 缓存已建立 | 直接改数据库 | 接口返回**旧值**（证明命中缓存） | 错误推测 | P1 |
| TC-CACHE-003 | **写操作后缓存失效** | 同上 | 改库 + 调改价接口 | 返回**新值**（证明失效生效） | 错误推测 | P1 |
| TC-CACHE-004 | 空值哨兵 | — | 请求不存在的 ID 两次 | 第二次不再打库 | 错误推测 | P2 |
| TC-CACHE-005 | TTL 有抖动 | — | 连续创建多个缓存 | TTL 在 30~35 分钟之间随机 | 边界值 | P2 |
| TC-CACHE-006 | **Redis 挂掉降级** | 停 Redis | 请求详情 | 正常返回（查库），浏览量不丢 | 错误推测 | **P0** |

> **TC-CACHE-002/003 是用"绕过应用直接改数据库"来验证的**：
> 数据库改了而接口还返回旧值 → 证明走了缓存；
> 调一次写接口后再查 → 变成新值 → 证明失效生效。
> **这比看日志可靠得多。**

# 第七部分：这套用例的不足

**把不足写出来，比假装没有更有用。** 这一节也是面试时最容易加分的地方。

| 不足 | 具体表现 | 补法 |
| --- | --- | --- |
| **没有真正的集成测试** | 单元测试全用 Mockito 隔离了数据库，**SQL 写错了测不出来**（`ProductMapper.xml` 的动态 SQL 一行都没被覆盖） | 加 `@SpringBootTest` + Testcontainers，专门测 Mapper |
| **Controller 层没测** | 参数绑定、`@Valid` 校验、全局异常处理的映射都没覆盖 | `@WebMvcTest` 切片测试 |
| **没有性能测试** | Redis 那组数据是**串行请求**的响应时间，不是并发下的 TPS | JMeter 压测，出 TPS / P95 / 错误率曲线 |
| **没有端到端测试** | "登录 → 发布 → 审核 → 下单"整条链路靠手工+脚本 | Playwright / Cypress |
| **覆盖率不高** | 总体 36%，`config` 和部分 Service 是 0 | 按模块补，优先业务类 |
| **没有缺陷管理流程** | 缺陷是文档形式的，没走 Jira/禅道 | 单人项目没必要，但要知道真实团队怎么做 |

**面试时可以这样说**：

> "我的单元测试用 Mockito 隔离了数据库，好处是跑得快（全套 3 秒），
> 代价是**覆盖不到 SQL 层** —— `ProductMapper.xml` 里那段动态 SQL 一行都没被测到。
> 所以我另外用 38 项接口自检 + 容器冒烟来补这一段。
> 如果继续做，我会先用 Testcontainers 把 Mapper 层补上，
> 再用 JMeter 出一份并发压测数据 —— 现在那组 Redis 性能数据是串行的，
> 严格说不算压测。"
