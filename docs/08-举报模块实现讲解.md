# 第二部分：为什么举报要分类

```java
/**
 * 举报类型。
 * <p>
 * 为什么要把举报分类，而不是只让用户写一段文字？
 * <p>
 * 因为**分类决定了处理的优先级和方式**：
 * 违禁物品要立刻下架，价格欺诈要先核对价格，虚假信息要对比描述和图片。
 * 一堆没有分类的文字描述，管理员只能一条条读；有了分类就能按类型批量判断。
 */
public enum ReportType {
    FAKE(1, "虚假信息"),
    ILLEGAL(2, "违禁物品"),
    PRICE_FRAUD(3, "价格欺诈"),
    OTHER(4, "其他");
}
```

**这四类不是随便列的，它们对应四种不同的处理动作：**

| 类型 | 管理员要做什么 | 紧急程度 |
| --- | --- | --- |
| 虚假信息 | 对比图片和描述、看是否有盗图 | 中 |
| **违禁物品** | 直接下架，可能还要上报 | **高** |
| 价格欺诈 | 查同款市场价，判断是否离谱 | 中 |
| 其他 | 人工判断 | 低 |

**如果只有一个"举报理由"文本框，管理员就无法快速判断该先处理哪一类。** 有了分类，列表可以按类型筛选，高风险的能优先处理。

### 四种类型在 UI 上的呈现

```js
const REPORT_TYPES = [
  { value: 1, label: '虚假信息' },
  { value: 2, label: '违禁物品' },
  { value: 3, label: '价格欺诈' },
  { value: 4, label: '其他' }
]
```

```js
function typeTag(type) {
  return { 1: 'warning', 2: 'danger', 3: 'primary', 4: 'info' }[type] || 'info'
}
```

**违禁物品用红色（danger）**，因为它是唯一可能涉及法律风险的类别。**用颜色表达优先级**，管理员扫一眼列表就知道哪条要先看。

## 2.1 为什么"已处理"和"已驳回"必须分开

```java
/**
 * 「已处理」和「已驳回」要分开：它们对举报人的含义完全不同 ——
 * 前者是"你说得对，我们已经处置了"，后者是"我们核实过，这个商品没问题"。
 * 合并成一个"已结束"会让举报人觉得自己的反馈被无视了。
 */
public enum ReportStatus {
    PENDING(0, "待处理"),
    HANDLED(1, "已处理"),
    REJECTED(2, "已驳回");
}
```

**这是"要给用户反馈"的产品设计，而不是技术设计。**

如果只有一个"已结束"，举报人看到的状态是：

> 你的举报：已结束

他无法判断是"平台认同我"还是"平台否决我"。**两种情况都叫"已结束"，但一种会让他觉得被支持，一种会让他觉得白费力气。**

实测两种结果的真实文案：

```
[你的举报已处理] 你举报的「联想拯救者 R9000P 游戏本」经核实存在违规，商品已被下架。
                处理结论：经核实商品图片系盗用他人实拍图，已下架处理。

[你的举报未通过] 你举报的「机械革命极光pro」经核实未发现违规。
                处理结论：经核实该商品价格属于正常市场区间，未发现价格欺诈。
```

**两条通知的语气和内容都不同，但都给了明确的结论。** 举报人知道发生了什么，也知道为什么。

> **状态机不只是技术的，它也是产品语言的一部分。**
> 每多一个状态，就多一种"平台想对用户说的话"。

# 第三部分：提交举报 —— 三道校验

```java
@Override
@Transactional(rollbackFor = Exception.class)
public Long create(Long userId, ReportCreateDTO dto) {
    Product product = productMapper.selectById(dto.getProductId());
    if (product == null) {
        throw new BusinessException(ResultCode.PRODUCT_NOT_FOUND);
    }

    // 1. 不能举报自己的商品
    if (product.getUserId().equals(userId)) {
        throw new BusinessException(ResultCode.CANNOT_REPORT_SELF);
    }

    // 2. 同一用户对同一商品只允许一条"待处理"的举报
    Long pending = reportMapper.selectCount(Wrappers.<Report>lambdaQuery()
            .eq(Report::getProductId, product.getId())
            .eq(Report::getUserId, userId)
            .eq(Report::getStatus, ReportStatus.PENDING.getCode()));
    if (pending > 0) {
        throw new BusinessException(ResultCode.ALREADY_REPORTED);
    }

    Report report = new Report();
    ...
}
```

## 3.1 第一道：不能举报自己的商品

```java
// 不能举报自己的商品。
// 否则卖家可以用自己的账号给自己的商品刷举报，或者反过来 ——
// 拿举报当工具去干扰别人的商品。这两种都不该允许。
if (product.getUserId().equals(userId)) {
    throw new BusinessException(ResultCode.CANNOT_REPORT_SELF);
}
```

**这个校验看似多余，其实拦住了两种滥用：**

| 滥用方式 | 后果 |
| --- | --- |
| 自己举报自己，然后自己"承认违规" | 制造"平台已处理"的假象，或者刷信誉 |
| 反过来 —— 有人用举报骚扰别人的商品 | 这条拦不住，但下面的规则能限制 |

**这是本项目"不能操作自己的东西"系列里的第四条：**

| 位置 | 规则 |
| --- | --- |
| 收藏 | 不能收藏自己的商品 |
| 留言 | 不能给自己商品发一级留言 |
| 订单 | 不能买自己的商品 |
| **举报** | **不能举报自己的商品** |

> **同一个模式在四个模块里复现，说明它是这类平台的基本规则**：
> **凡是"可以让数字变好看"或"可以攻击别人"的操作，都要挡住"自己对自己"的路径。**

## 3.2 第二道：重复举报要分情况

```java
// 同一个用户对同一个商品只允许有一条"待处理"的举报。
// 注意加了 status 条件：如果上一次举报已经被驳回了，
// 用户发现了新的证据，应该允许他再举报一次。
Long pending = reportMapper.selectCount(Wrappers.<Report>lambdaQuery()
        .eq(Report::getProductId, product.getId())
        .eq(Report::getUserId, userId)
        .eq(Report::getStatus, ReportStatus.PENDING.getCode()));
```

**注意那个 `status = PENDING` 条件。** 它决定了两种截然不同的行为：

| 场景 | 不加 status 条件 | 加了 status 条件（本项目） |
| --- | --- | --- |
| 举报正在处理中 | 拦住 ✅ | 拦住 ✅ |
| 举报被驳回后，用户又发现新证据 | **还是拦住 ❌** | **允许再次举报 ✅** |

**"已经举报过就不能再举报"听起来合理，但会堵死合法的跟进。** 用户第一次举报时证据不足被驳回，后来拍到了确凿的照片 —— 他却永远不能再举报这个商品了。

**状态条件让规则变精确**：**拦的是"重复提交同一件事"，不是"这个人再也不能举报这个商品"。**

实测：

```
=== R4. lisi reports product 2 ===        report id = 1
=== R5. duplicate report while pending === {"code":8003,"message":"你已经举报过该商品，平台正在处理中"}
=== R13. lisi reports product 4 (after previous one handled) ===  report id = 2   ← 允许
```

## 3.3 第三道：参数校验

```java
@NotBlank(message = "请说明举报理由")
@Size(min = 5, max = 255, message = "举报理由为 5-255 个字符")
private String reason;
```

**`min = 5` 是为了拦住"举报""假的""1"这类无意义输入。**

举报是要占用管理员时间的，**一个字的举报等于让管理员去猜你说什么。** 要求 5 个字，虽然挡不住故意捣乱，但至少能让敷衍的成本高一点。

实测：

```
=== R3. reason too short === {"code":400,"message":"举报理由为 5-255 个字符"}
```

# 第四部分：管理端处理 —— 一次操作完成三件事

## 4.1 处理的完整流程

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void handle(Long adminId, String adminName, Long reportId, ReportHandleDTO dto) {
    Report report = reportMapper.selectById(reportId);
    if (report == null) {
        throw new BusinessException(ResultCode.REPORT_NOT_FOUND);
    }
    // 已处理/已驳回的举报不能再处理一次，否则会重复处置商品、重复通知举报人
    if (!ReportStatus.PENDING.getCode().equals(report.getStatus())) {
        throw new BusinessException(ResultCode.REPORT_ALREADY_HANDLED,
                "该举报当前状态为「" + ReportStatus.descOf(report.getStatus()) + "」，无法重复处理");
    }

    boolean valid = ReportStatus.HANDLED.getCode().equals(dto.getStatus());
    boolean needOffShelf = valid && Boolean.TRUE.equals(dto.getOffShelf());
    boolean offShelfDone = false;

    // 1. 写处理结果
    reportMapper.update(null, Wrappers.<Report>lambdaUpdate()
            .set(Report::getStatus, dto.getStatus())
            .set(Report::getHandleResult, dto.getHandleResult())
            .set(Report::getHandlerId, adminId)
            .set(Report::getHandleTime, LocalDateTime.now())
            .eq(Report::getId, reportId));

    // 2. 举报成立且选了"同时下架" → 复用商品管理的处置能力
    if (needOffShelf) { ... }

    // 3. 通知举报人
    ...
}
```

**一次点击，三件事同时在同一个事务里完成：**

| 步骤 | 做什么 | 失败会怎样 |
| --- | --- | --- |
| 1 | 记录处理结论 | 举报还是"待处理" |
| 2 | 下架商品（可选） | 商品还在，但举报显示"已处理" —— **矛盾** |
| 3 | 通知举报人 | 处理完了但举报人不知道 |

**如果不在一个事务里，第 2 步失败会导致"举报说已处理，商品却还在"这种最糟糕的状态。** 举报人会以为平台在敷衍他。

## 4.2 复用现成能力的价值

```java
// 2. 举报成立且选了"同时下架" → 直接复用商品管理的处置能力。
//    forceOffShelf 内部会：下架商品、写审核留痕、关闭进行中的订单、
//    通知卖家。这一整套能力早就写好了，这里不该重新实现一遍。
adminProductService.forceOffShelf(adminId, adminName, report.getProductId(), offShelf);
```

**如果不复用，会漏掉多少东西？** 看看 `forceOffShelf` 内部做了什么：

```java
public void forceOffShelf(Long adminId, String adminName, Long productId, ForceOffShelfDTO dto) {
    Product product = requireProduct(productId);
    // ① 校验状态
    // ② 改商品状态 + 写处置原因
    // ③ 写审核留痕（biz_audit_record）
    // ④ 关闭进行中的订单（并通知买卖双方）
    // ⑤ 通知卖家
}
```

**如果在举报服务里手写一遍，几乎必然会漏掉 ③ 和 ④。** 因为写的时候你只想着"把商品下架"，不会想到"还有订单挂着"。

**这正是模块化的价值：已经想清楚的事，不要重新想一遍。**

> 这是整个项目里最漂亮的复用之一：**举报处理 → 商品处置 → 订单关闭 → 通知双方**，
> 一条链路上四层能力串起来，而举报模块只写了一行调用。

## 4.3 处理结论为什么必填

```java
/**
 * 处理结论。必填，因为它会原样通知给举报人 ——
 * 只说"已处理"却不说什么结论，举报人等于没收到反馈。
 */
@NotBlank(message = "请填写处理结论")
private String handleResult;
```

**举报人花了时间举报，平台必须给出"为什么"。**

如果管理员可以空着结论点"已处理"，举报人收到的通知就是：

> 你的举报已处理。

**—— 处理了什么？举报成立吗？商品下架了吗？他什么都不知道。**

这和"已结束"合并状态是同一个问题：**平台没有把话说清楚。**

## 4.4 重复处理的防护

```java
if (!ReportStatus.PENDING.getCode().equals(report.getStatus())) {
    throw new BusinessException(ResultCode.REPORT_ALREADY_HANDLED,
            "该举报当前状态为「" + ReportStatus.descOf(report.getStatus()) + "」，无法重复处理");
}
```

**不做这个校验会怎样？**

1. 管理员处理了一次举报（商品已下架）
2. 网络卡顿，他又点了一次
3. **商品被下架第二次** → `forceOffShelf` 会抛"只有在售商品才能强制下架"，整个请求失败
4. 更糟的情况：如果商品后来重新上架了，第二次处理会**再下架一次**，并且再发一轮通知

**这是"终态不可流转"的又一处应用**——和订单模块的 `requireStatus` 是同一个思路。

实测：

```
=== R12. handle the SAME report again ===
{"code":8004,"message":"该举报当前状态为「已处理」，无法重复处理"}
```

# 第五部分：一个真实 bug —— 复用的代价

**这是本篇最有价值的一节。**

## 5.1 现象

测试时，我拿一个**已经售出**的商品试了"举报成立 + 同时下架"：

```
=== V1. report product 4 then handle with off-shelf ===
report id = 3
{"code":3002,"message":"只有在售商品才能强制下架"}
```

**整个举报处理失败了。**

## 5.2 根因：被复用方法的前置条件变成了我的失败点

调用链是这样的：

```
AdminReportService.handle()
    ├─ ① 写举报处理结论            ← 成功
    ├─ ② adminProductService.forceOffShelf()
    │       └─ if (!ON_SALE) throw 3002     ← 抛异常
    └─ ③ 通知举报人                ← 没执行到
```

`forceOffShelf` 自己有一个**合理的前置条件**：

```java
if (!ProductStatus.ON_SALE.getCode().equals(product.getStatus())) {
    throw new BusinessException(ResultCode.PRODUCT_STATUS_ILLEGAL, "只有在售商品才能强制下架");
}
```

单独看这个校验是对的 —— **商品已经下架了，你再下架一次确实没意义。**

但站在举报处理的角度，这个异常是错误的：

| 目标 | 是否达成 |
| --- | --- |
| 记录"举报成立"的结论 | ❌ 被回滚了 |
| **让商品不可见** | ✅ **商品已经售出了，本来就不在售** |
| 通知举报人 | ❌ 没执行到 |

**"让商品不可见"这个目标已经达成了**（售出的商品本来就不在公开列表里），但我却因为这个"已经达成的目标"而让整个操作失败。

**这就是复用带来的副作用：你以为在调一个"下架商品"的动作，实际上调用的是一个"只有特定状态才能执行的动作"。**

## 5.3 修复：目标已达成则跳过

```java
if (needOffShelf) {
    Product product = productMapper.selectById(report.getProductId());
    // 商品可能已经被下架、售出或删除了。
    // 这种情况下"让商品不可见"这个目标**已经达成**，不需要再下架一次 ——
    // 如果硬调 forceOffShelf，它会抛"只有在售商品才能强制下架"，
    // 导致整笔举报处理失败，管理员连处理结论都记不下来。
    if (product != null && ProductStatus.ON_SALE.getCode().equals(product.getStatus())) {
        ForceOffShelfDTO offShelf = new ForceOffShelfDTO();
        offShelf.setReason("举报处理：" + dto.getHandleResult());
        adminProductService.forceOffShelf(adminId, adminName, report.getProductId(), offShelf);
        offShelfDone = true;
    }
}
```

**关键思路的转变：**

| 之前 | 现在 |
| --- | --- |
| "我要下架这个商品" | **"我要让这个商品不可见"** |
| 必须成功调用下架 | 已经不可见了就不用调 |

**把"动作"改成"目标"，问题就消失了。**

修复后：

```
=== handle report 3 with offShelf=true (product not on sale) ===
{"code":200,"message":"已处理并通知举报人"}     ← 成功
```

## 5.4 连带修正：通知要如实描述

发现了第二个问题：**通知里写死了"商品已被下架"。**

```java
// ❌ 之前：不管有没有真的下架，都说"已下架"
+ (needOffShelf ? "，商品已被下架。" : "。")
```

而 `needOffShelf` 只表示"管理员勾选了这个选项"，**不代表下架动作真的执行了**。

所以修复时加了第三个状态变量：

```java
// 记录"这次是否真的下架了商品"，后面通知里要如实描述 ——
// 商品已经售出/下架时我们会跳过下架动作，这时候不能跟举报人说"已下架"
boolean offShelfDone = false;
```

```java
String content = valid
        ? "你举报的" + productName + "经核实存在违规"
          + (offShelfDone ? "，商品已被下架。" : "。")
          + "处理结论：" + dto.getHandleResult()
        : ...
```

实测（商品已售出，跳过了下架）：

```
你举报的「机械革命极光pro」经核实存在违规。处理结论：经核实商品图片系盗用他人实拍图，已下架处理。
```

**注意这里没有说"商品已被下架"** —— 因为确实没有下架（它已经售出了）。**如实描述，才不会误导举报人。**

> **"用户想做什么"（needOffShelf，一个意图）和"实际发生了什么"（offShelfDone，一个事实）
> 是两个不同的东西，不能混用。**
> 通知里应该说事实，而不是意图。

## 5.5 这个 bug 的通用教训

**调用一个"有条件的方法"之前，先问自己：它的前置条件在我的场景里一定成立吗？**

如果答案是否定的，有三种处理方式：

| 方式 | 例子 | 评价 |
| --- | --- | --- |
| 先判断再调用 | 本项目采用 | ✅ 清晰，但要知道对方的前置条件 |
| 捕获异常当成功 | `try { forceOffShelf } catch (...) {}` | ❌ 会吞掉真实的失败 |
| 复制一份不带校验的实现 | 另写一个 `offShelfIgnoreStatus()` | ❌ 逻辑重复，以后改一处漏一处 |

**第一种最好，但它要求你了解被调用方的契约。** 这也是为什么 `forceOffShelf` 的注释要写清楚它在什么条件下会抛异常 —— **异常信息不只是给用户看的，也是给调用方看的。**

# 第六部分：查询的两个细节

## 6.1 待处理排在最前面

```xml
ORDER BY
    CASE WHEN r.status = 0 THEN 0 ELSE 1 END ASC,
    r.create_time DESC
```

**排序策略就是工作优先级。**

管理员打开举报列表，他最关心的是"**还有什么没处理**"，而不是"最新的举报是什么"。

- 如果按时间倒序：昨天漏处理的那条会被今天的新举报挤到后面，**越积越多**
- 用 `CASE WHEN` 把待处理顶到最前：**待办永远在第一屏**

**这不是技术问题，是工作流设计。** 一个"按时间排序"的列表会让待办事项不断沉底，最终没人处理。

## 6.2 商品已被删除，举报仍然要显示

```xml
<!--
  商品那张关联**故意不加 p.deleted = 0** —— 商品已经被删了，
  举报记录仍然要能看到，否则管理员点进列表发现"被举报的商品不见了"，
  这个举报就没法处理了。商品状态通过 productStatus 返回给前端展示。
-->
FROM biz_report r
LEFT JOIN biz_product p ON p.id = r.product_id
```

**这是一个反直觉的决定。** 项目里到处都在强调"手写 SQL 要加 `deleted = 0`"，这里却故意不加。

**因为查询的目的不同：**

| 场景 | 目的 | 要不要过滤已删 |
| --- | --- | --- |
| 商品列表 | 给用户看"能买的东西" | 要 |
| 我的收藏 | 给用户看"收藏了什么" | 要（已删的收藏没意义） |
| **举报列表** | **给管理员看"待处理的事"** | **不要** |

**删除商品不等于处理完举报。** 如果商品被删了，这个举报记录就"消失"了，管理员会以为举报被处理过。

前端也做了对应处理：

```vue
<div class="cell-title" @click="goProduct(row.productId)">
  {{ row.productTitle || '（商品已删除）' }}
</div>
```

**`productTitle` 为 null 时显示"（商品已删除）"**，而不是一片空白。

> **规则不是死的。** "手写 SQL 要加 deleted = 0"这条规则的**目的是"不返回用户不该看到的数据"**，
> 而在举报列表这个场景里，**已删除商品的数据正是管理员需要看到的**。
> **理解规则背后的目的，才能判断什么时候该破例。**

## 6.3 一段 SQL 服务两个场景

```java
/**
 * 只查某个用户提交的举报。
 * <p>
 * 由后端从 token 取，不接受前端传入 —— 否则改个参数就能看别人的举报记录。
 * 同一段 SQL 因此能同时服务"我的举报"和"管理后台列表"两个场景：
 * 前者带上这个条件，后者留空。
 */
@Schema(hidden = true)
private Long userId;
```

```java
// 用户侧：强制带上 userId
query.setUserId(userId);

// 管理侧：显式清空，防止有人从前端塞一个 userId 把列表筛成别人的
query.setUserId(null);
```

**两边都做得很明确：一边强制赋值，一边强制清空。**

容易犯的错误是只在用户侧赋值、管理侧不管 —— 那么前端传 `?userId=3` 就能让管理员看到筛选后的列表。**虽然影响不大，但"参数能被意外控制"本身就是隐患。**

> **同一个查询对象被多个接口复用时，每个接口都要显式声明"这个字段我管不管"。**
> 沉默 = 把这个字段的控制权交给了调用方。

# 第七部分：前端实现

## 7.1 举报入口：轻量但不隐蔽

```vue
<el-button text type="info" @click="openReportDialog">
  <el-icon><Warning /></el-icon>
  举报
</el-button>
```

**为什么用 `text` 样式而不是主按钮？**

因为举报不是正常流程的一部分。主按钮（`type="primary"`）是"我希望你点"的视觉暗示，而举报是"需要时才用"的功能。

**但也不能藏起来。** 放在操作区最右边、用灰色文字按钮，位置固定、随时可见 —— **不打扰正常用户，但需要的人找得到。**

## 7.2 举报前先给一句提醒

```vue
<el-alert
  type="warning"
  :closable="false"
  show-icon
  title="请如实举报。恶意举报会影响你的账号信誉，平台会记录举报行为。"
/>
```

**这句话的作用不是"阻止恶意举报"**（真想捣乱的人不会被一句话吓住），而是：

1. **给正常用户一个确认**："我知道我在做什么"
2. **为后续处理留下依据**："平台已经提醒过"
3. **降低误报**：有些人只是想"反馈一下"，看到"举报"两个字会重新考虑

**注意措辞是"会影响你的账号信誉"，而不是"将被封号"。** 威胁性的文案会让正常用户不舒服，**陈述事实就够了。**

## 7.3 管理端：处理弹窗随选项变化

```vue
<el-form-item v-if="form.status === 1" label="同时下架商品">
  <el-switch v-model="form.offShelf" />
  <span class="form-tip inline">
    开启后会强制下架该商品，并自动关闭进行中的订单、通知卖家
  </span>
</el-form-item>
```

两个细节：

**① 只在"举报成立"时显示下架开关。** 举报不成立时下架商品是荒谬的，**不显示比显示了再禁用更好**。

**② 提示语说清了连带影响**："自动关闭进行中的订单、通知卖家"。

**管理员需要知道"点这个开关会波及什么"。** 如果只写"同时下架商品"，他不会想到还有订单和通知 —— 而这个开关确实会触发那些动作。

```js
await handleReport(current.value.id, {
  status: form.status,
  handleResult: form.handleResult,
  // 驳回时没必要传下架，明确置 false 避免后端误解
  offShelf: form.status === 1 ? form.offShelf : false
})
```

**注意这里显式置 `false`，而不是留 `undefined`。**

虽然后端有 `valid && Boolean.TRUE.equals(dto.getOffShelf())` 双重保护，但**前端也不该依赖后端的兜底**。传一个明确的值，两边都清楚。

## 7.4 用户侧：我的举报

举报之后用户会问："我的举报有结果了吗？"

站内通知能回答"有结果了"，但**看不了全部历史**。所以做了一个列表页：

```vue
<div v-if="item.handleResult" class="result">
  <span class="label">处理结论：</span>{{ item.handleResult }}
</div>

<div v-if="item.handleTime" class="handled text-secondary">
  {{ item.handlerName || '平台' }} 于 {{ formatTime(item.handleTime, true) }} 处理
</div>
```

**显示"谁处理的、什么时候处理的"** —— 让举报人知道这是**一个具体的人看过并做出了判断**，而不是系统自动回复。

**这个细节对信任感很重要。** 同样是"已处理"，写着"admin 于 10:30 处理"和什么都不写，给人的感觉完全不同。

## 7.5 空状态要有引导

```vue
<el-empty v-if="!loading && !list.length" description="还没有提交过举报">
  <el-button type="primary" @click="router.push('/product/list')">去逛逛</el-button>
</el-empty>
```

**"还没有提交过举报"是正常的**，不该让用户觉得"这里是不是坏了"。给一个去浏览商品的动作，页面就不是死胡同。
