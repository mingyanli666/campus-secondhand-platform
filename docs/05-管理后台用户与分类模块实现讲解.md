## 1.3 一个贯穿全篇的主题：**管理操作的"防呆"**

用户管理和分类维护，本质上都是"管理员对平台数据做处置"。这类操作有三个特点：

| 特点 | 后果 | 本项目的应对 |
| --- | --- | --- |
| **不可逆** | 删错了就没了 | 逻辑删除 + 引用检查 |
| **影响面大** | 一个误操作影响很多用户 | 操作前二次确认 + 明确的后果提示 |
| **可能锁死自己** | 管理员把自己禁用了就进不来 | 服务端拦截 + 前端禁用按钮 |

后面会逐一展开。

# 第二部分：用户管理 —— 管理操作的边界与防呆

## 2.1 刻意不做的功能：修改用户角色

打开 `AdminUserController`，你会发现**没有一个"修改角色"的接口**。这是有意为之：

```java
/**
 * 管理后台 - 用户管理接口。
 * <p>
 * 这里刻意**没有提供"修改用户角色"的接口**。给用户提权是一件需要谨慎对待的事，
 * 一个点的位置不对就可能把自己或别人变成管理员。本项目不做角色变更，
 * 管理员账号由 DataInitializer 初始化，需要新增就走数据库 —— 这是有意的收紧。
 */
```

**为什么不加？** 三个理由：

1. **需求里没有。** 需求说的是"用户管理"，不是"权限管理"。多做一个没人要求、又有风险的功能，不划算。
2. **提权是最危险的操作。** 一旦客能把自己变成管理员，前面所有的 `@RequireRole` 就全部失效了。
3. **少一个接口 = 少一个攻击面。** 这是安全设计的基本原则。

> **"不做"也是一种设计决策，而且要认真说明理由。**
> 答辩时如果说"我特意没做角色变更，因为……"，比"我做了角色变更"更能体现工程思维。

## 2.2 防呆一：不能禁用自己

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void updateStatus(Long operatorId, Long userId, Integer status) {
    requireUser(userId);

    // 防呆：不能把自己禁用掉。
    // 这类"自我锁死"的操作在后台系统里一定要拦，否则管理员一个误操作
    // 就再也登不进来了，只能去数据库里改。
    if (Constants.STATUS_DISABLED.equals(status) && userId.equals(operatorId)) {
        throw new BusinessException(ResultCode.CANNOT_DISABLE_SELF);
    }

    User update = new User();
    update.setId(userId);
    update.setStatus(status);
    userMapper.updateById(update);
}
```

`operatorId` 是从 `UserContext.userId()` 传进来的（Controller 那边取的 token），**不是前端传的**：

```java
public Result<Void> updateStatus(@PathVariable Long id, @Valid @RequestBody StatusDTO dto) {
    adminUserService.updateStatus(UserContext.userId(), id, dto.getStatus());
    return Result.success(dto.getStatus() == 1 ? "已启用该账号" : "已禁用该账号", null);
}
```

**前端也有对应的处理**——把自己的禁用按钮置灰：

```vue
<el-button
  v-if="row.status === 1"
  size="small"
  type="danger"
  plain
  :disabled="row.id === myId"
  @click="handleToggleStatus(row, 0)"
>
  禁用
</el-button>
```

**两层防护的含义不同：**

- 前端置灰 → **体验**：管理员不会点到一个注定失败的操作
- 后端拦截 → **安全**：就算有人直接调接口，也禁不掉自己

实测验证：

```
=== 5. admin disables HIMSELF ===
{"code":2006","message":"不能禁用自己的账号"}
```

## 2.3 防呆二：重置密码为什么不能用固定的 "123456"

```java
/**
 * 生成随机密码时使用的字符集。
 * 刻意去掉了 0 / O / 1 / l / I 这些容易看错的字符 ——
 * 管理员要把这个密码念给用户或抄下来，混淆字符会带来真实的沟通成本。
 */
private static final String PASSWORD_CHARS =
        "abcdefghjkmnpqrstuvwxyzABCDEFGHJKMNPQRSTUVWXYZ23456789";

@Override
public String resetPassword(Long userId) {
    requireUser(userId);

    // 随机生成而不是重置成固定的 "123456"。
    // 固定默认密码是真实存在的安全隐患：所有人都知道，
    // 谁都能拿它去试任何一个被重置过的账号。
    String newPassword = RandomUtil.randomString(PASSWORD_CHARS, 8);

    User update = new User();
    update.setId(userId);
    update.setPassword(BCrypt.hashpw(newPassword, BCrypt.gensalt()));
    userMapper.updateById(update);

    // 日志里不打印密码明文，只记录"谁重置了谁的密码"
    log.info("管理员重置了用户 {} 的密码", userId);

    // 明文通过返回值交给前端展示一次，不入库
    return newPassword;
}
```

### 固定默认密码为什么危险

想象"重置成 123456"这种常见做法会发生什么：

1. 张三的账号被重置了，密码是 `123456`
2. 张三还没登录、或者根本没注意到
3. **任何人都可以用 `用户名 + 123456` 登录张三的账号**

这不是理论风险，是真实存在的漏洞（很多系统都这么干过）。随机生成就杜绝了这个问题。

### 混淆字符的处理

注意字符集里没有 `0 O 1 l I`。为什么？

管理员拿到密码后要**念给用户**或者**写在纸条上**。「这是数字 1 还是小写 L？」——这种沟通成本是真实的。去掉易混字符，密码依然有足够强度（8 位、57 个字符集）。

> **安全性和可用性经常要做取舍，但很多取舍是"不用牺牲安全就能换来的便利"。**
> 去掉混淆字符就是这一类——它不降低安全强度，却显著提升了可用性。

### 密码明文的生命周期

这是这段代码里最值得注意的设计：

```
生成明文 newPassword
    ↓
BCrypt 加密 → 存入数据库（永不还原）
    ↓
明文通过 HTTP 响应返回一次 → 前端弹窗展示
    ↓
用户关闭弹窗 → 明文从内存中消失
    ↓
日志里只有 "重置了用户 3 的密码"，没有明文
```

**明文只在两个地方短暂存在：内存和这一次响应。数据库、日志都拿不到。**

前端弹窗上也明确写了这一点：

```vue
<el-alert
  type="warning"
  :closable="false"
  show-icon
  title="新密码只显示这一次"
  description="关闭后无法再次查看。请立即复制并转告该用户，建议其登录后自行修改。"
/>
```

实测验证：

```
=== P1. admin resets lisi password ===
newPassword = ZrYXeg2m
length=8  contains confusing chars? no (good)

=== P2. lisi login with OLD password ===
{"code":2002,"message":"账号或密码错误"}

=== P3. lisi login with NEW password ===
code = 200  nickname = 李四
```

**旧密码立即失效 —— 这才叫"重置"。**

## 2.4 用户列表的两个设计细节

### 商品数为什么必须显示

```java
/**
 * 管理后台 - 用户列表项。
 * <p>
 * 继承 UserVO 拿到基础字段，再补一个 productCount。
 * 管理员判断"要不要禁用某个用户"时，看到他有 30 件在售商品和看到 0 件，
 * 决策是完全不一样的 —— 所以这个数字必须给出来。
 */
public class AdminUserVO extends UserVO {
    private Long productCount;
}
```

**这是"帮用户做决策"的设计。** 光看用户名和状态，管理员没法判断该不该禁用；看到"已发布 30 件商品、信誉分 100"，就知道这是个正常卖家，需要谨慎处理。

```vue
<el-table-column label="发布商品" width="100" align="center">
  <template #default="{ row }">
    <el-link v-if="row.productCount > 0" type="primary" @click="goUserProducts(row)">
      {{ row.productCount }} 件
    </el-link>
    <span v-else class="text-secondary">0 件</span>
  </template>
</el-table-column>
```

数字还能点，直接跳到商品管理页按这个卖家筛选。**从"发现问题"到"处理问题"不用重新找。**

### 信誉分低于 60 变色

```vue
<span :class="{ low: row.creditScore < 60 }">{{ row.creditScore }}</span>
```

```css
.low {
  color: #ef4444;
  font-weight: 600;
}
```

**把"需要注意的数据"视觉上标出来。** 管理员扫一眼列表就知道谁有问题，不用一个个数字去比。

## 2.5 一条重要的设计说明

注意 `updateStatus` 只改了 `status` 一个字段：

```java
User update = new User();
update.setId(userId);
update.setStatus(status);
userMapper.updateById(update);
```

这正是利用 `updateById` **"只更新非 null 字段"** 的特性——不会把 `password`、`role` 覆盖掉。

同一个特性在审核模块是坑（想清空字段做不到），在这里却是优点。**理解一个特性的适用边界，比记住"它能用/不能用"更重要。**

# 第三部分：分类维护 —— 删除前必须检查引用

## 3.1 删除分类为什么不能直接删

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void delete(Long id) {
    Category category = requireCategory(id);

    // 删除前必须检查有没有商品在用这个分类。
    // 否则删完之后，这些商品的 category_id 就成了悬空引用，
    // 列表里显示"未分类"，卖家也改不回去（下拉框里已经没有这个选项了）。
    Long productCount = productMapper.selectCount(
            Wrappers.<Product>lambdaQuery().eq(Product::getCategoryId, id));
    if (productCount > 0) {
        throw new BusinessException(ResultCode.CATEGORY_HAS_PRODUCT,
                "该分类下还有 " + productCount + " 件商品，无法删除。可以改为「停用」，"
                        + "停用后发布商品时不再显示该分类，已发布的商品不受影响。");
    }

    // 这里走逻辑删除（Category 有 @TableLogic），数据仍可追溯
    categoryMapper.deleteById(id);
    log.info("删除分类 {} - {}", id, category.getName());
}
```

### 不检查会发生什么

假设「手机」分类下有 50 件商品，管理员直接删掉：

| 后果 | 说明 |
| --- | --- |
| 列表显示"未分类" | `LEFT JOIN` 找不到分类，`categoryName` 为 null |
| 按分类筛选失效 | 用户点「手机」，这 50 件商品不会出现 |
| 卖家改不回来 | 编辑商品时下拉框里已经没有「手机」选项了 |
| **数据一致性被破坏** | `biz_product.category_id` 指向了一个不存在的 ID（悬空引用） |

**最后一条是最严重的。** 数据库层面没有外键约束（项目里没用外键，这是常见做法），所以数据库不会拦你，全靠应用层自己把关。

### 报错信息里的"出路"

注意那句错误提示：

```
该分类下还有 2 件商品，无法删除。
可以改为「停用」，停用后发布商品时不再显示该分类，已发布的商品不受影响。
```

**不只说"不能做"，还告诉管理员"那该怎么办"。** 这是好的错误提示的标准：

| 层次 | 例子 | 评价 |
| --- | --- | --- |
| 最差 | `操作失败` | 管理员一头雾水 |
| 一般 | `该分类下还有商品，无法删除` | 知道原因了，但不知道下一步 |
| **好** | `...还有 2 件商品无法删除。可以改为「停用」...` | 有原因、有具体数字、有替代方案 |

### 实测

```
=== C6. delete category that HAS products (id=1 手机) ===
{"code":3012,"message":"该分类下还有 2 件商品，无法删除。可以改为「停用」，..."}

=== C8. delete the empty category ===
{"code":200,"message":"删除成功"}
```

**有商品的删不掉，没商品的能删掉 —— 规则精确生效。**

## 3.2 "停用"和"删除"的区别

这两个操作看起来都是"让分类消失"，但语义完全不同：

| | 停用（`status = 0`） | 删除（`deleted = 1`） |
| --- | --- | --- |
| 前台是否显示 | 不显示 | 不显示 |
| 已发布的商品 | **不受影响**，正常展示 | **受影响**，变成"未分类" |
| 能否恢复 | 一键启用即可 | 逻辑删除，需要改数据库 |
| 适用场景 | 暂时不开放某品类 | 建错了，要彻底去掉 |

**在 UI 上也体现了这个区分**：列表里用 `el-switch` 直接切换启停（轻量、可逆），删除按钮在有商品时**直接置灰并给出 tooltip 说明**：

```vue
<el-tooltip :disabled="row.productCount === 0" content="该分类下还有商品，无法删除" placement="top">
  <span>
    <el-button
      size="small"
      type="danger"
      plain
      :disabled="row.productCount > 0"
      @click="handleDelete(row)"
    >
      删除
    </el-button>
  </span>
</el-tooltip>
```

> 这里有个 Element Plus 的细节：`el-tooltip` 包裹一个 `disabled` 的按钮时，
> tooltip 不生效——因为禁用元素不触发鼠标事件。所以外面套了一层 `<span>`，
> 让鼠标事件落在 span 上。**这类小坑用得多了自然会记住。**

## 3.3 分类名唯一性：逻辑删除的坑第三次出现

```java
/**
 * 校验分类名唯一。
 * <p>
 * 为什么不在数据库上建唯一索引？因为分类是逻辑删除的：
 * 删掉"平板电脑"之后再建一个同名的，就会被唯一索引挡住 —— 这正是
 * 第一阶段在用户表上避开的那个坑，这里同样避开。
 *
 * @param excludeId 编辑时排除自己
 */
private void checkNameUnique(String name, Long excludeId) {
    Long count = categoryMapper.selectCount(Wrappers.<Category>lambdaQuery()
            .eq(Category::getName, name)
            .ne(excludeId != null, Category::getId, excludeId));
    if (count > 0) {
        throw new BusinessException(ResultCode.CATEGORY_NAME_EXISTS);
    }
}
```

**这是"逻辑删除 + 唯一索引冲突"这个问题第三次出现：**

| 出现位置 | 处理方式 |
| --- | --- |
| `sys_user.username`（第一阶段） | 用户表干脆不做逻辑删除 |
| `sys_category.name`（本阶段） | 不建唯一索引，服务层校验 |
| `biz_favorite (user_id, product_id)`（第一阶段） | 收藏表用物理删除 |

**同一个问题在不同表上有不同的解法，取决于业务语义。** 没有万能方案。

### 服务层校验的代价

必须诚实地说：**服务层校验有并发窗口。**

```
时刻 T1: 管理员A 检查 "智能家居" 不存在 → 通过
时刻 T2: 管理员B 检查 "智能家居" 不存在 → 通过
时刻 T3: 管理员A 插入成功
时刻 T4: 管理员B 插入成功          ← 两条同名分类
```

数据库唯一索引能从根本杜绝这个问题，但它和逻辑删除冲突。

**为什么我接受这个代价？** 因为：
- 分类维护是**极低频操作**（一个平台可能就建 10 个分类，之后基本不动）
- 就算真的出现同名，影响也只是"列表里有两个手机"，管理员随手删一个就行
- 相比之下，"删了分类后不能重建同名分类"这个必然发生的问题更烦人

**这类判断叫"评估风险的实际影响"，比追求理论上的完美更重要。**

### `.ne(condition, column, value)` 的用法

```java
.ne(excludeId != null, Category::getId, excludeId)
```

这是 MyBatis-Plus 的**条件重载**：第一个参数为 false 时不加这个条件。

- **新建**时 `excludeId = null` → 不加 `id != null` 这个条件 → 检查全表
- **编辑**时 `excludeId = 5` → 加 `id != 5` → 检查其他分类，**排除自己**

**没有这个重载的话，编辑分类时改个图标都会被自己的名字挡住。**

## 3.4 一个命名教训：`UserStatusDTO` → `StatusDTO`

一开始我把"启用/禁用"的请求体命名成 `UserStatusDTO`，写在用户管理里。后来分类维护也需要同样的东西（结构完全一样：一个 0/1 的 status 字段），我直接复用了它。

**但名字就不对了**——分类接口上出现一个叫 `UserStatusDTO` 的参数，读代码的人会愣一下。

于是改成了 `StatusDTO`：

```java
/**
 * 通用的"启用/停用"请求体。
 * <p>
 * 用户和分类的状态语义完全一致（1 启用 / 0 禁用），所以共用一个 DTO。
 * 一开始我把它命名成 UserStatusDTO，加到分类接口上时名字就说不通了 ——
 * 命名要按"它是什么"而不是"第一次用在哪"。
 */
public class StatusDTO { ... }
```

> **命名要按"它本质上是什么"，而不是"我第一次在哪用它"。**
> 这条规则看起来简单，但实际写代码时非常容易违反——因为你是**从使用场景出发**去写的，
> 很自然就用场景来命名了。

# 第四部分：手写 SQL 的两个新场景

这一阶段又写了两条自定义 SQL，都用了**相关子查询**做计数。

## 4.1 用户列表：带每人发布的商品数

```xml
<select id="selectAdminUserPage" resultType="com.digital.platform.vo.AdminUserVO">
    SELECT
        u.id, u.username, u.nickname, u.avatar, u.phone, u.email,
        u.gender, u.campus, u.intro, u.role, u.status,
        u.credit_score    AS creditScore,
        u.last_login_time AS lastLoginTime,
        u.create_time     AS createTime,
        (SELECT COUNT(*) FROM biz_product p
          WHERE p.user_id = u.id AND p.deleted = 0) AS productCount
    FROM sys_user u
    <where>
        <if test="query.keyword != null and query.keyword != ''">
            AND (
                u.username LIKE CONCAT('%', #{query.keyword}, '%')
                OR u.nickname LIKE CONCAT('%', #{query.keyword}, '%')
                OR u.phone    LIKE CONCAT('%', #{query.keyword}, '%')
            )
        </if>
        <if test="query.role != null and query.role != ''">
            AND u.role = #{query.role}
        </if>
        <if test="query.status != null">
            AND u.status = #{query.status}
        </if>
    </where>
    ORDER BY u.create_time DESC, u.id DESC
</select>
```

### 相关子查询是什么

```sql
(SELECT COUNT(*) FROM biz_product p WHERE p.user_id = u.id AND p.deleted = 0) AS productCount
```

**"相关"的意思是：子查询里引用了外层的列 `u.id`。**

所以它不是"执行一次算出一个数"，而是"**外层每一行，都拿这行的 id 去数一次**"。概念上像是一个 for 循环：

```java
for (User u : users) {
    u.productCount = countProductsOf(u.id);   // 每行算一次
}
```

区别是：**这个"循环"发生在数据库内部**，不需要把数据搬到 Java 里再循环。这就是它的价值。

### 为什么不用 LEFT JOIN + GROUP BY

```sql
-- 另一种写法
SELECT u.*, COUNT(p.id) AS productCount
FROM sys_user u
LEFT JOIN biz_product p ON p.user_id = u.id AND p.deleted = 0
GROUP BY u.id
```

两种写法都能得到正确结果。我选了子查询，原因：

| | 相关子查询 | LEFT JOIN + GROUP BY |
| --- | --- | --- |
| 可读性 | 更直观："数这个人的商品" | 需要理解 GROUP BY 的语义 |
| 字段选择 | `u.*` 和 `u.xxx` 随便写 | **必须把所有非聚合列写进 GROUP BY**（或用 ONLY_FULL_GROUP_BY 兼容写法） |
| 性能 | MySQL 有优化，小数据量够用 | 大数据量通常更优 |

**对毕设的数据量（几千用户），性能差异可以忽略，我优先选可读性。**

> 如果真的到了十万级用户，这里应该改成 `LEFT JOIN + GROUP BY`，或者给
> `biz_product(user_id, deleted)` 建联合索引。**知道什么时候该换方案，比一开始就用"最优方案"更重要。**

## 4.2 分类列表：同一个套路

```xml
<select id="selectAdminCategoryList" resultType="com.digital.platform.vo.AdminCategoryVO">
    SELECT
        c.id, c.name, c.icon, c.sort, c.status,
        (SELECT COUNT(*) FROM biz_product p
          WHERE p.category_id = c.id AND p.deleted = 0) AS productCount
    FROM sys_category c
    WHERE c.deleted = 0
    ORDER BY c.sort ASC, c.id ASC
</select>
```

**和上一个几乎一样，只有两处不同**，而这两处不同恰好覆盖了本项目最需要记住的两个点。

## 4.3 ⚠️ 两个 SQL 的 deleted 条件不一样，这不是笔误

对比一下：

```sql
-- UserMapper.xml：没有 deleted 条件
FROM sys_user u
<where>
    <if test="...">...</if>
</where>

-- CategoryMapper.xml：有 deleted 条件
FROM sys_category c
WHERE c.deleted = 0
```

**为什么不一样？**

| 表 | 有 `deleted` 字段吗 | 手写 SQL 要写 `deleted = 0` 吗 |
| --- | --- | --- |
| `sys_user` | **没有**（用户用 `status` 控制启用/禁用） | 不用 |
| `sys_category` | 有（`@TableLogic`） | **必须写** |
| `biz_product` | 有 | **必须写** |

`sys_user` 没有 `deleted` 字段，是第一阶段为了避开"逻辑删除 + username 唯一索引冲突"特意做的设计——**在这里体现出好处了：少一个必须记住的条件。**

### 这是第三次强调这个坑

| 第几次 | 位置 | 说明 |
| --- | --- | --- |
| 第一次 | `ProductMapper.xml` 的列表查询 | 写完发现被删的商品还在列表里 |
| 第二次 | `ProductMapper.sumViewCount()` | 聚合统计没排除已删商品 |
| 第三次 | `CategoryMapper.xml` | 本文档 |

**规则：只要手写 SQL，先问自己一句"这张表有 deleted 吗？要写 deleted = 0 吗？"**

因为 MyBatis-Plus 的逻辑删除**只对 `BaseMapper` 自动生成的方法生效**，手写的一律不管。它不会报错、不会警告，就是默默地多返回几条本该被删的数据。

### 一个防错的习惯

我现在的做法是：**写完一条手写 SQL，立刻想一下"这张表有没有 `deleted`"，然后在 XML 里加一行注释说明。**

比如 `ProductMapper.xml` 里：

```xml
<!--
  商品列表分页查询。
  注意几个关键点：
  1. 手动写了 p.deleted = 0 —— MyBatis-Plus 的逻辑删除只会自动作用于
     它自己生成的方法，手写 SQL 必须自己处理，这是新手最容易漏的地方。
  ...
-->
```

**注释写给"三个月后的自己"看。** 那时候你已经忘了哪张表有什么字段了。

# 第五部分：安全补丁 —— 禁用用户为什么没生效

**这是本阶段最重要的一节。** 它记录了一个"功能看起来做完了，实际上只做了一半"的典型问题。

## 5.1 发现过程

写完"禁用用户"功能后，我去验证它是否真的生效。逻辑上应该测两件事：

1. 被禁用的用户**能不能登录** → 能想到
2. 被禁用的用户**手里已有的 token 还能不能用** → **这才是容易漏的**

写了个测试：

```
=== step 1: lisi 未被禁用时登录，拿到 token ===
token obtained, length = 216

=== step 2: lisi 用这个 token（基线，期望 200） ===
{"code":200,"message":"操作成功",...}

=== step 3: 管理员禁用 lisi ===
{"code":200,"message":"已禁用该账号"}

=== step 4: lisi 用【同一个】token ===
--- 查自己的资料 ---
{"code":200,"message":"操作成功","data":{"id":3,...,"status":0,...}}     ← 还能用！
--- 发布商品 ---
{"code":200,"message":"发布成功，等待平台审核","data":5}                    ← 甚至还能发帖！
```

**"禁用"完全没生效。**

## 5.2 根因：JWT 的无状态特性带来的盲区

回看拦截器的逻辑：

```java
// 3. 校验 token
LoginUser loginUser = jwtUtil.parseToken(resolveToken(request));
if (loginUser == null) {
    throw new BusinessException(ResultCode.UNAUTHORIZED);
}

// 4. 写入上下文
UserContext.set(loginUser);
```

**只校验了签名，没查用户状态。**

这不是"忘了写"，而是**JWT 的设计使然**——这正是第一阶段介绍 JWT 时说的"优点"：

> JWT 的核心思想是：不用服务器记，把身份信息写在令牌里，然后用密钥盖个章防伪。

**"不用服务器记"意味着服务器不知道 token 签发之后发生了什么。**

| 时刻 | 事件 | token 状态 |
| --- | --- | --- |
| T1 | lisi 登录，服务器签发 token | 有效 |
| T2 | 管理员禁用 lisi（数据库 `status = 0`） | **服务器不知道** |
| T3 | lisi 拿 T1 的 token 来发帖 | **签名校验通过 → 放行** ❌ |
| T4 | ... | 一直到 token 过期（72 小时） |

**"禁用用户"变成了"72 小时后生效"。** 而管理员禁用账号最常见的场景恰恰是"这个人正在发违规内容，马上给我停掉"——**这个功能在最需要它的场景下是失效的。**

## 5.3 修复

在解析 token 之后，**回数据库确认账号仍然可用**：

```java
// 4. 回数据库确认账号仍然可用。
//    只校验签名是不够的：JWT 一旦签发就有效到过期为止，
//    如果这期间管理员把账号禁用了，光靠签名根本拦不住 ——
//    用户还能拿旧 token 继续发帖、下单，最长 72 小时，"禁用"形同虚设。
//    代价是每个需登录的请求多一次主键查询，对本项目的量级完全可以接受；
//    真要扛高并发，这里应该换成缓存（Caffeine / Redis）而不是砍掉校验。
User user = userMapper.selectById(loginUser.getUserId());
if (user == null) {
    throw new BusinessException(ResultCode.UNAUTHORIZED);
}
if (!Constants.STATUS_ENABLED.equals(user.getStatus())) {
    throw new BusinessException(ResultCode.USER_DISABLED);
}
// 角色和昵称以数据库为准：token 可能是很久以前签发的，里面的信息会过期
loginUser.setRole(user.getRole());
loginUser.setNickname(user.getNickname());
```

### 修复后的实测

```
=== AFTER FIX ===
step 1. lisi 拿到 token
step 2. 管理员禁用 lisi
step 3. lisi 复用同一个 token：
  --- 查资料 ---   {"code":2004,"message":"账号已被禁用，请联系管理员"}     ✅
  --- 发布商品 --- {"code":2004,"message":"账号已被禁用，请联系管理员"}     ✅
  --- 浏览公开列表 --- 200                                                  ✅ 公开接口不受影响
step 4. 管理员重新启用 lisi，旧 token 立刻恢复可用：
  {"code":200,"message":"操作成功",...}                                    ✅
```

**最后一行的行为值得注意**：重新启用后，**用户不需要重新登录**，他手里的 token 立刻又能用了。因为拦截器每次都去查实时状态，所以状态一改立刻生效——**这也是"回数据库查"带来的好处。**

## 5.4 顺带修好的第二个问题：角色和昵称会过期

```java
// 角色和昵称以数据库为准：token 可能是很久以前签发的，里面的信息会过期
loginUser.setRole(user.getRole());
loginUser.setNickname(user.getNickname());
```

原来的代码直接用 token 里的 `role` 做权限判断。假设（本项目目前不支持，但将来可能）：

1. 管理员把张三从 ADMIN 降级成 USER
2. 张三拿着旧的 token 继续调管理接口
3. token 里写的还是 `role = ADMIN` → **`@RequireRole` 校验通过** → 越权

改成从数据库读角色之后，这种"权限变更延迟"问题也一并解决了。

> **JWT 里存的是"签发那一刻的快照"。** 凡是会变的东西（状态、角色），
> 都不能只信 token，必须以数据库为准。**只有不会变的东西（用户 ID）才适合放在 token 里当权威。**

## 5.5 性能取舍：为什么我接受"每个请求多一次查询"

这个修复的代价是：**每个需要登录的请求多一次数据库查询。**

这值得吗？先看成本：

| 指标 | 数值 |
| --- | --- |
| 查询类型 | `SELECT ... WHERE id = ?`（主键查询，走聚簇索引） |
| 单次耗时 | 亚毫秒级（本地 MySQL） |
| 频次 | 每个需登录的请求 1 次 |

再看收益：**"禁用用户"这个功能从"72 小时后生效"变成"立刻生效"。**

**对一个二手交易平台来说，"能立刻封禁违规用户"的价值远大于那点查询开销。**

不过这个取舍有边界。真到了高并发场景，正确做法**不是砍掉校验**，而是**加缓存**：

```java
// 生产环境的做法示意（本项目未实现）
User user = userCache.get(userId);        // Caffeine 本地缓存 / Redis
if (user == null) {
    user = userMapper.selectById(userId);
    userCache.put(userId, user, 5, TimeUnit.MINUTES);
}
```

**注意：缓存会重新引入延迟**（最多 5 分钟），所以"禁用"又变成"5 分钟后生效"。这是一个新的取舍点——**缓存时间越短越安全，越长越省资源。**

> **取舍不是"选一个更好的"，而是"清楚每个选项放弃了什么"。**

## 5.6 为什么公开接口不做这个检查

修复只加在了"需要登录"的路径上：

```java
// 2. 公开接口放行
if (isPublic) {
    // 公开接口也尝试解析 token，方便详情页判断"当前用户是否已收藏"
    LoginUser user = jwtUtil.parseToken(resolveToken(request));
    if (user != null) {
        UserContext.set(user);
    }
    return true;      // ← 这里没有回数据库查状态
}
```

**理由：**

1. **公开接口本来就不需要账号有效。** 一个被禁用的用户浏览商品列表，对平台没有任何危害。
2. **数量大。** 商品列表、详情是流量最高的接口，每个都查一次库不划算。
3. **语义上说不通。** 如果被禁用的用户连商品都不能看，那"禁用"就等于"封 IP"了，太重。

实测也确认了：禁用后 lisi 访问 `/api/product/page` 返回 200。

> **安全措施要有明确的作用域。** "禁用账号"意味着"不能以这个身份做操作"，
> 而不是"不能访问整个网站"。**想清楚一条规则的边界，比一刀切地到处加检查更重要。**

```

**这是对之前那个 bug 的正面回应。** 上次的问题是：管理员能在数据库里填任何字符串当图标名，填错了构建不报错、页面一片空白。

这次的解法不是"再多加一道校验"，而是**从源头消灭出错的可能**：

| 方案 | 效果 |
| --- | --- |
| 校验 + 报错提示 | 填错了会被拦，但管理员还是得试几次 |

> **最好的错误处理是"让错误无法发生"，而不是"发生了再补救"。**

## 6.3 跨页面跳转带参数

```

**为此还给商品管理页补了一个"分类下拉筛选"**——原来只有关键词搜索，接不住 `categoryId` 参数。

> **做跨页面跳转时，一定要检查"目标页面能不能接住这些参数"。**
> 只写 `router.push` 不检查接收方，是很容易漏的一步。

而且 URL 上带着参数还有个好处：**管理员可以把 `/admin/product?categoryId=1` 这个链接直接发给同事**，对方打开就是同样的筛选结果。

## 6.4 菜单又多了两项

const menus = [
  { path: '/admin', title: '数据看板', icon: 'DataLine' },

注释也同步更新了：`后续每做完一个模块（举报处理、公告管理）再往这里加一行`。

**菜单和实际功能保持一致**——这是上一阶段定下的规矩，继续执行。

## 7.1 本阶段的安全设计

| 攻击手法 | 后果 | 防护 | 代码位置 |
| --- | --- | --- | --- |

| **禁用用户的旧 token 继续可用** | **封禁形同虚设，违规内容继续发** | **拦截器回查账号状态** | `AuthInterceptor` |
| token 里角色过期 | 已降权的用户仍能用管理员权限 | 角色以数据库为准 | `AuthInterceptor` |
| 删除有商品的分类 | 悬空引用、数据不一致 | 删除前检查引用数 | `AdminCategoryServiceImpl` |
| 分类重名 | 前台出现两个相同分类 | 服务层唯一性校验 | `AdminCategoryServiceImpl` |
| 图标名不存在 | 前台渲染空白 | 下拉框限定 + 渲染兜底 | `CategoryManage.vue` |
