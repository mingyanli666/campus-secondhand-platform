# 二、缺陷详情

## DEF-001 禁用用户后旧 token 仍然有效

| 字段 | 内容 |
| --- | --- |
| **严重级** | 严重（安全） |
| **模块** | 认证 / 权限 |
| **发现阶段** | 功能验证（做完"禁用用户"功能后主动验证） |
| **状态** | 已修复，已加回归用例 |

### 复现步骤

```
1. 用 zhangsan 正常登录，拿到 token A
2. 用 admin 登录，在用户管理里禁用 zhangsan
3. 用 token A 请求 GET /api/user/profile
```

### 实际结果

```
HTTP 200  ← 账号已被禁用，但请求依然成功
```

进一步验证发现：**不只是能看资料，还能发布商品、能下单**——等于"禁用"这个功能在最需要它的场景下完全失效。

### 预期结果

立即返回 2004「账号已被禁用」，最长不应该超过 token 的有效期（72 小时）。

### 根因分析

**JWT 是无状态的**——这是它的设计意图，也是这个缺陷的来源。

```
签发 token 时：服务器把 userId / role 编码进 token，用密钥签名
之后的每次请求：服务器只验证签名是否有效
```

服务器**不知道**签名之后账号发生了什么变化。管理员点"禁用"改的是数据库里的 `status` 字段，而 token 里根本没有这个信息，签名也依然有效。

```
时间线：
  T0  签发 token（有效期 72h）
  T1  管理员禁用账号
  T1~T72  旧 token 一路畅通  ← 缺陷区间
```

**为什么这个缺陷值得单独说**：它不是一个"忘了写 if"的低级错误，而是**技术选型带来的固有代价**。用 JWT 就一定会有这个问题，区别只是有没有意识到。

### 修复方案

在拦截器里回查数据库：

```java
// AuthInterceptor.preHandle
LoginUser loginUser = jwtUtil.parseToken(resolveToken(request));
if (loginUser == null) {
    throw new BusinessException(ResultCode.UNAUTHORIZED);
}

// 回库确认账号仍然可用
User user = userMapper.selectById(loginUser.getUserId());
if (user == null) {
    throw new BusinessException(ResultCode.UNAUTHORIZED);
}
if (!Constants.STATUS_ENABLED.equals(user.getStatus())) {
    throw new BusinessException(ResultCode.USER_DISABLED);
}
// 角色也以数据库为准：token 里的是"签发那一刻的快照"
loginUser.setRole(user.getRole());
```

**两个关键点**：

1. **不只看 status，角色也要回库取**。否则管理员给用户降权后，旧 token 里的 `role=ADMIN` 还能继续越权。
2. **代价是每个需登录的请求多一次主键查询**。这是有意的取舍：

| 方案 | 封禁是否立即生效 | 每请求成本 |
| --- | --- | --- |
| 只验签名（修复前） | ❌ 最长 72 小时 | 0 |
| **回查数据库（当前）** | ✅ 立即 | 1 次主键查询（亚毫秒） |
| 加短 TTL 缓存 | ✅ 有最多 N 秒延迟 | 内存读 |
| token 黑名单 | ✅ 立即 | 1 次 Redis 读 |

选了第二种：**正确性优先**，而且主键查询很便宜。
真到扛不住的量级，正确做法是上缓存，**而不是把这道检查砍掉**。

### 验证

```
禁用后立即用旧 token 请求  → 2004 ✓
公开接口（分类列表）仍然 200 ✓（@PublicApi 不查库）
```

### 回归用例

`AuthInterceptorTest` 3 个用例，其中一个是「禁用用户的旧 token 立即失效」。

### 经验

> **"功能实现了"和"功能有效"是两件事。**
> 写完"禁用用户"之后，我特意回过头去验证"禁用到底有没有用"，才发现这个问题。
> 如果当时点了一下按钮看到成功提示就收工，这个洞会一直留着。

## DEF-002 重新提交审核后驳回原因清不掉

| 字段 | 内容 |
| --- | --- |
| **严重级** | 中（数据一致性） |
| **模块** | 商品 |
| **发现阶段** | 手工回归 |
| **状态** | 已修复 |

### 复现步骤

```
1. admin 驳回商品 101，原因填「商品描述与实际不符」
2. zhangsan（卖家）编辑商品，改正描述后重新提交
3. 打开商品详情
```

### 实际结果

商品状态已经变回「待审核」，但页面上仍然挂着「驳回原因：商品描述与实际不符」。

### 预期结果

重新提交后驳回原因应该被清空——上一轮的结论不适用于新一轮审核。

### 根因分析

修复前是这样写的：

```java
exist.setRejectReason(null);
productMapper.updateById(exist);   // ← 这句不生效
```

**MyBatis-Plus 的 `updateById` 会跳过实体里为 null 的字段。**

这个特性本身是合理的（只更新变化的列，减少写入），但它导致了一件反直觉的事：
**你没法用 `updateById` 把某个字段改回 null**。

```java
// 生成的实际 SQL（修复前）
UPDATE biz_product SET title = ?, status = ?, update_time = ? WHERE id = ?
//                                 ↑ 没有 reject_reason，因为它被跳过了
```

### 修复方案

改用 `LambdaUpdateWrapper` **显式指定要写的字段**：

```java
productMapper.update(null, Wrappers.<Product>lambdaUpdate()
        .set(Product::getStatus, ProductStatus.PENDING.getCode())
        .set(Product::getRejectReason, null)        // ← 显式 set，null 也会写
        .set(Product::getUpdateTime, LocalDateTime.now())
        .eq(Product::getId, productId));
```

### 影响范围

这个坑在**三个地方**都存在，全部修了：

| 位置 | 场景 |
| --- | --- |
| `ProductServiceImpl.update` | 卖家编辑商品 |
| `ProductServiceImpl.resubmit` | 卖家重新提交审核 |
| `AdminProductServiceImpl.audit` | 管理员**审核通过**时（商品"已上架"却带着上次的驳回原因） |

**第三个最隐蔽**——审核通过时 `rejectReason` 应该清空，但因为同样用了 `updateById` 的思路，会出现"上架中"的商品带着驳回理由这种自相矛盾的数据。

### 验证

```sql
-- 驳回 → 编辑 → 重新提交
SELECT status, reject_reason FROM biz_product WHERE id = 101;
-- 期望：0 (待审核) | NULL
```

### 经验

> **框架的"便利特性"往往有一个反方向的代价。**
> `updateById` 跳过 null 字段，让 90% 的更新变简单了，
> 但剩下 10%「我要把字段改成 null」就必须换一种写法。
>
> 判断标准：**这个字段的业务语义里，"null"是不是一个有效值？**
> 是 → 必须用 `UpdateWrapper` 显式 set。

## DEF-003 商品已售出时举报处理整体失败

| 字段 | 内容 |
| --- | --- |
| **严重级** | 严重（业务逻辑） |
| **模块** | 举报 |
| **发现阶段** | 场景测试 |
| **状态** | 已修复 |

### 复现步骤

```
1. 某商品已经成交（状态 = 已售出）
2. 用户之前举报过它，举报仍在「待处理」
3. admin 处理这条举报，勾选「同时下架商品」
```

### 实际结果

```
HTTP 200  {"code":3002,"message":"只有在售商品才能强制下架"}
```

**整个举报处理失败**，举报状态没变、审核记录没写、卖家也没收到通知。

### 预期结果

举报应该处理成功。商品已经售出 = 本来就不在公开列表里 = **"让它不可见"这个目标已经达成了**，
下架这一步没有意义，但不该让整个流程失败。

### 根因分析

处理举报时复用了商品管理里现成的「强制下架」方法：

```java
// 举报处理（修复前）
if (needOffShelf) {
    adminProductService.forceOffShelf(adminId, adminName, productId, dto);  // ← 抛异常
}
```

而 `forceOffShelf` 里有一道**完全合理**的状态校验：

```java
if (!ProductStatus.ON_SALE.getCode().equals(product.getStatus())) {
    throw new BusinessException(ResultCode.PRODUCT_STATUS_ILLEGAL, "只有在售商品才能强制下架");
}
```

**这道校验站在商品管理的角度是对的**（防止把已售出的商品改成下架，造成数据矛盾）。
但站在举报处理的角度看，它变成了一个不该存在的失败点。

**两个场景对"前置条件"的预期不一样，而方法只有一个。**

### 修复方案

处理前先判断状态，已不在售就跳过这一步：

```java
boolean offShelfDone = false;
if (needOffShelf && ProductStatus.ON_SALE.getCode().equals(product.getStatus())) {
    adminProductService.forceOffShelf(...);
    offShelfDone = true;
}
```

**顺带发现并修了第二个问题**：通知文案里写死了「商品已被平台下架」，
但商品没被下架时这句话是失实的。改成用 `offShelfDone` 标志决定措辞：

```java
String action = offShelfDone ? "已被下架" : "已售出，无需下架";
notificationService.send(sellerId, SYSTEM, "举报处理结果",
        "你的商品「" + title + "」" + action + "。原因：" + reason, productId);
```

### 验证

| 商品状态 | 勾选同时下架 | 预期 |
| --- | --- | --- |
| 在售 | 是 | 处理成功 + 商品变下架 + 通知「已被下架」 |
| 已售出 | 是 | **处理成功** + 商品保持已售出 + 通知「已售出，无需下架」 |
| 已下架 | 是 | 处理成功 + 通知「已售出，无需下架」 |
| 任意 | 否 | 处理成功，不动商品 |

### 经验

> **调用一个有前置条件的方法之前，先问：这个前置条件在我这个场景下一定成立吗？**
>
> 复用是对的，但"复用"不等于"无脑调用"。
> 复用的代价是**把对方的约束也一起继承了**——包括那些在你的场景里并不成立的约束。
>
> 顺带还有一层：**异常一旦抛出，整个事务回滚**，
> 本来只是"下架这一步没必要做"，结果变成"举报处理整个失败"。

## DEF-004 上传图片后数据库存了 blob URL

| 字段 | 内容 |
| --- | --- |
| **严重级** | 高（功能不可用） |
| **模块** | 上传 / 前端 |
| **发现阶段** | 功能验证 |
| **状态** | 已修复 |

### 复现步骤

```
1. 登录后打开发布商品页
2. 上传一张图片
3. 页面显示上传成功、有缩略图
4. 提交发布 → 查看商品详情
```

### 实际结果

图片显示不出来。查数据库：

```sql
SELECT cover_image FROM biz_product WHERE id = 210;
-- blob:http://localhost:5173/8f3a-4b2c-...
```

**存进去的是浏览器的临时 blob 地址**，换个浏览器、刷新页面之后就失效了。

### 预期结果

```sql
-- /uploads/2026/10/0fbbaa2e8381422397b2bb5b3fc4221d.png
```

### 根因分析

前端的上传处理函数：

```js
// 修复前 —— 错误写法
async function handleUpload(options) {
  const url = await uploadImage(options.file)
  options.onSuccess(url)      // ← 手动调了一次
}
```

看起来没问题。但 `async` 函数**返回的是 Promise**，而 Element Plus 的 `el-upload`
检测到 Promise 之后，会**自己再调一次 `onSuccess`**：

```
① uploadImage 成功，返回 /uploads/xxx.png
② 手动调 onSuccess('/uploads/xxx.png')   → file.response = '/uploads/xxx.png'
③ async 函数结束，隐式 return undefined
④ Element Plus 看到 Promise 完成，调 onSuccess(undefined)
⑤ file.response 被覆盖成 undefined
⑥ 提交表单时拿到的图片地址是 —— 浏览器为预览生成的 blob: 地址
```

**两次回调，第二次把第一次的结果覆盖了。**

### 修复方案

**只返回 Promise，不手动调 `onSuccess`：**

```js
// 修复后
function handleUpload(options) {
  return uploadImage(options.file)
}
```

再加一层兜底，过滤掉不该入库的地址：

```js
.filter((url) => typeof url === 'string'
             && !url.startsWith('blob:')
             && !url.startsWith('data:'))
```

### 影响范围

**同一个 bug 在头像上传里也存在**，一起修了。

### 验证

```
上传 → 提交 → 查库 → cover_image 是 /uploads/... ✓
换浏览器打开详情页 → 图片正常显示 ✓
```

### 经验

> **"页面上看起来对了"是最危险的验证信号。**
> 缩略图能显示，是因为浏览器为 blob 生成了临时地址——**渲染成功和数据正确是两件事**。
>
> 这类问题的通用检查方法：**看落库的实际值，不看页面的表现。**
> 我做这个项目之后养成了一个习惯：涉及"保存"的功能，一定去数据库确认一遍存的是什么。

## DEF-005 非法路径参数返回 500 而不是 400

| 字段 | 内容 |
| --- | --- |
| **严重级** | 低（错误码规范） |
| **模块** | 全局异常处理 |
| **发现阶段** | 接口自检 |
| **状态** | 已修复 |

### 复现步骤

```
GET /api/product/abc        （id 应该是数字）
GET /api/nothing            （不存在的路由）
```

### 实际结果

```
GET /api/product/abc  →  HTTP 500  {"code":500,"message":"服务器内部错误"}
GET /api/nothing      →  HTTP 500
```

### 预期结果

```
GET /api/product/abc  →  400  「参数 id 格式不正确」
GET /api/nothing      →  404  「接口不存在」
```

### 根因分析

`GlobalExceptionHandler` 只处理了 `BusinessException`、参数校验异常和兜底的 `Exception`。
`MethodArgumentTypeMismatchException`（类型转换失败）和 `NoHandlerFoundException` 没有被单独处理，
**落进了兜底分支被当成"服务器内部错误"**。

### 发现的偶然性

这个缺陷是**被测试脚本意外暴露的**：

```powershell
# 测试脚本里用 $pid 做参数名
function Test-Api($pid) { ... }
#        ↑ $pid 是 PowerShell 的只读自动变量（当前进程 ID）
```

结果请求 URL 变成了空值/异常值，接口回了 500。本来以为是脚本问题，
顺手看了一眼状态码，才发现是后端把"参数错"报成了"服务器错"。

### 修复方案

```java
@ExceptionHandler(MethodArgumentTypeMismatchException.class)
public Result<Void> handleTypeMismatch(MethodArgumentTypeMismatchException e) {
    return Result.error(ResultCode.PARAM_ERROR,
            "参数 " + e.getName() + " 格式不正确");
}

@ExceptionHandler(NoHandlerFoundException.class)
public Result<Void> handleNotFound(NoHandlerFoundException e) {
    return Result.error(ResultCode.NOT_FOUND, "接口不存在：" + e.getRequestURL());
}
```

### 为什么这个"低"级别也要修

**500 是一个承诺**：它意味着"服务端出了我没想到的问题"。把它用在参数错误上，
会有两个后果：

1. **监控失真**：所有 5xx 都会触发告警，参数错误混在里面，真正的服务故障会被淹没
2. **排查成本**：前端看到 500 会以为是后端挂了，实际是自己传错了参数

### 经验

> **异常处理的价值不在于"不出错"，而在于"出错时能不能一眼看出是谁的问题"。**
> 400 / 401 / 403 / 404 / 500 这几个码的边界划清楚，排查效率差别很大。

页面上所有中文变成 `æ‰‹æœº` 这种样子，
但**代码里写死的字符串（如"操作成功"）是正常的**。

### 根因分析

**"常量正常、数据库读出来的乱码"这个对比就是突破口** —— 问题在数据落库时的字符集。

```sql
SELECT HEX(name) FROM sys_category WHERE id = 1;
-- 本机 MySQL：E6898BE69CBA                    ← 正确
-- 容器 MySQL：C3A6E280B0E280B9C3A6C593C2BA    ← 乱码
```

坏掉的那串把每个字节都重新编码了一遍，`0x89 → ‰`、`0x8B → ‹`、`0x9C → œ`
—— **这是 CP1252 的映射表**。而 **MySQL 的 `latin1` 实际就是 CP1252**。

官方镜像的 entrypoint 执行 init SQL 时调用的客户端没有指定字符集：

```bash
mysql --defaults-extra-file=<(...) --protocol=socket -uroot -hlocalhost --comments
#                                                                ↑ 没有 --default-character-set
```

客户端默认字符集从 locale 推导，容器里不设 locale 就退回 latin1。

### 修复

```yaml
mysql:
  environment:
    LANG: C.UTF-8
```

**改完必须 `docker compose down -v` 重建** —— initdb 只在数据目录为空时执行。

### 一个走不通的方案

挂 `.cnf` 配置文件：

```
[Warning] World-writable config file '/etc/mysql/conf.d/charset.cnf' is ignored.
```

Windows 绑定挂载的文件权限是 `0777`，MySQL 出于安全拒绝加载，加 `:ro` 也没用。

### 经验

> **这个缺陷在本地开发时永远不会出现。**
> 开发机上 MySQL 是按 README 里的 `--default-character-set=utf8mb4` 导入的，一直是好的。
> 只有走容器初始化这条路径才会触发。
>
> **换一条入口路径，就等于换了一套默认值。** 部署验证不能省。

## DEF-007 Prettier 拆分内联事件导致构建失败

| 字段 | 内容 |
| --- | --- |
| **严重级** | 中（构建中断） |
| **模块** | 工具链 |
| **发现阶段** | 构建验证 |
| **状态** | 已修复 |

### 复现步骤

```
1. 引入 Prettier，配置 semi: false（与原有代码风格一致）
2. npx prettier --write .
3. npm run build
```

### 实际结果

```
[vite:vue] src/views/admin/ProductManage.vue (312:23):
Error parsing JavaScript expression: Unexpected token, expected "," (3:16)
```

构建直接失败。

### 预期结果

格式化不应该改变代码语义。

### 根因分析

原来有三处这样的写法：

```vue
<el-button @click="detailVisible = false; openAudit(currentRow, true)">
```

Prettier 处理这个内联表达式时做了两件事：

```
① 按 semi: false 的规则去掉分号
② 因为行太长，把它拆成多行

结果：
@click="
  detailVisible = false
  openAudit(currentRow, true)
"
```

**两条语句失去了分隔符，变成语法错误。**

### 为什么很难发现

```
ESLint          ✅ 通过
Prettier        ✅ 通过（它就是自己改的）
单元测试        ✅ 通过（测的是 script 部分）
生产构建        ❌ 失败
```

**三个工具都说没问题，只有真的 build 一次才暴露。**

### 修复方案

抽成具名函数（多语句内联处理器本来就不该这么写）：

```js
function auditFromDrawer(pass) {
  detailVisible.value = false
  openAudit(currentRow.value, pass)
}
```

```vue
<el-button @click="auditFromDrawer(true)">
```

### 经验

> **工具链的改动必须用"最终产物"验证，不能只看工具自己的检查。**
>
> 这件事之后，我在 CI 里加了 `smoke` 任务：真的把服务拉起来。
> 因为"lint 通过 + 测试通过"并不等于"能跑"。

它们全都出现在"非正常路径"上：

- 禁用之后**还继续用旧 token**
- 驳回之后**再修改重新提交**

- 上传之后**去看数据库存了什么**
- 传一个**类型不对**的参数
- **换一条路径**（容器）部署
- **真的构建一次**

## 3.2 按根因类型

| 根因类型 | 数量 | 缺陷 | 特征 |
| --- | --- | --- | --- |

**3/7 属于"框架特性"类** —— 这类缺陷的共性是：

# 四、从缺陷看测试策略

## 4.1 这 7 个缺陷教给我的四件事

### ① 写完一个功能，要验证它真的"生效"

DEF-001 是写完"禁用用户"之后回头验证才发现的。
**"按钮点了有成功提示"不等于"功能真的起作用了"。**

### ② 看落库的值，不看页面的表现

DEF-004 里页面上缩略图显示得好好的，数据库里存的却是临时地址。
**渲染成功 ≠ 数据正确。**

### ③ 复用别人的方法，要继承他的约束

DEF-003 复用了 `forceOffShelf`，连带继承了"只有在售才能下架"这个约束——
而这个约束在举报场景里并不成立。

### ④ 换一个环境，就换了一套默认值

DEF-006 只在容器里出现，本地永远是好的。
**部署验证不能靠"我本地跑过"。**

## 4.2 对应的用例补充

每个缺陷修完都要补一条**回归用例**，否则同样的坑还会再踩：

| 缺陷 | 补的用例 |
| --- | --- |
| DEF-001 | `AuthInterceptorTest` - 禁用用户的旧 token 立即失效 |
| DEF-002 | `ProductServiceImplTest.resubmit_from_rejected_clears_reason` |
| DEF-003 | `AdminProductServiceImplTest.forceOffShelf_requires_on_sale` + 场景用例 |
| DEF-004 | 手工验证 + 数据库检查（前端无自动化覆盖） |
| DEF-005 | 接口自检 TC-EDGE-003 / 004 |
| DEF-006 | 容器冒烟：`docker compose up --wait` + 中文接口校验 |
| DEF-007 | CI 的 `smoke` 任务（真的构建 + 启动） |

## 4.3 面试怎么讲

被问到"你发现过什么 bug"时，**不要只讲现象，要讲这三层**：

```
① 现象和复现路径      —— 证明你真的遇到过
② 根因（为什么会出现） —— 证明你理解背后的机制
③ 修复和取舍          —— 证明你会做工程判断
```

以 DEF-001 为例：

> "做禁用用户功能的时候，我写完特意去验证'禁用到底有没有用'，
> 结果发现被禁用的账号拿着旧 token 还能正常发帖。
>
> 根因是 JWT 无状态——服务器只验签名，不知道签发之后账号状态变了。
>
> 修复是在拦截器里回查一次数据库，同时把角色也从数据库取，
> 因为 token 里的角色是签发那一刻的快照，管理员降权后旧 token 还是会越权。
> 代价是每个请求多一次主键查询，我评估过可以接受——
> 真要优化应该加缓存，而不是把这道检查砍掉。"

**这个回答里有：主动验证的意识、对技术选型代价的理解、明确的取舍。**
比"我修了一个 bug"有价值得多。

# 五、缺陷记录模板

> 记录缺陷的价值在于**让没参与的人也能复现和判断**。下面是本项目用的模板。

```markdown
## DEF-XXX 一句话说清问题

| 字段 | 内容 |
| --- | --- |
| 严重级 | 严重 / 高 / 中 / 低 |
| 模块 | 商品 / 订单 / 认证 ... |
| 发现阶段 | 功能验证 / 场景测试 / 回归 / 部署验证 |
| 状态 | 待确认 / 修复中 / 已修复 / 已关闭 |
| 关联用例 | TC-XXX-001 |

### 复现步骤
1.
2.
3.

### 实际结果
（贴实际输出 / 截图 / SQL 结果）

### 预期结果
（明确写"应该是什么"，不要写"不正常"）

### 根因分析
（为什么会出现 —— 这一栏最重要，没有它这条记录就没有价值）

### 修复方案
（改了什么、为什么这么改、有没有别的方案）

### 验证方式
（怎么确认真的修好了）

### 回归用例
（补了哪条自动化）
```

## 几个写作要求

| 要求 | 原因 |
| --- | --- |
| **预期结果必须具体** | 写"应该正确"等于没写；要写"返回 400 且提示参数格式不正确" |
| **根因要写到机制层** | "因为用了 updateById"不够，要写"updateById 跳过 null 字段，所以 set 为 null 不生效" |
| **修复要写取舍** | 只说"我改了"看不出工程判断 |
| **必须写回归用例** | 否则同样的坑还会再踩，而且没人知道曾经踩过 |
| **附上实际输出** | 日志/SQL 结果/截图，比描述可信 |
