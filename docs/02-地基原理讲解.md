# 一、全局视角：一个请求的完整一生

在讲任何代码之前，先在大脑里装下这张图。所有 Web 项目都是这个骨架：

```
【浏览器】用户点击"登录"
    ↓ axios.post('/api/auth/login', {username, password})
【Vite 开发服务器】localhost:5173 —— 发现路径是 /api 开头，代理转发
    ↓
【Tomcat】localhost:8080 —— 收到 HTTP 请求，转成 HttpServletRequest 对象
    ↓
【DispatcherServlet】Spring MVC 的总调度，根据 URL 找到 AuthController.login()
    ↓
【拦截器 AuthInterceptor】检查 token（登录接口标了 @PublicApi，放行）
    ↓
【Controller】接参数、做校验（@Valid）
    ↓
【Service】写业务逻辑（查用户名、比对密码、生成 token）
    ↓
【Mapper】MyBatis-Plus 生成 SQL 发给 MySQL
    ↓
【MySQL】查数据，返回结果
    ↑ 反过来一路包装成 Result → 序列化成 JSON → 返回浏览器
【浏览器】axios 拦截器剥掉外壳 → 存 token 到 localStorage → 跳转首页
```

**关键认知**：后面写的每一个功能，都只是在这条链路的某一环里加代码。
骨架搭对了，你只需要关心"业务逻辑"那一环。

# 二、后端骨架

目录结构（`backend/src/main/java/com/digital/platform/`）：

```
controller/   ← 只负责"收请求、发响应"
service/      ← 只负责"业务规则"
mapper/       ← 只负责"和数据库说话"
entity/       ← 数据库表的 Java 映射
dto/          ← 前端传进来的数据
vo/           ← 返回给前端的数据
common/       ← 所有人都要用的公共件
config/       ← 一次性配置
security/     ← 鉴权相关
```

## 2.1 为什么分层？不分层不行吗

**不行。** 如果把所有代码写在一个类里，一个月后要加个"登录失败 5 次锁定账号"的功能，
就得在几百行代码里找密码比对那一段，改错还影响别的功能。

分层的本质是**职责分离**。看 `controller/AuthController.java`：

```java
@PostMapping("/login")
public Result<LoginVO> login(@Valid @RequestBody LoginDTO dto) {
    return Result.success("登录成功", userService.login(dto));
}
```

只有三行。Controller 完全不知道密码怎么校验、token 怎么生成。
它只做两件事：把请求转成 DTO，把结果转成 Result。

**实际好处**：以后加"登录失败锁定"，只改 Service，Controller 一行不动。
这叫**低耦合**，是需求里"可拓展性良好"的技术落地。

## 2.2 统一返回格式 Result：为什么每个接口都包一层

如果有的接口返回 `{"id":1}`，有的返回 `"成功"`，有的抛异常返回 HTML 错误页，
前端就要写无数 if-else 猜"这次到底成没成功"。

有了 `Result`，前端的判断逻辑就**永远只有一条**（在 `utils/request.js` 里）：

```javascript
if (res.code === 200) {
  return res.data        // 成功，剥掉外壳
}
ElMessage.error(res.message)  // 失败，统一弹提示
```

`common/result/ResultCode.java` 更进一步：把"账号已被注册"这类提示语集中管理，
**改文案只改一处**。

## 2.3 全局异常处理：try-catch 的终结者

看 `service/impl/UserServiceImpl.java` 的 `login()`，它**一处 try-catch 都没有**：

```java
if (user == null || !BCrypt.checkpw(dto.getPassword(), user.getPassword())) {
    throw new BusinessException(ResultCode.USERNAME_OR_PASSWORD_ERROR);
}
```

它直接 `throw`。因为 `common/exception/GlobalExceptionHandler.java` 上挂着
`@RestControllerAdvice`，像一张网兜住所有 Controller 抛出的异常：

```java
@ExceptionHandler(BusinessException.class)
public Result<Void> handleBusinessException(BusinessException e) {
    return Result.fail(e.getCode(), e.getMessage());
}
```

**这就是业务代码能写得这么干净的原因**：只管"条件不满足就抛异常"，
怎么变成 JSON 返回是全局处理器的事。

它接管的异常类型：

| 异常 | 触发场景 | 处理方式 |
| --- | --- | --- |
| `BusinessException` | 自己抛的业务错误 | 原样返回 code 和 message |
| `MethodArgumentNotValidException` | `@Valid` 校验失败 | 拼接所有字段错误，返回 400 |
| `BindException` | 表单/查询参数校验失败 | 同上 |
| `ConstraintViolationException` | 方法级 `@Validated` 失败 | 同上 |
| `MaxUploadSizeExceededException` | 上传文件过大 | 返回 6003 |
| `Exception` | 兜底 | 打印完整堆栈，返回"服务器开小差了" |

最后那个兜底最重要：**哪怕代码有 bug 崩了，用户看到的也是友好提示，
而不是一页 Java 堆栈**。这就是需求里"容错性良好"。

## 2.4 鉴权：JWT 到底是什么

### 2.4.1 传统 Session 方案为什么不行

Session 方案：登录成功后服务器在内存里存 `{sessionId: "abc123", userId: 1}`，
给浏览器一个 Cookie 存 sessionId。下次请求带 Cookie，服务器查内存"这是谁"。

问题：

- 服务器重启 → 内存清空 → **所有人掉线**
- 用户多了 → 服务器内存压力大
- 部署两台机器负载均衡 → 用户在 A 机登录，请求分到 B 机 → **B 机不认识他**

### 2.4.2 JWT 的思路：把身份"签在票上"

核心思想：**不用服务器记，把身份信息写在令牌里，然后用密钥盖章防伪。**

`security/JwtUtil.java` 的 `generateToken()`：

```java
Jwts.builder()
    .subject(String.valueOf(userId))      // 用户ID
    .claim("username", username)          // 账号
    .claim("role", role)                  // 角色
    .issuedAt(now)                        // 签发时间
    .expiration(new Date(now + expire))   // 过期时间
    .signWith(key())                      // 【关键】用密钥签名
    .compact();
```

生成的 token 用 `.` 分成三段：

```
eyJhbGciOiJIUzM4NCJ9 . eyJzdWIiOiIxIiwidXNlcm5hbWUiOiJhZG1pbiJ9 . yUEnysc9yXiQzssUT5HVODvcX...
      头部                        载荷（用户信息）                            签名
```

**注意**：中间那段只是 Base64 编码，**不是加密**！任何人都能解开看到
`{"sub":"1","username":"admin","role":"ADMIN"}`。

安全性靠**第三段的签名**。签名用 `application.yml` 里的 `platform.jwt.secret` 算出。
别人想改载荷里的 `role`（USER → ADMIN），必须用同样密钥重算签名——
**他不知道密钥，改完签名就对不上**。

### 2.4.3 拦截器：请求进门的第一道关卡

`security/AuthInterceptor.java` 的 `preHandle()`，每次请求都会先跑：

```java
// 1. 跨域预检请求（OPTIONS）放行
if ("OPTIONS".equalsIgnoreCase(request.getMethod())) return true;

// 2. 标了 @PublicApi 的接口放行（登录、注册、商品列表）
if (isPublic) { ... return true; }

// 3. 解析 token，失败抛 401
LoginUser loginUser = jwtUtil.parseToken(resolveToken(request));
if (loginUser == null) throw new BusinessException(ResultCode.UNAUTHORIZED);

// 4. 用户存入 ThreadLocal，业务层随时能取
UserContext.set(loginUser);

// 5. 接口标了 @RequireRole(ADMIN) 且当前不是 ADMIN → 抛 403
```

### 2.4.4 ThreadLocal 和"串号"坑（重点）

`security/UserContext.java`：

```java
private static final ThreadLocal<LoginUser> HOLDER = new ThreadLocal<>();
```

**ThreadLocal 是"每个线程各自独立的储物柜"。** Tomcat 处理每个请求用一个独立线程：

- 请求 A 进来 → 线程 1 把自己的用户存进自己的柜子
- 请求 B 同时进来 → 线程 2 存进自己的柜子
- **两个请求互不干扰**，不需要在每个方法里层层传 `userId` 参数

Service 里就能直接 `UserContext.userId()` 拿到当前登录用户，
看着像"全局变量"，实际线程安全。

**但有个大坑**：Tomcat 线程是**复用**的。线程 1 处理完请求 A 不销毁，
而是等待处理下一个请求 C。如果不清空柜子，请求 C 会读到请求 A 的用户信息——
**张三的操作记到了李四头上**。

所以 `afterCompletion` 必须清理：

```java
public void afterCompletion(...) {
    UserContext.clear();   // 内部是 HOLDER.remove()
}
```

这是线上事故级的问题，面试也爱问。

### 2.4.5 @PublicApi 和 @RequireRole：用注解表达意图

传统做法是在配置里维护一长串"不需要登录的路径"，**新增接口时容易忘记加**。

注解方式是**就地声明**：

```java
@PublicApi                    // 这个接口公开
@PostMapping("/login")
public Result<LoginVO> login(...) { }
```

拦截器用 `AnnotatedElementUtils.hasAnnotation()` 检查方法上有没有这个注解。
**看代码就知道权限要求，不会忘。**

`@RequireRole(RoleType.ADMIN)` 同理，管理后台所有接口都会标上它。
普通用户即使带合法 token 访问也会被拦到 403 —— **这就是"杜绝越权操作"的技术实现**。

## 2.5 配置体系：application.yml 是怎么变成 Java 对象的

**第一类：框架自己的配置**，Spring Boot 自动识别：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/used_digital_platform
```

这些 key 是 Spring Boot 约定好的，内部有对应自动配置类会读。

**第二类：自定义配置**，需要手动映射 —— `config/PlatformProperties.java`：

```java
@Data
@Component
@ConfigurationProperties(prefix = "platform")
public class PlatformProperties {
    private Jwt jwt = new Jwt();
    private File file = new File();
    private Cors cors = new Cors();

    @Data
    public static class Jwt {
        private String secret;
        private Integer expireHours = 72;
    }
}
```

`@ConfigurationProperties(prefix = "platform")` 把 yml 里 `platform.jwt.secret`
自动塞进 `properties.getJwt().getSecret()`。

**为什么用配置类而不是到处写 `@Value`？**

- 集中在一处，加字段只改这里
- IDE 有自动补全和类型检查
- yml 里一眼能看到有哪些配置项

`JwtUtil` 通过构造器注入拿到它（`@RequiredArgsConstructor` 自动生成构造器，Lombok 的功劳）。

# 三、数据库是怎么连上的

数据库连接是最容易出错、也最值得理解的部分。分四步。

## 第 1 步：JDBC —— Java 和数据库的"通用插头"

Java 不能直接跟 MySQL 说话，中间需要标准接口：**JDBC**（Java Database Connectivity）。
MySQL 官方提供驱动实现，就是 `pom.xml` 里的：

```xml
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>
```

`scope=runtime` 表示：编译时不需要（只调用 JDBC **标准接口**），运行时才需要（干活的是它）。

**不用 Spring 的话要这么连接：**

```java
Class.forName("com.mysql.cj.jdbc.Driver");
Connection conn = DriverManager.getConnection(url, username, password);
PreparedStatement ps = conn.prepareStatement("SELECT * FROM sys_user WHERE username = ?");
ps.setString(1, "admin");
ResultSet rs = ps.executeQuery();
while (rs.next()) { ... }
rs.close(); ps.close(); conn.close();   // 还要记得关！
```

每个查询都写这一堆是灾难，所以有了下一步。

## 第 2 步：连接池 HikariCP —— 为什么不能每次新建连接

`DriverManager.getConnection()` 每次都**真正建立 TCP 连接**，
走网络握手 + MySQL 认证，耗时几十毫秒。高并发下 1000 个请求建 1000 条连接，
MySQL 直接拒绝。

**连接池思路**：启动时先建好一批连接放着，用的时候借一条，用完还回去，不销毁重建。

`application.yml` 里的配置：

```yaml
spring:
  datasource:
    hikari:
      minimum-idle: 5            # 最少保持 5 条空闲连接
      maximum-pool-size: 20      # 最多 20 条
      connection-timeout: 30000  # 借不到连接时最多等 30 秒
      max-lifetime: 1800000      # 连接最长活 30 分钟（防止 MySQL 先断）
```

**Spring Boot 自动做了这些**：检测到 classpath 上有 HikariCP 和 MySQL 驱动，
就自动创建 `DataSource`（数据源 = 连接池）Bean，配置来自 `spring.datasource.*`。
**不用写一行 Java 代码** —— 这就是"约定优于配置"。

## 第 3 步：MyBatis-Plus 是怎么接管数据库的

### 机制一：自动配置 SqlSessionFactory

`mybatis-plus-spring-boot3-starter` 里的自动配置类会：

1. 从 Spring 容器找到上一步的 `DataSource`
2. 读 `application.yml` 里 `mybatis-plus.*` 配置
3. 创建 `SqlSessionFactory` —— MyBatis 的核心工厂，负责生产"能执行 SQL 的会话"

### 机制二：@MapperScan + 动态代理（最神奇的一点）

启动类：

```java
@SpringBootApplication
@MapperScan("com.digital.platform.mapper")
public class DigitalPlatformApplication { }
```

`mapper/UserMapper.java`：

```java
@Mapper
public interface UserMapper extends BaseMapper<User> {
    // 里面一行代码都没有！
}
```

**一个没有实现类的接口，为什么能调用 `userMapper.selectById(1)`？**

答案是 **JDK 动态代理**。`@MapperScan` 启动时扫描到接口，
MyBatis 在内存里动态生成实现类（代理对象）注册到 Spring 容器。
调用时实际执行代理逻辑：

```
1. 判断方法名是 selectById（MyBatis-Plus 内置方法）
2. 根据 @TableName("sys_user") 知道表名
3. 根据 @TableId 知道主键是 id
4. 拼 SQL: SELECT id, username, ... FROM sys_user WHERE id = ? AND deleted = 0
5. 交给 JDBC 执行
6. 把 ResultSet 每列按 map-underscore-to-camel-case 映射成 User 属性
7. 返回 User 对象
```

**这就是 BaseMapper 不写 SQL 就能增删改查的原因。**
复杂查询（多表关联、统计）再手写 SQL 或用 QueryWrapper。

### 机制三：插件拦截 SQL

`config/MybatisPlusConfig.java` 注册的插件在 **SQL 执行前**拦截并改写：

```java
// 分页插件：调 page(1, 10)，自动加 LIMIT 0,10 并自动执行 COUNT 查询
interceptor.addInnerInterceptor(pagination);

// 防全表攻击：没有 WHERE 的 UPDATE/DELETE 直接报错拦截
interceptor.addInnerInterceptor(new BlockAttackInnerInterceptor());
```

分页插件价值很大：**没有它要手写 `LIMIT` 和 `COUNT(*)` 两条 SQL**，
换数据库语法还不一样。有了它只写 `new Page<>(1, 10)`。

### 顺带说说逻辑删除

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: deleted      # 逻辑删除字段叫 deleted
      logic-delete-value: 1            # 删了置为 1
      logic-not-delete-value: 0        # 没删是 0
```

只要实体里有 `deleted` 字段（比如 `Product`）：

- `deleteById(5)` → 实际执行 `UPDATE biz_product SET deleted = 1 WHERE id = 5`
- `selectById(5)` → 实际执行 `SELECT ... WHERE id = 5 AND deleted = 0`

**数据永远不会真的消失**，满足需求里"所有发布信息可全程追溯"。

> **注意**：`User` 实体**故意没有 `deleted` 字段**。
> 因为用户表有 `username` 唯一索引，如果用户做逻辑删除，
> 删掉后同名的账号再注册就会撞唯一索引。所以用户改用 `status`（1 正常 / 0 禁用）控制。

## 第 4 步：一条请求的完整数据流

以"登录时查用户"为例：

```
UserServiceImpl.login()
  └─ userMapper.selectOne(Wrappers.<User>lambdaQuery().eq(User::getUsername, "admin"))
       ↓
     【动态代理拦截】
       ↓
     MyBatis 拼 SQL: SELECT id,username,password,... FROM sys_user
                     WHERE username = ? AND deleted = ?
                                            ↑ User 没有 deleted 字段，不追加
       ↓
     【分页插件等拦截器】本次无额外改写
       ↓
     MyBatis 向连接池要一条连接 → HikariCP 给一条空闲连接
       ↓
     JDBC PreparedStatement 把 "admin" 填进 ? 占位符（预编译，防 SQL 注入）
       ↓
     【MySQL】执行，返回结果集
       ↓
     MyBatis 映射结果集 → User 对象（username→username, credit_score→creditScore）
       ↓
     归还连接到 HikariCP
       ↓
     返回 User 对象给 Service
```

> **排查问题的第一手段**：每执行一次查询控制台都会打印 SQL
> （因为配了 `log-impl: StdOutImpl`）。接口返回不对时，先看 SQL 有没有问题。

# 四、前端骨架：Vue 3 是怎么跑起来的

## 4.1 为什么要有"前端工程"

传统写法每个页面一个 `.html`，改个导航栏要改 20 个文件。

现代前端工程的核心是**组件化**：把页面拆成可复用的积木。
`layout/UserLayout.vue` 就是"顶部导航 + 内容区 + 页脚"这块积木，
所有页面嵌在它的内容区里。

## 4.2 main.js：应用的启动装配

```javascript
const app = createApp(App)

// 全局注册 Element Plus 图标，模板里能直接 <el-icon><Search /></el-icon>
for (const [name, component] of Object.entries(ElementPlusIconsVue)) {
  app.component(name, component)
}

app.use(createPinia())                   // 状态管理
app.use(router)                          // 路由
app.use(ElementPlus, { locale: zhCn })   // UI 组件库，中文
app.mount('#app')                        // 挂载到 index.html 的 <div id="app">
```

> **注意顺序**：`createPinia()` 必须在 `router` 之前。
> 因为路由守卫里要读 `useUserStore()`，Pinia 没装就报错。初学者常踩这个坑。

## 4.3 路由：URL 和组件的对应关系

`router/index.js` 维护映射表：

```javascript
{ path: '/login', component: () => import('@/views/user/Login.vue') }
```

`() => import(...)` 是**懒加载**：只有真的访问 `/login`，浏览器才下载该组件代码。
好处是首页加载更快。

### 路由守卫：拦截的关口

```javascript
router.beforeEach((to) => {
  const userStore = useUserStore()

  if (to.meta.requiresAuth && !userStore.isLogin) {
    ElMessage.warning('请先登录')
    return { path: '/login', query: { redirect: to.fullPath } }
  }
  if (to.meta.requiresAdmin && !userStore.isAdmin) {
    return { path: '/' }
  }
})
```

`to.meta` 是路由上挂的自定义信息：

```javascript
{ path: '/publish', component: ..., meta: { requiresAuth: true } }
```

> **重要**：前端拦截只是为了体验，**不是安全**。
> 懂技术的人可以直接调接口绕过前端。真正的防线永远是后端的 `AuthInterceptor`。
> **前端拦截 + 后端校验，两层都要有。**

`query: { redirect: to.fullPath }` 是贴心设计：用户访问"我的收藏"被拦到登录页，
登录成功后自动回到"我的收藏"，而不是跳到首页。

## 4.4 Pinia：为什么需要"状态管理"

**问题场景**：导航栏要显示用户名，个人中心也要显示，商品列表可能还要用。
每个组件自己查一遍就重复了；靠父子组件传参，跨好几层又很麻烦。

Pinia 提供的是一块**全局共享内存**：

```javascript
export const useUserStore = defineStore('user', () => {
  const token = ref(localStorage.getItem('udp_token') || '')
  const userInfo = ref(JSON.parse(localStorage.getItem('udp_user') || 'null'))

  const isLogin = computed(() => !!token.value)

  async function doLogin(form) {
    const data = await userApi.login(form)
    token.value = data.token
    userInfo.value = data.userInfo
    localStorage.setItem('udp_token', data.token)   // 持久化
  }
})
```

任何组件里 `const userStore = useUserStore()` 拿到的都是**同一份数据**。
`token` 变了，所有用到它的地方自动更新 —— 这就是 Vue 的**响应式**。

- `ref()` 包起来的值，`.value` 一改 Vue 就知道要重新渲染
- `computed()` 是派生值，`token` 变了 `isLogin` 自动重算
- `localStorage` 解决"刷新页面状态丢失"：下次打开从里面读回来，不用重新登录

## 4.5 request.js：axios 封装（前端最核心的公共件）

**请求拦截器 —— 出门前自动带 token：**

```javascript
service.interceptors.request.use((config) => {
  const userStore = useUserStore()
  if (userStore.token) {
    config.headers.Authorization = `Bearer ${userStore.token}`
  }
  return config
})
```

没有这一步，每个接口都要手写 `headers`，忘一个就 401。

**响应拦截器 —— 统一剥壳和错误处理：**

```javascript
service.interceptors.response.use((response) => {
  const res = response.data
  if (res.code === 200) return res.data                  // 成功，直接给 data
  if (res.code === 401) { handleUnauthorized(); ... }    // 登录失效
  ElMessage.error(res.message || '操作失败')              // 业务错误自动弹提示
  return Promise.reject(new Error(res.message))
})
```

因为有它，业务代码才这么干净：

```javascript
await userStore.doLogin(form)     // 不需要判断 code
ElMessage.success('登录成功')      // 不需要弹错误提示
```

> **细节**：`isLoggingOut` 标志位。页面同时发 5 个请求都 401 时，
> 没有它会弹 5 个"登录已失效"弹窗。这类"并发去重"实际项目必须考虑。

## 4.6 Vite 是干什么的

**问题一**：浏览器不认识 `.vue` 文件，也不认识 `@/` 路径别名，Vite 负责转换。

**问题二**：跨域。前端 `5173`，后端 `8080`，浏览器同源策略会阻止跨域请求。
Vite 代理解决：

```javascript
proxy: {
  '/api': { target: 'http://localhost:8080', changeOrigin: true }
}
```

原理：浏览器请求 `localhost:5173/api/auth/login`，
**Vite 服务器在 Node.js 层面转发**给 `localhost:8080`。
服务器之间通信不受浏览器同源策略限制。

> 这只是开发环境的便利。后端 `config/WebMvcConfig.java` 里也配了 CORS
> （`addCorsMappings`），那是为了打包部署后不走代理的场景。**两套并存是常见做法。**

# 五、把前后端串起来看：一次登录的全景

| 阶段 | 前端 | 后端 |
| --- | --- | --- |
| 1. 用户输入 | `Login.vue` 的 `form.username/password` | — |
| 2. 表单校验 | Element Plus 的 `rules` 前端先拦一道 | — |
| 3. 发请求 | `userStore.doLogin()` → `request.js` 请求拦截器 | — |
| 4. 跨域 | Vite 代理转发 `/api` → `8080` | — |
| 5. 收请求 | — | Tomcat → `DispatcherServlet` → 匹配 `AuthController.login` |
| 6. 权限 | — | `AuthInterceptor` 看到 `@PublicApi`，放行 |
| 7. 参数校验 | — | `@Valid @RequestBody LoginDTO` 触发注解校验，失败抛异常 |
| 8. 业务 | — | `UserServiceImpl.login()`：查用户 → BCrypt 比对 → 生成 JWT |
| 9. 数据库 | — | `UserMapper` 动态代理 → MyBatis 生成 SQL → HikariCP → MySQL |
| 10. 返回 | — | `Result.success(data)` → Jackson 序列化成 JSON |
| 11. 收响应 | `request.js` 响应拦截器：`code===200` → 返回 `data` | — |
| 12. 存状态 | `userStore` 存 token 和用户信息到内存 + localStorage | — |
| 13. 跳转 | `router.push('/')`，路由守卫放行 | — |
| 14. 渲染 | `UserLayout` 读 `userStore.nickname` 显示用户名 | — |
