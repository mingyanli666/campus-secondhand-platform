# 第一部分：整体地图

## 1.1 新增了什么

```
后端（20 个新文件）
├── 枚举        2 个：AuditAction（审核动作）/ NotificationType（通知类型）
├── 实体        2 个：AuditRecord（审核记录）/ Notification（站内通知）
├── Mapper      2 个：AuditRecordMapper / NotificationMapper
├── DTO         2 个：AuditDTO / ForceOffShelfDTO
├── VO          3 个：AuditRecordVO / NotificationVO / DashboardVO
├── 审核业务    2 个：AdminProductService(+Impl)
├── 通知业务    2 个：NotificationService(+Impl)
├── 看板业务    2 个：AdminDashboardService(+Impl)
└── 控制器      3 个：AdminProductController / AdminDashboardController / NotificationController

前端（6 个新文件）
├── 接口封装    2 个：api/admin.js / api/notification.js
├── 布局        1 个：layout/AdminLayout.vue
├── 页面        2 个：views/admin/{Dashboard,ProductManage}.vue
└── 组件        1 个：components/NotificationBell.vue
```

## 1.2 这一阶段解决了什么

上一阶段结束时，业务流程是**断的**：

```
卖家发布 ──► 待审核 ──► ✗ 没人处理，商品永远上不了架
```

这一阶段把断点接上了：

```
卖家发布 ──► 待审核 ──► 管理员审核 ──┬──通过──► 已上架 ──► 出现在商品列表
                                     │
                                     └──驳回──► 审核驳回 ──► 卖家收到通知
                                                              │
                                                              └──修改后重新提交──┐
                                                                                 │
                                                        ◄────────────────────────┘
```

**这就是需求里说的"业务闭环完整"。** 一个流程如果中间有一环只能靠人去数据库里改，那它就不是闭环。

## 1.3 三个新概念

| 概念 | 作用 | 对应文件 |
| --- | --- | --- |
| **审核留痕** | 记录"谁、什么时候、对什么、做了什么决定、为什么" | `biz_audit_record` |
| **站内通知** | 把平台的决定主动推给用户 | `sys_notification` |
| **角色隔离** | 管理端接口和用户端接口彻底分开 | `@RequireRole` |

# 第二部分：权限入口 —— 管理端与用户端怎么隔开

这是整个后台的**命门**。如果这一层做错了，后面写再多功能都是白费。

## 2.1 一行注解保护整个模块

```java
@Tag(name = "06-管理后台·商品审核")
@RestController
@RequestMapping("/api/admin/product")
@RequireRole(RoleType.ADMIN)          // ← 就这一行
@RequiredArgsConstructor
public class AdminProductController {
```

`@RequireRole` 加在**类**上，这个 Controller 里的所有接口就都只对管理员开放。

## 2.2 拦截器是怎么找到这个注解的

回看第一阶段的 `AuthInterceptor.preHandle()`：

```java
// 先查方法，再查类
RequireRole requireRole = AnnotatedElementUtils.findMergedAnnotation(handlerMethod.getMethod(), RequireRole.class);
if (requireRole == null) {
    requireRole = AnnotatedElementUtils.findMergedAnnotation(handlerMethod.getBeanType(), RequireRole.class);
}
if (requireRole != null) {
    boolean allowed = Arrays.stream(requireRole.value())
            .anyMatch(role -> role.getCode().equals(loginUser.getRole()));
    if (!allowed) {
        throw new BusinessException(ResultCode.FORBIDDEN);   // 403
    }
}
```

**查找顺序是"方法优先，类兜底"**，这个设计很有用：

- 类上标 `@RequireRole(ADMIN)` → 整个模块都要管理员
- 某个方法上再标 `@RequireRole(USER, ADMIN)` → 可以放宽单个方法

如果顺序反了（先类后方法），方法级的注解就永远没机会生效了。

## 2.3 实测：普通用户拿着合法 token 也进不来

```
=== 1. 普通用户访问管理接口 ===
{"code":403,"message":"没有操作权限"}          ← 商品列表
{"code":403,"message":"没有操作权限"}          ← 数据看板

=== 2. 未登录访问管理接口 ===
{"code":401,"message":"登录已失效，请重新登录"}
```

注意 403 和 401 的区别，**这个区分很重要**：

| 状态码 | 含义 | 前端应对 |
| --- | --- | --- |
| 401 | 没登录 / token 失效 | 跳转登录页 |
| 403 | 登录了，但权限不够 | 提示"没有权限"，留在原页 |

如果把 403 也当成 401 处理，普通用户点到一个管理员链接就会被莫名其妙地踢去登录页——**他已经登录了，会一脸懵。**

## 2.4 前端的两道闸门

**第一道：路由守卫**（`router/index.js`）：

```js
{
  path: '/admin',
  component: () => import('@/layout/AdminLayout.vue'),
  // 父路由上的 meta 会合并到所有子路由，所以这里写一次就够了
  meta: { requiresAuth: true, requiresAdmin: true },
  children: [
    { path: '', name: 'AdminDashboard', ... },
    { path: 'product', name: 'AdminProduct', ... }
  ]
}
```

**父路由的 `meta` 会自动合并到所有子路由**——这是 vue-router 4 的特性。所以 `/admin` 和 `/admin/product` 都会带上 `requiresAdmin`，不用每个子路由重复写。

守卫逻辑在第一阶段就写好了：

```js
if (to.meta.requiresAdmin && !userStore.isAdmin) {
  ElMessage.error('没有访问权限')
  return { path: '/' }
}
```

**第二道：界面本身不给入口**

```js
const menus = [
  { path: '/admin', title: '数据看板', icon: 'DataLine' },
  { path: '/admin/product', title: '商品管理', icon: 'Goods' }
]
```

普通用户的头像下拉菜单里根本看不到「管理后台」这一项：

```vue
<el-dropdown-item v-if="userStore.isAdmin" command="admin" divided>
  管理后台
</el-dropdown-item>
```

## 2.5 ⚠️ 必须澄清的一点

**前端这两道闸门都不是安全措施。**

用户打开浏览器控制台，手动调 `fetch('/api/admin/dashboard/stats')`，前端守卫一点用都没有。**真正的安全永远只在后端那一行 `@RequireRole`。**

那前端为什么还要做？**为了体验**——不让用户点进去再看到一堆报错。

> 记住这个层次关系：
> **后端校验 = 门锁；前端校验 = 门口的指示牌。**
> 指示牌能减少走错门的人，但防不住真想闯的人，也代替不了门锁。

# 第三部分：审核业务 —— 一次事务写三张表

## 3.1 为什么管理服务要单独写一套

我们已经有 `ProductService` 了，为什么还要 `AdminProductService`？

因为**关注点完全不同**：

| | `ProductService` | `AdminProductService` |
| --- | --- | --- |
| 服务对象 | 卖家本人 | 平台管理员 |
| 数据范围 | 只有自己的商品 | 全平台商品 |
| 关键约束 | `requireOwner()` 校验归属 | 校验管理员角色 |
| 典型操作 | 发布、编辑、下架自己的 | 审核、驳回、强制下架任何人的 |

**混在一起的最大风险是越权。** 想象一下把"审核"方法加到 `ProductService` 里，哪天有人忘了加 `@RequireRole`，一个卖家就能自己审核自己的商品上架——**整个审核机制就废了。**

用两个类，权限注解和权限校验就**物理隔离**了，出错的可能性大大降低。

> 这类"看起来重复了一点，但把风险隔开了"的设计，在真实项目里是常态。
> **该重复的地方要敢于重复。**

## 3.2 审核主流程

打开 `service/impl/AdminProductServiceImpl.java` 的 `audit()` 方法：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void audit(Long adminId, String adminName, Long productId, AuditDTO dto) {
    Product product = requireProduct(productId);

    // ---------- 校验一：前置状态 ----------
    if (!ProductStatus.PENDING.getCode().equals(product.getStatus())) {
        throw new BusinessException(ResultCode.PRODUCT_STATUS_ILLEGAL,
                "该商品当前状态为「" + ProductStatus.descOf(product.getStatus()) + "」，无法审核");
    }

    boolean pass = AuditAction.PASS.getCode().equals(dto.getAction());

    // ---------- 校验二：条件必填 ----------
    if (!pass && StrUtil.isBlank(dto.getReason())) {
        throw new BusinessException(ResultCode.PARAM_ERROR, "驳回时必须填写原因，方便卖家修改");
    }

    LocalDateTime now = LocalDateTime.now();

    // ---------- 第 1 件事：改商品状态 ----------
    productMapper.update(null, Wrappers.<Product>lambdaUpdate()
            .set(Product::getStatus, pass ? ProductStatus.ON_SALE.getCode() : ProductStatus.REJECTED.getCode())
            .set(Product::getRejectReason, pass ? null : dto.getReason())
            .set(pass, Product::getPublishTime, now)
            .set(Product::getAuditTime, now)
            .set(Product::getAuditorId, adminId)
            .set(Product::getUpdateTime, now)
            .eq(Product::getId, productId));

    // ---------- 第 2 件事：写审核记录 ----------
    saveRecord(product, adminId, adminName,
            pass ? AuditAction.PASS : AuditAction.REJECT,
            pass ? null : dto.getReason());

    // ---------- 第 3 件事：通知卖家 ----------
    if (pass) {
        notificationService.send(product.getUserId(), NotificationType.AUDIT,
                "商品审核通过",
                "你发布的「" + product.getTitle() + "」已通过审核，其他用户现在可以看到它了。",
                productId);
    } else {
        notificationService.send(product.getUserId(), NotificationType.AUDIT,
                "商品审核未通过",
                "你发布的「" + product.getTitle() + "」未通过审核。原因：" + dto.getReason()
                        + "。修改后可以重新提交审核。",
                productId);
    }
}
```

### 两道校验，两种性质

**校验一是"状态机校验"**——业务规则，不允许在错误的状态下做操作。

实测：

```
=== 10. 重复审核同一商品 ===
{"code":3002,"message":"该商品当前状态为「审核驳回」，无法审核"}
```

注意错误信息里带了**当前状态的中文名**。这比干巴巴的"操作失败"有用得多——管理员一看就知道发生了什么。

**校验二是"条件校验"**——校验规则依赖于另一个字段的值。

看 `AuditDTO`：

```java
@NotNull(message = "请选择审核结果")
@Min(1) @Max(2)
private Integer action;

/**
 * 驳回原因。
 * 这里不能加 @NotBlank —— 因为"通过"时不需要填原因。
 * 这种"根据另一个字段决定是否必填"的校验叫条件校验，
 * 用注解表达不了，放在 Service 层判断。
 */
@Size(max = 255)
private String reason;
```

**为什么注解表达不了？** 因为 `@NotBlank` 是静态的——要么必填、要么不必填。而这里的要求是"当 `action == 2` 时必填"。

有些框架支持条件校验（比如自定义校验注解 + 分组），但对一个字段的依赖来说，**在 Service 里写三行 if 是最简单清楚的方案**，没必要为了"不写业务代码"去引入复杂机制。

实测：

```
=== 6. 驳回但没填原因 ===
{"code":400,"message":"驳回时必须填写原因，方便卖家修改"}
```

### `.set(condition, column, value)` —— 条件更新的用法

注意这一行：

```java
.set(pass, Product::getPublishTime, now)
```

这是 MyBatis-Plus 的**三参数重载**：第一个参数是布尔条件，为 false 时这一列就不写进 SQL。

为什么需要它？看两个场景：

| 场景 | `status` | `rejectReason` | `publishTime` |
| --- | --- | --- | --- |
| 通过 | 1 已上架 | 清空 | **设为当前时间** |
| 驳回 | 4 驳回 | 驳回原因 | **不动** |

审核驳回的商品根本没过上架，"上架时间"就不该有值。用条件写法一行解决，不用写两个 if 分支。

### 为什么"改状态"必须用 UpdateWrapper

这一行是整段代码里最需要理解的：

```java
.set(Product::getRejectReason, pass ? null : dto.getReason())
```

如果按直觉写成：

```java
Product update = new Product();
update.setId(productId);
update.setStatus(ProductStatus.ON_SALE.getCode());
update.setRejectReason(null);      // ← 想清空
productMapper.updateById(update);
```

**`rejectReason` 根本不会被清空。** 原因见下一部分——这是我在这个项目里踩了**两次**的坑。

## 3.3 强制下架：另一个审核动作

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void forceOffShelf(Long adminId, String adminName, Long productId, ForceOffShelfDTO dto) {
    Product product = requireProduct(productId);

    if (!ProductStatus.ON_SALE.getCode().equals(product.getStatus())) {
        throw new BusinessException(ResultCode.PRODUCT_STATUS_ILLEGAL, "只有在售商品才能强制下架");
    }

    productMapper.update(null, Wrappers.<Product>lambdaUpdate()
            .set(Product::getStatus, ProductStatus.OFF_SHELF.getCode())
            // 复用 rejectReason 字段承载"平台的处置原因"
            .set(Product::getRejectReason, dto.getReason())
            .set(Product::getAuditTime, LocalDateTime.now())
            .set(Product::getAuditorId, adminId)
            .set(Product::getUpdateTime, LocalDateTime.now())
            .eq(Product::getId, productId));

    saveRecord(product, adminId, adminName, AuditAction.FORCE_OFF, dto.getReason());

    notificationService.send(product.getUserId(), NotificationType.SYSTEM,
            "商品已被下架",
            "你发布的「" + product.getTitle() + "」因违反平台规范已被下架。原因：" + dto.getReason(),
            productId);
}
```

### 下架原因为什么必须填（`@NotBlank`）

```java
public class ForceOffShelfDTO {
    @NotBlank(message = "请填写下架原因")
    @Size(max = 255, message = "下架原因不能超过 255 个字符")
    private String reason;
}
```

这和 `AuditDTO.reason` 的处理**故意不同**：审核驳回时原因必填（因为这是一次性的动作），强制下架也必填。原因是：

- **要留痕**：将来卖家申诉、或者追究管理员操作是否合规，都要有据可查
- **卖家有权知道**：商品突然消失却不知道为什么，是最糟糕的用户体验

### 一个字段承载两种语义的取舍

`biz_product` 表里没有"下架原因"这一列，我复用了 `rejectReason`，并把它的语义扩展成**"平台处置原因"**：

```java
/**
 * 平台处置原因。
 * 审核驳回时填"为什么不合格"，管理员强制下架时填"为什么被下架"。
 * 两个场景共用同一列，是为了避免为低频场景单独加字段；语义由 status 区分。
 */
private String rejectReason;
```

**这是一个刻意的取舍。** 两种做法对比：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 复用 `rejectReason` | 不加字段、SQL 简单 | 语义要靠 `status` 区分，读代码时要多理解一层 |
| 新增 `off_shelf_reason` | 语义清晰 | 多一列、多一个"哪个场景该填哪个"的判断 |

我选了复用，因为**强制下架是低频操作**，为它单独加一列不值。但要在代码注释里说清楚——**"复用"和"偷懒"的区别，就在于有没有把语义写明白。**

### 前端也要跟着适配

既然下架原因存在 `rejectReason` 里，前端展示时就要按状态区分标题（`MyProducts.vue`）：

```vue
<el-alert
  v-if="item.rejectReason && (item.status === 4 || item.status === 2)"
  :type="item.status === 4 ? 'error' : 'warning'"
  :closable="false"
>
  {{ item.status === 4 ? '驳回原因' : '下架原因' }}：{{ item.rejectReason }}
</el-alert>
```

**改了后端字段语义，一定要检查所有读到这个字段的地方。** 这是最容易漏的联动修改。

## 3.4 事务边界

`@Transactional(rollbackFor = Exception.class)` 包住了三个写操作：

1. `productMapper.update(...)` —— 改商品状态
2. `auditRecordMapper.insert(...)` —— 写审核记录
3. `notificationMapper.insert(...)` —— 发通知

**如果第 3 步失败会怎样？**

没有事务的话：商品上架了、审核记录写了，但卖家没收到通知。卖家会以为自己的商品还在审核中，可能重复提交、或者去别的地方发帖问。

有了事务：**三步全部回滚**，管理员看到报错，重新点一次即可，数据任何时候都是一致的。

实时验证（第 27 项测试，商品 3 的完整审核历史）：

```
=== 27. full audit trail for product 3 ===
count = 5
  [审核驳回] reason=[商品描述与图片不符，请补充实拍图后重新提交]
  [审核通过] reason=[]
  [强制下架] reason=[疑似盗用他人图片，经核实后强制下架]
  [审核通过] reason=[]
  [审核驳回] reason=[商品描述与图片不符，请补充实拍图后重新提交]
```

**5 次操作全部留痕，一次不漏。** 这就是"业务可全程追溯"。

# 第四部分：反复出现的坑 —— updateById 与 null

**这是本项目最有价值的一段。** 同一个坑我踩了两次，第二次还是在"已经知道这个坑"之后。

## 4.1 现象

测试时发现：卖家点了「重新提交审核」后，商品虽然回到了待审核状态，**但还挂着上一次的驳回原因**。

```
=== 11. seller resubmits rejected product ===
pending total = 1  status = 0  rejectReason = [商品描述与图片不符，请补充实拍图后重新提交]
                                       ↑ 已经是"待审核"了，却还带着上轮的驳回原因
```

## 4.2 当时的代码

```java
Product update = new Product();
update.setId(productId);
update.setStatus(ProductStatus.PENDING.getCode());
update.setRejectReason(null);          // ← 意图：清空驳回原因
update.setUpdateTime(LocalDateTime.now());
productMapper.updateById(update);
```

看上去完全合理，但 `rejectReason` 就是清不掉。

## 4.3 原理：MyBatis-Plus 的字段更新策略

`updateById` 生成 SQL 时，会**逐个判断每个字段要不要写进去**。默认策略是 `FieldStrategy.NOT_NULL`：

```
字段值 != null  →  写进 SET 子句
字段值 == null  →  跳过，不写
```

所以上面那段代码实际生成的 SQL 是：

```sql
UPDATE biz_product
SET status = 0, update_time = '2026-10-19 16:43:00'   -- 注意：没有 reject_reason！
WHERE id = 3 AND deleted = 0
```

`setRejectReason(null)` 被**静默忽略**了。没有报错、没有警告，就是没生效。

## 4.4 这个特性其实是"好事"

先别急着骂它。`NOT_NULL` 策略解决了一个很实际的问题：

```java
// 想只改昵称，其他字段别动
User update = new User();
update.setId(1);
update.setNickname("新昵称");
userMapper.updateById(update);
// SQL: UPDATE sys_user SET nickname = '新昵称' WHERE id = 1
// 而不是把 password、role、status 全部覆盖一遍
```

如果 MyBatis-Plus 把所有字段都写进去，上面这段就会把 `password`、`role` 覆盖成 `null`——**那才是灾难。**

**"只更新变化的列"是它想给你的能力；"没法把字段改回 null"是这个能力的代价。**

## 4.5 正确姿势：显式 UpdateWrapper

要把字段改成 null，只能用 `UpdateWrapper` 显式 `set`：

```java
productMapper.update(null, Wrappers.<Product>lambdaUpdate()
        .set(Product::getStatus, ProductStatus.PENDING.getCode())
        .set(Product::getRejectReason, null)      // ← 这样才真的写 null
        .set(Product::getUpdateTime, LocalDateTime.now())
        .eq(Product::getId, productId));
```

生成的 SQL：

```sql
UPDATE biz_product
SET status = 0, reject_reason = null, update_time = '...'
WHERE id = 3
```

`Wrappers.<Product>lambdaUpdate()` 用方法引用指定列，**没有拼字符串，也就没有 SQL 注入风险**。

## 4.6 我在哪里踩了两次

**第一次**：写审核模块时，因为要"审核通过时清空驳回原因"，我用了 `LambdaUpdateWrapper`——**这次是对的**。

**第二次**：但商品模块的 `update()` 和 `resubmit()` 是上一阶段写的，里面同样有"清空驳回原因"的需求，用的还是 `updateById`——**漏了**。

修完之后，我在 `ProductServiceImpl` 里抽了一个明确的辅助方法：

```java
/**
 * 显式清空平台处置原因。
 * <p>
 * 必须用 UpdateWrapper：MyBatis-Plus 的 updateById 会忽略实体里为 null 的字段
 * （这个特性平时很有用，可以只更新变化的列），代价就是"想把某个字段改回 null"
 * 时它做不到，只能用它显式 set。这是本项目踩过的坑里最隐蔽的一个。
 */
private void clearRejectReason(Long productId) {
    productMapper.update(null, Wrappers.<Product>lambdaUpdate()
            .set(Product::getRejectReason, null)
            .eq(Product::getId, productId));
}
```

**把坑写进方法名和注释里**，下次谁看到这个调用都会问一句"为什么要单独写个方法"，然后就学到了。

## 4.7 验证修复

```
=== 22. BEFORE:  status=2  rejectReason=[疑似盗用他人图片，经核实后强制下架]
=== 23. resubmit: status=0  rejectReason=[]          ← 清空了 ✅
=== 24. 再驳回:    status=4  rejectReason=[商品描述与图片不符，请补充实拍图后重新提交]
=== 25. 编辑后:    status=0  rejectReason=[]          ← 也清空了 ✅
```

## 4.8 教训：修完要全局搜同类写法

这是本章最重要的一条。

我在审核模块里**已经躲过了这个坑**，但商品模块里的同类代码没有被"传染"到正确写法。**已知的坑不会自动扩散到所有地方。**

修完一个 bug，一定要做两件事：

**① 全局搜索同类模式**

```bash
# 找所有 updateById 的调用，逐个检查"有没有想清空某个字段"
grep -rn "updateById" backend/src/main/java
```

**② 把规则写进代码注释或团队约定**

> **规则：`updateById` 只能把字段改成非 null 值；要改成 null，必须用 `LambdaUpdateWrapper` 显式 `set`。**

这条规则我写进了 `docs/03-商品模块实现讲解.md`，也在这个文档里重复一遍——**因为它值得被记住两次。**

# 第五部分：审核留痕 —— 快照式审计表设计

## 5.1 表结构

```sql
CREATE TABLE `biz_audit_record` (
    `id`            BIGINT       NOT NULL AUTO_INCREMENT,
    `product_id`    BIGINT       NOT NULL                COMMENT '商品ID',
    `product_title` VARCHAR(100) DEFAULT NULL            COMMENT '商品标题快照',
    `admin_id`      BIGINT       NOT NULL                COMMENT '审核人ID',
    `admin_name`    VARCHAR(50)  DEFAULT NULL            COMMENT '审核人账号快照',
    `action`        TINYINT      NOT NULL                COMMENT '审核动作 1通过 2驳回 3强制下架',
    `reason`        VARCHAR(255) DEFAULT NULL            COMMENT '驳回原因',
    `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    KEY `idx_product` (`product_id`),
    KEY `idx_admin` (`admin_id`)
)
```

## 5.2 为什么要存快照

注意 `product_title` 和 `admin_name` 这两个字段——**它们的数据在别的表里已经有了，为什么要冗余一份？**

因为审计记录的职责是"还原当时发生了什么"：

| 时间 | 事件 | 如果只存 `product_id` 会怎样 |
| --- | --- | --- |
| 10:00 | 张三发布「iPhone 14 Pro」 | —— |
| 10:05 | 管理员驳回 | 记录：商品 3 被驳回 |
| 10:10 | 张三把标题改成「代开发票 加微信」 | —— |
| 11:00 | 有人查审核记录 | 显示「代开发票 加微信」被驳回 ❌ **失真** |

存了快照后，记录里显示的永远是**当时**的标题：「iPhone 14 Pro」。管理员改昵称、商品改标题，都不影响历史记录。

**这就是审计类表的通用设计原则：存快照，不存引用。**

## 5.3 追加型表：只插不改不删

这张表**没有任何更新和删除操作**，只有 `insert` 和 `select`。

好处：
- 记录永远不会被篡改（代码层面就没有改的入口）
- 责任清晰，出问题能追溯到具体的人和时间
- 不需要 `deleted` 字段（因为不删）

## 5.4 枚举的扩展能力

上一阶段定义 `AuditAction` 时只有两种动作，这阶段加了第三种：

```java
public enum AuditAction {
    PASS(1, "审核通过"),
    REJECT(2, "审核驳回"),
    FORCE_OFF(3, "强制下架");      // ← 新增
    ...
}
```

因为用了枚举而不是散落的数字，新增动作只需要改这一处，所有用到 `descOf()` 的地方自动支持。

`AuditRecordVO` 里有个方便前端的字段：

```java
vo.setAction(r.getAction());
vo.setActionText(AuditAction.descOf(r.getAction()));   // "审核通过" / "审核驳回" / "强制下架"
```

**后端把枚举翻译成中文一起返回**，前端就不用维护一份"1 对应什么文字"的映射表了——**两处维护就一定会有一处忘记改。**

# 第六部分：站内通知 —— 让平台"会说话"

## 6.1 为什么需要它

"审核不通过"这件事，如果只改数据库状态，**卖家根本不知道**。他只会发现商品不见了、列表里也没有，然后开始困惑、重复提交、或者发帖问客服。

**任何"平台对用户内容做了处置"的操作，都必须通知到人。** 这是需求里"交互逻辑清晰、友好提示"的一部分。

## 6.2 统一发送入口

所有通知都通过一个方法发出（`NotificationService.send`）：

```java
void send(Long userId, NotificationType type, String title, String content, Long bizId);
```

**为什么不各处在自己的 Service 里直接 insert？**

因为通知这种东西**一定会越来越多**：审核结果、订单状态、留言回复、系统公告……

如果每处都自己 insert，就会出现：有的忘了设 `isRead = 0`、有的忘了设 `createTime`、有的类型值写错。**统一入口保证每条通知的结构都一致。**

## 6.3 越权防护：userId 从 token 取

```java
@Operation(summary = "我的通知列表")
@GetMapping("/page")
public Result<PageResult<NotificationVO>> page(
        @RequestParam(required = false) Long current,
        @RequestParam(required = false) Long size) {
    return Result.success(notificationService.page(UserContext.userId(), current, size));
}
```

接口签名里**没有 `userId` 参数**，用户没法指定查谁的通知。

Service 层还做了第二道防护：

```java
// 只能查自己的通知：userId 条件必须带上，
// 否则改个参数就能读到别人的通知（越权）
IPage<Notification> page = notificationMapper.selectPage(
        new Page<>(pageNum, pageSize),
        Wrappers.<Notification>lambdaQuery()
                .eq(Notification::getUserId, userId)     // ← 必须带
                .orderByDesc(Notification::getCreateTime));
```

标记已读也是同理：

```java
@Override
public void markRead(Long userId, Long notificationId) {
    // 带 userId 条件更新：即使别人拿到我的通知ID，也改不动
    notificationMapper.update(null, Wrappers.<Notification>lambdaUpdate()
            .set(Notification::getIsRead, Constants.READ)
            .eq(Notification::getId, notificationId)
            .eq(Notification::getUserId, userId));       // ← 双条件
}
```

**这里有个细节值得注意：更新比查询更需要小心。**

查询带错了条件，最多是看到别人的数据（信息泄漏）；**更新带错了条件，是修改了别人的数据（数据破坏）。** 所以写更新语句时，"归属条件"一次都不能省。

实测验证：

```
=== 18. two-way check ===
unread before = 3     (zhangsan 的未读数)
unread after  = 0     (全部已读后)
=== 19. lisi can NOT see zhangsan notifications ===
lisi unread = 0       ← lisi 看到的是自己的，不是 zhangsan 的 ✅
```

## 6.4 通知的内容怎么写

```java
notificationService.send(product.getUserId(), NotificationType.AUDIT,
        "商品审核未通过",
        "你发布的「" + product.getTitle() + "」未通过审核。原因：" + dto.getReason()
                + "。修改后可以重新提交审核。",
        productId);
```

实测收到的内容：

```
type=1  title=商品审核未通过
content=你发布的「索尼 A7M4 全画幅微单」未通过审核。
        原因：商品描述与图片不符，请补充实拍图后重新提交。修改后可以重新提交审核。
```

一条好的通知包含四要素：

| 要素 | 本例 | 为什么 |
| --- | --- | --- |
| **发生了什么** | 未通过审核 | 让用户一眼知道结论 |
| **针对什么** | 商品标题 | 用户可能有几十个商品，必须指明是哪个 |
| **为什么** | 管理员填的原因 | 知道原因才有改进方向 |
| **接下来能做什么** | 修改后可以重新提交 | 只报问题不给出口，用户会更焦虑 |

`bizId` 存的是商品 ID，前端点击通知就能跳到对应商品页——**通知不只是文字，还要能"跳过去"。**

## 6.5 前端铃铛的实现要点

`components/NotificationBell.vue` 用 `el-popover` 实现下拉面板，两个关键点：

**① 未读数用独立接口，不要靠列表长度**

```js
async function loadUnread() {
  unread.value = Number(await getUnreadCount())    // 只查 COUNT
}
```

未读数可能超过列表的 10 条上限，用列表长度算会不准。

**② 点开才加载列表**

```vue
<el-popover @show="loadList">
```

用户不点铃铛就不发请求。**这类"按需加载"是性能设计的常识——不是所有数据都该在页面打开时全部拉下来。**

# 第七部分：数据看板 —— 统计怎么写才不慢

```java
@Override
public DashboardVO stats() {
    DashboardVO vo = new DashboardVO();

    vo.setUserCount(userMapper.selectCount(null));
    vo.setDisabledUserCount(userMapper.selectCount(
            Wrappers.<User>lambdaQuery().eq(User::getStatus, Constants.STATUS_DISABLED)));

    vo.setProductCount(productMapper.selectCount(null));
    vo.setPendingCount(countByStatus(ProductStatus.PENDING));
    vo.setOnSaleCount(countByStatus(ProductStatus.ON_SALE));
    vo.setSoldCount(countByStatus(ProductStatus.SOLD));

    Long totalView = productMapper.sumViewCount();
    vo.setTotalViewCount(totalView == null ? 0L : totalView);

    return vo;
}
```

## 7.1 用 COUNT 而不是"全查出来在 Java 里数"

**反面教材：**

```java
List<Product> all = productMapper.selectList(null);       // ❌ 把 10 万条商品全查出来
long pending = all.stream().filter(p -> p.getStatus() == 0).count();
```

后果：
1. 10 万条数据全部加载进 JVM 内存 → **内存爆炸**
2. 网络传输 10 万条 → **慢**
3. 数据库要读出完整行数据 → **IO 浪费**

正确做法是让**数据库自己数**——`COUNT(*)` 只需要扫索引，不需要把数据搬出来：

```sql
SELECT COUNT(*) FROM biz_product WHERE status = 0 AND deleted = 0
```

**"聚合交给数据库"是一条基本原则。** 数据库就是为了处理数据而生的，别把它当纯存储用。

## 7.2 手写 SQL 别忘了 deleted = 0

`totalViewCount` 需要求和，`selectCount` 做不到，只能手写：

```java
/**
 * 统计所有商品的累计浏览量。
 * <p>
 * 注意手写的 SQL 必须自己写 deleted = 0 —— 逻辑删除只对
 * MyBatis-Plus 自动生成的方法生效，手写的一律不管。
 */
@Select("SELECT COALESCE(SUM(view_count), 0) FROM biz_product WHERE deleted = 0")
Long sumViewCount();
```

两个细节：

**① `deleted = 0` 必须自己写。** 这是第三次强调这个坑了（第一次在列表 SQL，第二次在详情，现在是聚合 SQL）。**只要手写 SQL，就要问自己一句"逻辑删除条件加了吗"。**

**② `COALESCE(SUM(...), 0)`。** 如果表里一条数据都没有，`SUM()` 返回的是 `NULL` 而不是 0。Java 那边拿到 `null` 就得做判空。用 `COALESCE` 让它在 SQL 层就返回 0：

```java
vo.setTotalViewCount(totalView == null ? 0L : totalView);   // Java 侧再兜一层
```

**两层兜底**——数据库层给合理默认值，Java 层再防一次。数据展示类的代码，宁可多兜一次。

# 第八部分：前端实现

## 8.1 AdminLayout：独立的后台布局

后台和前台是**两套完全不同的壳**：

| | `UserLayout` | `AdminLayout` |
| --- | --- | --- |

## 8.2 菜单只列已实现的模块

```js
/**
```

## 8.3 审核弹窗：常用原因一键填充

还有一个隐性的好处：**统一了驳回话术**。不同管理员写法五花八门（"描述不符"、"图和货不一致"、"图片造假"），卖家看到的提示质量参差不齐。给几个标准选项，输出质量就稳定了。

## 8.4 状态 Tab 上的数量徽标

```vue
<el-badge v-if="counts[0]" :value="counts[0]" class="tab-badge" />
```

```js
/** 拉各状态的数量，显示在 Tab 上 */
async function loadCounts() {
  await Promise.all(
    [0, 1, 2, 3, 4].map(async (status) => {
      const data = await adminPageProducts({ current: 1, size: 1, status })
      counts[status] = Number(data.total)
    })
  )
}
```

两个优化点：

**① `size: 1`——只要 `total`，不要数据。**

我们只需要数量，传 1 条就够了。传 `size: 100000` 只是白白传回一堆用不上的数据。

**② `Promise.all` 并发请求。**

5 个状态的查询互相不依赖，串行要 5 个来回，并发只要 1 个来回的时间。

```js
// ❌ 串行：5 次网络往返
for (const s of [0,1,2,3,4]) { await query(s) }

// ✅ 并发：1 次网络往返的时间
await Promise.all([0,1,2,3,4].map(s => query(s)))
```

**这是前端性能优化里性价比最高的一招**——不需要改后端、不需要加缓存，改几行代码就有效果。

## 8.5 详情抽屉 + 审核时间线

管理员审核前需要看完整信息，用 `el-drawer` 从右侧滑出，不打断列表浏览：

```js
async function openDetail(row) {
  currentRow.value = row
  detailVisible.value = true
  detailLoading.value = true
  try {

    const [d, r] = await Promise.all([getProduct(row.id), getAuditRecords(row.id)])
    detail.value = d
    records.value = r
    specList.value = parseSpec(d.spec)
  } finally {
    detailLoading.value = false
  }
}
```

同样用了 `Promise.all` 并发请求两个接口。

审核历史用 `el-timeline` 展示，颜色按动作区分：

```vue

  :type="r.action === 1 ? 'success' : r.action === 2 ? 'danger' : 'warning'"
>
```

**通过=绿色、驳回=红色、强制下架=橙色**，管理员一眼能看出这个商品的历史轨迹。

## 8.6 一个细节：`finally` 里恢复 loading

```js
async function loadList() {
  loading.value = true
  try {
    const data = await adminPageProducts(query)
    list.value = data.records
    total.value = Number(data.total)
  } finally {
    loading.value = false          // ← 放在 finally，不是 try 里
  }
}
```

**为什么必须放 `finally`？** 如果放在 `try` 的末尾，一旦请求抛异常（网络断了），`loading` 会永远停在 `true`，页面转圈转到天荒地老。

`finally` 保证**无论成功失败都恢复**。这个模式在整个项目里到处都是，值得养成习惯。

# 第九部分：实战排查 —— 图片上传成功却不显示

> 这一节是本阶段的真实事故记录。**排查过程本身比结论更有价值。**

## 9.1 现象

用户上架了商品、上传了图片，但**图片显示不出来**。

## 9.2 排查路径

### 第 1 步：先怀疑数据，不是代码

第一件事不是看代码，而是**看数据库里到底存了什么**。

```sql
select id, title, status, cover_image from biz_product order by id desc limit 5;
```

结果：

```
id  title              cover_image
4   机械革命极光pro      blob:http://localhost:5173/d136d076-6b1f-4a08-bfbf-390da395b97a
3   索尼 A7M4 全画幅微单  /uploads/product/2026/10/4b6c07776c914b1f983fe5f10f65464d.png
2   联想拯救者 R9000P     /uploads/product/2026/10/4be7382503d04097889913c3b3123093.png
1   iPhone 14 Pro        /uploads/product/2026/10/0fbbaa2e8381422397b2bb5b3fc4221d.png
                                                ↑ 正常的都是 /uploads/ 开头
```

**问题定位了。** 商品 4 存的是 `blob:http://localhost:5173/...`。

`blob:` 是**浏览器为本地文件预览生成的临时地址**，只存在于当前这个页面标签的内存里。存进数据库后：
- 别人看不到（他们的浏览器没有这个 blob）
- 用户自己刷新页面后也看不到（blob 已经释放了）

### 第 2 步：确认文件到底传上去没有

```powershell
Get-ChildItem -Recurse backend\uploads -File
```

结果：

```
0fbbaa2e8381422397b2bb5b3fc4221d.png    2631
4b6c07776c914b1f983fe5f10f65464d.png    2631
4be7382503d04097889913c3b3123093.png    2631
cf64435579da40dba54bbd3139f91d7f.webp  29796   ← 新出现的
f24bb9902b4e490e9e9a35373208dc71.webp  29796   ← 新出现的
```

**两个 29KB 的新文件。** 文件**确实上传成功了**（而且传了两次，用户试了两遍）。

所以结论非常明确：

> **不是上传失败，也不是渲染失败 —— 是上传成功了，但前端存进数据库的是错的地址。**

这个结论把排查范围从"整个上传链路"缩小到了"前端取地址的那几行代码"。

### 第 3 步：读第三方库的源码

`Publish.vue` 里取地址的逻辑是：

```js
return fileList.value
  .map((f) => (typeof f.response === 'string' ? f.response : f.url))
```

`f.response` 应该存着服务器返回的地址。既然走了 `f.url` 分支，说明 **`f.response` 不是字符串**。

那就去看 Element Plus 到底怎么处理 `http-request` 的返回值。**`node_modules` 里的编译产物是可以直接读的**：

```js
// element-plus/es/components/upload/src/upload-content.vue_...mjs (107-109 行)
const request = httpRequest(options)
requests.value[uid] = request
if (request instanceof Promise) request.then(options.onSuccess, options.onError)
```

```js
// element-plus/es/components/upload/src/use-handlers.mjs (47-54 行)
const handleSuccess = (response, rawFile) => {
  const file = getFile(rawFile)
  if (!file) return
  file.status = "success"
  file.response = response        // ← 无条件赋值！
  props.onSuccess(response, file, uploadFiles.value)
  emitChange(file)
}
```

**根因清楚了。**

## 9.3 我的代码错在哪

```js
async function handleUpload(options) {     // ① async 函数 → 返回 Promise
  try {
    const url = await uploadImage(options.file)
    options.onSuccess(url)                 // ② 手动调了一次 onSuccess
  } catch (error) {
    options.onError(error)
  }
}                                          // ③ 没有 return → resolve 值是 undefined
```

执行顺序：

| 步骤 | 谁触发 | 传了什么 | `file.response` |
| --- | --- | --- | --- |
| 1 | 我调 `onSuccess` | `'/uploads/...'` | `'/uploads/...'` ✅ |
| 2 | 我的 async 函数正常结束 | —— | —— |
| 3 | Promise resolve，值是 `undefined` | —— | —— |
| 4 | Element Plus 的 `request.then(options.onSuccess)` | `undefined` | **`undefined`** ❌ |
| 5 | 我的取值逻辑回退到 `f.url` | —— | `'blob:...'` ❌ |

**关键在第 4 步**：Element Plus 检测到 `httpRequest` 返回了 Promise，就**替你**调了一次 `onSuccess`。而我的函数没有 `return`，所以它拿到的是 `undefined`——**把我刚写进去的正确值覆盖了。**

`handleSuccess` 里是**无条件赋值**（`file.response = response`），所以后一次调用一定会覆盖前一次。

## 9.4 修复

**① 只返回 Promise，不要手动调 `onSuccess`：**

```js
function handleUpload(options) {
  return uploadImage(options.file)
}
```

Element Plus 会自动把 Promise 的 resolve 值交给 `onSuccess`；如果 Promise reject，它会调 `onError`。**两条路径都是它的事，我不用管。**

其实 `http-request` 的类型签名本来就说清楚了：

```ts
httpRequest?: (options: UploadRequestOptions) => XMLHttpRequest | Promise<unknown>
```

**返回 `Promise` 是官方支持的用法。** 我多此一举地又调了一次回调。

**② 加一道兜底的格式过滤：**

```js
function collectImageUrls() {
  return fileList.value
    .map((f) => (typeof f.response === 'string' ? f.response : f.url))
    .filter((url) => typeof url === 'string'
        && !url.startsWith('blob:')
        && !url.startsWith('data:'))
}
```

**为什么必须加这道过滤？**

因为 `blob:` 和 `data:` 这类地址**永远不该进数据库**。就算以后有人改坏了上传逻辑，这道过滤会让问题**立刻暴露**（图片保存不了，用户马上反馈），而不是默默存一条坏数据——**坏数据是最难发现、最难清理的问题。**

这是"防御性编程"的典型应用：**在数据进出的边界上校验格式，而不是信任上游。**

## 9.5 同一个 bug 还藏在别处

修完上传后我顺手检查了头像上传（`Profile.vue`），**一模一样的写法**：

```js
async function handleAvatarUpload(options) {
  try {
    const url = await uploadAvatar(options.file)
    userStore.setUserInfo({ avatar: url })
    ElMessage.success('头像已更新')
    options.onSuccess(url)       // ← 同样的问题
  } catch (error) {
    options.onError(error)
  }
}
```

**它为什么没出问题？** 因为我恰好在 `onSuccess` 之外还单独调了 `userStore.setUserInfo({ avatar: url })`——数据库拿到的是这个正确值，`file.response` 被覆盖也无所谓。

**这纯属运气好。** 如果哪天有人把 `setUserInfo` 挪个位置，或者改成从 `fileList` 里取地址，同样的 bug 就会复发。

**所以一起修了。**

> **教训：修一个 bug 时，一定要搜一搜同样的写法在别处有没有。**
> 这和第 4.8 节"updateById 的坑"是同一个道理——**bug 不会自己扩散到该修的地方。**

## 9.6 清理坏数据

修代码不解决已经存进去的坏数据。磁盘上那两个 `.webp` 就是上传成功的原文件，直接把商品记录指过去：

```sql
update biz_product
   set cover_image = '/uploads/product/2026/10/cf64435579da40dba54bbd3139f91d7f.webp'
 where id = 4;

update biz_product_image
   set url = '/uploads/product/2026/10/cf64435579da40dba54bbd3139f91d7f.webp'
 where product_id = 4;
```

验证：

```
直连后端：      status=200  type=image/webp  size=29796
走 Vite 代理：  status=200  type=image/webp  size=29796
商品详情：      images = /uploads/product/2026/10/cf64435579da40dba54bbd3139f91d7f.webp
```

**图片正常了。**

> **顺带说一句：修复线上数据要"先查后改"。**
> 我先查了 `select ... where url like 'blob:%'` 确认影响范围只有 1 条，
> 才动手改。如果影响面很大，就该写脚本批量处理，并先备份。

## 9.7 这次排查的方法论

把过程抽象一下，这套思路适用于绝大多数"数据不对"的问题：

```
① 看数据，不看代码
   直接查数据库里存的是什么 → 定位到"地址错了"
        ↓
② 确认中间环节
   查磁盘文件是否存在 → 确认"上传本身是成功的"
   → 排查范围从"整条链路"缩小到"前端取地址这几行"
        ↓
③ 读源码，不猜
   第三方库的行为要看实际代码，不要凭印象
        ↓
④ 修 + 加防御
   改对的同时加一道格式校验，让同类问题无法悄悄发生
        ↓
⑤ 全局搜同类写法
   修完检查其他地方有没有一样的错
        ↓
⑥ 清理存量坏数据
   代码修了，已经写进去的坏数据还在
```

**第 ① 步是最重要的一步**，也是最容易被跳过的一步。很多人遇到"图片不显示"就一头扎进上传代码里读，读了半小时才发现数据库里存的是个 `blob:` 地址。

**先看数据，五分钟定位问题。**
