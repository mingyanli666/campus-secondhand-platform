# 第一部分：什么叫"预留"，什么叫"空实现"

## 1.1 空实现的三个问题

最省事的"预留"是这样：

```java
public interface RecommendService {
    List<Product> recommend(Long userId);
}

@Service
public class RecommendServiceImpl implements RecommendService {
    @Override
    public List<Product> recommend(Long userId) {
        return Collections.emptyList();   // ← 预留
    }
}
```

看起来"接口定义好了，随时可以填"。实际上有三个问题：

| 问题 | 后果 |
| --- | --- |
| **没法验收** | 演示时点一下返回空列表，老师看不出这是"预留"还是"没做完" |
| **接口设计没被验证** | 参数够不够？返回值够不够前端展示？空实现永远不会暴露这些问题 |
| **不知道离能用差多远** | 换实现时要重新趟一遍"数据从哪来、怎么组装" |

## 1.2 本项目采用的做法

```
① 定义接口契约（带完整 javadoc：现在做什么、以后怎么升级、已知不足）
② 写一个能跑的基线实现（不是空实现）
③ 接进 Controller，前端/curl 都能真的调用
④ 补测试，把基线的边界行为固定下来
⑤ 文档写清"升级时改哪里、哪些不用改"
```

**关键点：基线实现要"真的能用"，但不要"做过头"。**

- 能用 = 演示时能看到结果、能截图、能说清逻辑
- 不做过头 = 不为了实现协同过滤去搭离线计算、不去引第三方推荐引擎

**这三块加起来不到 300 行代码**，但换来的是答辩时的底气和一个真实的架构案例。

# 第二部分：整体设计

## 2.1 三层分离

```
┌──────────────────────────────────────────────────────────┐
│  ExtensionController        /api/extension/**             │
│  ── 只负责收参和返回，不含任何算法 ──                       │
└───────────────────────┬──────────────────────────────────┘
                        │ 依赖接口，不依赖实现
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
┌───────────────┐ ┌──────────────┐ ┌──────────────┐
│ Recommend     │ │ PriceEvalua  │ │ CreditRating │
│ Service       │ │ tionService  │ │ Service      │  ← 接口
└───────┬───────┘ └──────┬───────┘ └──────┬───────┘
        │                │                │
        ▼                ▼                ▼
┌───────────────┐ ┌──────────────┐ ┌──────────────┐
│ Recommend     │ │ PriceEvalua  │ │ CreditRating │
│ ServiceImpl   │ │ tionServiceImpl│ │ ServiceImpl │  ← 基线实现
│ （热度排序）   │ │ （同类均价）  │ │ （行为打分）  │
└───────────────┘ └──────────────┘ └──────────────┘
        ↕                ↕                ↕
   换算法只换这一层，Controller / VO / 前端全不动
```

## 2.2 为什么 Controller 依赖接口而不是实现

```java
@RequiredArgsConstructor
public class ExtensionController {
    private final RecommendService recommendService;   // ← 接口
}
```

Spring 按类型注入，所以：

```
现在：容器里装的是 RecommendServiceImpl（热度排序）
以后：写一个 RecommendServiceImplV2（协同过滤），
      把旧的标 @Primary 去掉 / 或者直接替换类名
      → Controller 一行不改，API 路径和返回结构不变
```

**这就是"对扩展开放、对修改关闭"在本项目里的具体落点。**

## 2.3 全部标 `@PublicApi`

推荐、价格参考、信誉等级都是**浏览者就该看到的辅助信息**，
游客在商品详情页也应该能看"同类都卖多少钱"。所以不走登录校验。

# 第三部分：智能推荐

## 3.1 接口

```java
public interface RecommendService {
    /** 相似商品（详情页「看了又看」） */
    List<ProductListVO> similarProducts(Long productId, int limit);
    /** 热门商品（首页推荐位） */
    List<ProductListVO> hotProducts(int limit);
}
```

## 3.2 基线实现做了什么

| 方法 | 策略 |
| --- | --- |
| `similarProducts` | 同分类 + 在售 + **排除自己**，按收藏数 → 浏览量降序 |
| `hotProducts` | 在售商品按收藏数 → 浏览量降序 |

两个实现细节：

**① 商品不存在时返回空列表，不抛异常**

```java
Product current = productMapper.selectById(productId);
if (current == null) {
    return List.of();   // 不是 BusinessException
}
```

理由：推荐位是「锦上添花」的功能，**不该因为它把详情页搞挂**。
这和商品详情接口的处理方式刻意不同——那里商品不存在必须报 3001，
因为那是主体内容。

**同一个"资源不存在"，在不同语境下的正确反应是不一样的。**

**② 两道上限**

```java
private static final int MAX_LIMIT = 20;
private static int clampLimit(int limit) {
    return Math.min(Math.max(limit, 1), MAX_LIMIT);
}
```

这是**业务层的第二道上限**：分页插件管的是"每页最多多少条"，
这里管的是"推荐位最多几条"。两回事，别指望前者兜住后者。

实测 `?limit=99999` → 返回 20 条。

## 3.3 它没做什么（诚实说明）

| 缺什么 | 后果 |
| --- | --- |
| 没有用户画像 | 同一件商品推给所有人结果一样，本质是排行榜不是推荐 |
| 没有协同过滤 | 不看"和你相似的人买了什么" |
| 没有多样性控制 | 结果可能全是同一个卖家的 |
| 没有冷启动处理 | 新用户和新商品一样对待 |

## 3.4 升级路径

### 方案一：基于内容的推荐

```
商品标题 + 品牌 + 型号 + 分类 → 向量化（TF-IDF / embedding）
→ 算余弦相似度 → 取 top N
```

**改动范围**：只有 `similarProducts` 的内部实现。

### 方案二：协同过滤

**数据已经在库里的**：

| 表 | 含义 |
| --- | --- |
| `biz_favorite` | 用户-商品 的显式偏好 |
| `biz_order` | 用户-商品 的强偏好（真金白银） |
| `biz_product.view_count` | 弱偏好 |

```
用户-物品矩阵 → 找相似用户 → 推荐他们交互过、而当前用户没见过的
```

**冷启动问题**：新用户没有行为数据 → 回落到当前的热度基线。
**这就是为什么要保留基线实现**——它不是要被删掉的临时方案，而是兜底策略。

### 方案三：接外部推荐服务

`RecommendServiceImpl` 改成调用 HTTP 的实现类即可。
**Controller、VO、前端全不动。**

# 第四部分：价格评估

## 4.1 接口

```java
public interface PriceEvaluationService {
    PriceEvaluationVO evaluate(Long productId);
}
```

返回体：

| 字段 | 含义 |
| --- | --- |
| `currentPrice` | 当前标价 |
| `averagePrice` / `minPrice` / `maxPrice` | 同类参考价 |
| `sampleCount` | 样本数 |
| `level` | 偏低 / 合理 / 偏高 / 数据不足 |
| `advice` | 一句话建议 |

## 4.2 基线算法

```
样本 = 同分类 + 同成色 + 在售 + 排除自己
样本 < 3        → 「数据不足」，不给结论
偏离度 = (当前价 - 均价) / 均价
偏离 < -15%     → 「偏低」
偏离 > +15%     → 「偏高」
其余            → 「合理」
```

## 4.3 三个刻意的决定

### ① 样本不足时说"不知道"

```java
if (samples.size() < MIN_SAMPLE) {
    vo.setLevel("数据不足");
    vo.setAdvice("同类在售商品只有 " + samples.size() + " 件，样本太少，暂时无法评估");
    return vo;
}
```

如果只有 1 件同类商品，"平均价"就是那一件的价格，结论毫无意义还会误导卖家。

**「评不出来」也是一种有效结论，比硬给一个错的好。**

### ② 阈值是 ±15% 而不是 ±5%

二手商品价格离散度极大：同样的机器，激活过和没激活过能差几百块。
阈值设太小会导致几乎所有商品都被判成"偏高/偏低"，反而没有参考价值。

**±15% 是让结论"有区分度但不泛滥"的经验值** —— 换成模型时这个阈值会被回归结果取代。

### ③ 成色为空时不做这一维过滤

```java
.eq(StrUtil.isNotBlank(product.getConditionLevel()),
    Product::getConditionLevel, product.getConditionLevel())
```

不是所有品类都会填成色（数据配件类通常不填）。
**用一个空值去过滤，会把所有样本筛没。**

## 4.4 升级路径

| 现状 | 未来 |
| --- | --- |
| 同分类同成色的算术平均 | 回归模型（特征：品牌溢价、使用时长、是否拆修、是否在保） |
| 结论是三档「偏低/合理/偏高」 | 输出「预计成交价区间 + 置信度」 |
| 样本来自**在售标价** | 样本换成 `biz_order` 里的**真实成交价快照**（更有说服力） |

> 最后一条其实是个现成的改进点：`biz_order` 表里已经有
> `product_title` / `price` 的成交快照，把样本从"大家标多少"换成"实际成交多少"，
> 准确度会明显提升。留作后续迭代。

# 第五部分：信誉评级

## 5.1 接口

```java
public interface CreditRatingService {
    CreditRatingVO rating(Long userId);
}
```

## 5.2 打分公式

```
score = 60                              起步分
      + min(成交数, 10) × 3             成交是最强正向信号，最多 +30
      + min(发布数, 5)  × 1             持续经营行为，最多 +5
      - min(被举报成立数, 5) × 10       违规是强负向信号，最多 -50
最终 clamp 到 [0, 100]

≥ 90 优秀 / ≥ 75 良好 / ≥ 60 一般 / < 60 较差
```

## 5.3 四个设计决定

### ① 用「成交数」而不是「发布数」做主信号

发布数谁都能刷（发一堆再删掉），**成交数是真金白银的行为**——
有人愿意付钱，说明这个卖家真的能交付。

### ② 各项都有上限

```java
private static final int SOLD_CAP = 10;      // 成交加分封顶
private static final int REPORT_CAP = 5;     // 举报扣分封顶
```

不封顶的话会有两个问题：
- 老用户刷到几百分，等级失去意义
- 一次事故把新用户打到负数

### ③ 各维度单独返回，不只给一个总分

```java
vo.setSoldCount(soldCount);
vo.setProductCount(productCount);
vo.setReportCount(reportCount);
vo.setDescription(describe(...));
```

**只给分数等于让人猜。** "较差"是因为成交太少还是被举报过？
这两种情况的改进方式完全不同。

### ④ 没有商品时跳过举报查询

```java
if (productIds.isEmpty()) {
    return 0;
}
```

不跳的话会拼出 `IN ()` 这种空条件，轻则报错重则扫全表。

## 5.4 已知问题（诚实列出）

| 问题 | 影响 |
| --- | --- |
| 没有时间衰减 | 三年前的一次举报和上个月的一样扣分 |
| **没有买家评价** | 本项目没做评价功能，"东西好不好"这个最关键维度缺了 |
| 阈值是拍的 | 60 起步、每单 +3，没有数据支撑 |
| 新用户吃亏 | 注册就是 60 分「一般」，容易让人觉得不靠谱 |

**这些恰恰说明了为什么它叫「基线」而不是「实现」** ——
真正的信誉体系需要大量历史数据和回测才能把权重定下来。

## 5.5 为什么现在就定义接口

这是本文档最想强调的一点：

> **数据从第一天就该开始攒。**
>
> 订单、举报记录已经在库里了。等真的要做模型时，
> 发现历史数据没留、要重新开始攒，才是最麻烦的。
>
> 而且 `report` 表目前没有 `seller_id` 冗余字段，现在查"某卖家的被举报数"
> 要先取商品 id 集合再 `IN` 查询。**如果早知道要做信誉体系，
> 这个字段第一天就该加上** —— 这就是"设计时预留"的实际价值。

## 6.2 边界行为

| 请求 | 结果 | 说明 |
| --- | --- | --- |
| `price-evaluation/999999` | `code=3001 商品不存在` | 主体资源不存在 → 报错 |
| `credit/999999` | `code=2003 用户不存在` | 同上 |
| `recommend/similar/999999` | `code=200`，返回 0 条 | **推荐位不报错** |
| `recommend/hot?limit=99999` | 返回 20 条 | 上限生效 |

**注意第 3 行和第 1 行的对比** —— 同一个"资源不存在"，
在主体接口里要报错，在辅助接口里要静默降级。**这是刻意的。**

## 6.3 测试与覆盖率

新增 17 个单元测试：

| 测试类 | 数量 | 覆盖率 |
| --- | --- | --- |
| `RecommendServiceImplTest` | 4 | **100%** |
| `PriceEvaluationServiceImplTest` | 6 | 93% |
| `CreditRatingServiceImplTest` | 7 | 98% |

重点覆盖的是**边界和降级行为**，而不是"排序准不准"：

- limit 传 99999 / 0 / 负数
- 商品不存在时返回空列表而不是异常
- 样本 2 件时说"数据不足"
- 价格恰好卡在 ±15% 边界上算「合理」
- 成交/举报加分扣分都能封顶
- 没有商品时不去查举报表

> 后端总测试数 58 → **75 个**，总体覆盖率 36.3% → **41.9%**。

## 6.4 写测试时又踩了一次 TableInfo 的坑

`.select(Product::getId)` 和 `.eq(Product::getUserId, ...)` 的**解析时机不同**：

| 方法 | 解析时机 | 不初始化 TableInfo 的后果 |
| --- | --- | --- |
| `.eq(...)` | 懒解析（拼 SQL 时才查列名） | 可能碰巧能过 |
| `.select(...)` | **立即解析** | 直接抛 `can not find lambda cache` |

所以只用了 `eq` 的测试不初始化也能跑，加了 `select` 的那个立刻就炸。
解决办法和之前一样——在 `@BeforeAll` 里手动 `TableInfoHelper.initTableInfo`。

# 第七部分：答辩问答准备

## 7.1 "你这个系统以后要加智能推荐，好加吗？"

> 好加，而且现在就能调。
>
> `/api/extension/recommend/similar/{id}` 已经在跑了，只是算法是基线版——
> 同分类按收藏数和浏览量排序，本质上是"排行榜"而不是真正的推荐。
>
> 但**接口和 Controller 已经稳定了**：换算法只需要写一个新的
> `RecommendService` 实现类，Controller、返回结构、前端一行都不用改。
>
> 数据也是现成的：`biz_favorite` 有用户-商品的偏好，
> `biz_order` 有成交这种强偏好，可以直接用来做协同过滤。
> 新用户冷启动就回落到现在的热度基线——这也是为什么基线实现不该删掉，
> 它是兜底策略。

## 7.2 "价格评估是怎么算的？"

> 基线版是取同分类、同成色、在售商品的价格算平均，再看当前标价偏离多少。
>
> 有三个刻意的设计：
> **一是样本少于 3 件时直接说"数据不足"** —— 只有 1 件同类商品的话，
> "平均价"就是那一件的价格，结论没有意义还会误导卖家；
> **二是阈值取 ±15%** —— 二手商品价格离散度本来就大，阈值太严会导致
> 几乎所有商品都被判成偏高偏低；
> **三是成色为空时不做这一维过滤** —— 不是所有品类都填成色，
> 用空值过滤会把样本筛没。
>
> 后续改进方向是把样本从"大家标多少"换成 `biz_order` 里的**实际成交价快照**，
> 这个数据已经在库里了。

## 7.3 "信誉评级是不是随便给个分？"

> 不是，每个维度都对应真实数据：成交数查 `biz_order` 里已完成的订单，
> 发布数查商品表，被举报数是查这个人的商品上"处理成立"的举报记录。
>
> 但我要诚实说它的不足：**没有时间衰减**，三年前的举报和上个月的一样扣分；
> **没有买家评价**，因为项目没做评价功能——这其实是最大的缺口，
> "东西好不好"是信誉里最关键的维度；**权重是我拍的**，没有数据支撑。
>
> 所以它叫"基线"不叫"实现"。真正的信誉体系需要大量历史数据和回测
> 才能把权重定下来。
>
> 而且这里有个更实际的教训：`report` 表当初没加 `seller_id` 冗余字段，
> 现在查"某卖家被举报几次"要先取商品 id 集合再 `IN` 查询。
> **如果设计时就规划了信誉体系，这个字段第一天就该加上** ——
> 这正是"预留"真正的价值：不是把代码写好放那儿，而是**提前把数据结构留对**。

## 7.4 这一节的通用价值

面试时如果被问"你的项目可拓展性怎么样"，**别说"我用了分层架构所以可拓展"**——
那是一句没有信息量的话。

要说的是：

```
① 我预留了哪几个扩展点（具体到接口名）
② 现在跑的是什么（基线实现，能演示）
③ 换实现要改哪些文件（具体到"只改实现类"）
④ 哪些数据已经准备好了（哪张表）
⑤ 哪些数据还没准备好（诚实说明，比如 report 缺 seller_id）
```

**第 ⑤ 条最重要** —— 能看出"预留"是走过脑子的，不是模板。
