## 1.2 交易链路终于闭环了

```
卖家发布 ──► 平台审核 ──► 上架 ──► 买家浏览 ──► 收藏 / 留言咨询
                                                        │
                                                        ▼
                                                  下单（待确认）
                                                        │
                                          ┌─────────────┴─────────────┐
                                          │                           │
                                    卖家确认                     卖家不处理/买家取消
                                          │                           │
                                     已确认(1)                   已取消(3) / 已关闭(4)
                                          │
                                    买家确认完成
                                          │
                                     已完成(2) ──► 商品标记为已售出
```

**这是需求里"业务闭环完整"的最后一环。** 前面所有功能都是"信息流转"，只有订单是"交易成立"。做完整条链路从"发布"到"成交"都能在界面上走通。

## 1.3 为什么订单是最难的一块

前几个模块都是"操作自己的数据"或"操作商品"，而订单有三个特殊性：

| 特殊性 | 后果 |
| --- | --- |
| **涉及两个人** | 每一步都要判断"你是谁"，而且买家和卖家的权限完全不同 |
| **状态不可逆** | 点错"确认完成"就回不去了，商品也变成已售出 |
| **会改动商品状态** | 订单完成后商品要下架，这个联动漏了就会"一物二卖" |

# 第二部分：数据模型 —— 订单为什么要存快照

## 2.1 三个快照字段

```java
/**
 * 订单实体，对应 biz_order 表。
 * <p>
 * 注意 product_title / product_cover / price 三个字段存的是**下单那一刻的快照**。
 * 为什么不像其他表那样只存 product_id 然后 JOIN？
 * <p>
 * 因为订单是"交易凭证"。商品后来被卖家改了标题、换了图片、改了价格，
 * 订单里显示的必须还是**当时约定的内容**，否则买卖双方对账时各说各话。
 */
private String productTitle;
private String productCover;
private BigDecimal price;
```

### 不存快照会发生什么

```
10:00  买家下单，商品标题「iPhone 14 Pro 256G 暗紫色」，价格 4899
10:05  卖家把标题改成「iPhone 14 Pro 256G 暗紫色 送充电器」
10:10  卖家把价格改成 5299
11:00  买家打开订单页 —— 显示「...送充电器」，价格 5299
```

**买家会以为卖家在他下单后涨价了。** 而实际上卖家只是改了商品信息。

这在真实交易里是会吵架的：

> 买家："我下单的时候是 4899！"
> 卖家："你现在看就是 5299 啊，我的商品页写得清清楚楚。"
> —— 平台没有凭证可以判。

**存了快照之后，订单永远显示 4899，因为那是"成交时的约定"。**

这是本项目**第三次**用快照的思路（前两次：审核记录存 `product_title`/`admin_name`、审核时的角色信息）：

| 表 | 快照字段 | 为什么 |
| --- | --- | --- |
| `biz_audit_record` | `product_title`、`admin_name` | 追溯"当时谁对什么做了什么" |
| `biz_order` | `product_title`、`product_cover`、`price` | 交易凭证"当时约定的内容" |

> **凡是"历史记录"性质的表，都要问一句："这条记录将来需要还原当时的什么？"**
> 需要还原的字段，就要存快照。

## 2.2 哪些字段**不**存快照

注意这里有个对比：`productTitle` 存了快照，但**买家卖家的昵称没有存**：

```xml
LEFT JOIN sys_user b ON b.id = o.buyer_id
LEFT JOIN sys_user s ON s.id = o.seller_id
```

**为什么昵称可以 JOIN 而标题必须快照？**

因为**昵称改了不影响交易内容**。张三把昵称从"张三"改成"张三同学"，对这笔交易没有任何影响——订单里显示哪个都是他本人。

而标题和价格**是交易标的和金额**，改了就是另一笔交易了。

> **判断标准：这个字段变了，会不会让"当时的约定"变得不成立？**
> 会 → 存快照；不会 → 外键关联就够了。

## 2.3 订单号为什么单独一个字段

```java
/** 订单号，对外展示用，用户报问题时说这个比说 id 清楚 */
private String orderNo;
```

**为什么不直接用主键 id 做对外标识？**

| | 用 `id` | 用 `orderNo` |
| --- | --- | --- |
| 用户看到 | "订单 3" | "订单号 OD20261019180218..." |
| 泄漏信息 | 平台总共 3 笔订单 | 看不出总量 |
| 排查沟通 | "你说的 3 是哪个 3？" | 一串唯一号码，没有歧义 |

**主键是数据库的内部标识，不应该直接暴露给用户。** 尤其是自增主键，它会泄漏业务量（订单 id 到了 100 万，说明平台成交了 100 万单）。

# 第三部分：状态机 —— 谁在什么状态下能做什么

## 3.1 五个状态

```java
public enum OrderStatus {
    PENDING(0, "待确认"),    // 买家已下单，等卖家响应
    CONFIRMED(1, "已确认"),  // 卖家接单了，等双方线下交易
    FINISHED(2, "已完成"),   // 交易完成，终态
    CANCELED(3, "已取消"),   // 一方主动取消，终态
    CLOSED(4, "已关闭");     // 平台介入关闭，终态
}
```

**为什么"已取消"和"已关闭"要分开？**

| | 已取消(3) | 已关闭(4) |
| --- | --- | --- |
| 谁发起 | **用户**（买家或卖家） | **平台**（管理员下架商品 / 删除商品） |
| 用户看到 | "订单被对方取消了" | "商品被平台下架，订单自动关闭" |
| 责任方 | 交易双方之间的事 | 平台对内容的处置 |

**这两种情况给用户的感受完全不同**，混在一个状态里会让用户搞不清"到底是我被拒了，还是商品出问题了"。

**状态的定义本身就是产品设计。** 多一个状态不是多一份复杂度，而是让用户能准确理解发生了什么。

## 3.2 完整的权限与状态对照

这是整个模块最核心的一张表：

| 操作 | 谁能做 | 前置状态 | 结果 | 商品变化 |
| --- | --- | --- | --- | --- |
| 下单 | 任何登录用户（非卖家） | 商品在售 + 无进行中订单 | 0 待确认 | 不变 |
| 卖家确认 | **仅卖家** | 0 | 1 已确认 | 不变 |
| 取消 | **买卖双方都可以** | 0 或 1 | 3 已取消 | 不变 |
| 买家确认完成 | **仅买家** | 1 | 2 已完成 | **→ 已售出** |
| 平台关闭 | 管理员（下架商品时触发） | 0 或 1 | 4 已关闭 | → 已下架 |

**每一个操作都是"双重校验"：先校验你是谁（权限），再校验现在能不能做（状态）。** 缺任何一半都有漏洞：

- 只校验权限不校验状态 → 可以对一个已完成的订单再点"确认"
- 只校验状态不校验权限 → 买家可以自己确认自己的订单（等于绕过卖家）

代码里是分成两个独立的方法：

```java
/** 校验身份 */
private void requireParticipant(Order order, Long userId) { ... }

/** 校验状态 */
private void requireStatus(Order order, OrderStatus expected, String action) {
    if (!expected.getCode().equals(order.getStatus())) {
        throw new BusinessException(ResultCode.ORDER_STATUS_ILLEGAL,
                "当前状态为「" + OrderStatus.descOf(order.getStatus()) + "」，无法" + action);
    }
}
```

实测验证：

```
=== O7. buyer tries to confirm ===       {"code":5005,"message":"只有卖家可以确认订单"}
=== O8. admin (third party) tries ===    {"code":5005,"message":"只有卖家可以确认订单"}
=== O11. seller tries to finish ===      {"code":5005,"message":"只有买家可以确认完成"}
=== O14. cancel a FINISHED order ===     {"code":5002,"message":"该订单当前状态为「已完成」，无法取消"}
```

**注意 O8**：连管理员都不能确认订单。这是刻意的——管理员的能力是"处置违规内容"，不是"替用户完成交易"。**权限要给得准，而不是给得大。**

## 3.3 `actions` 由后端算好交给前端

```java
/**
 * 可用操作。
 * <p>
 * 为什么后端算好而不是让前端判断？因为状态机规则（谁能做什么、
 * 在什么状态下能做）是业务知识，应该只有一处实现。
 * 前端照着布尔值渲染按钮即可，规则改了不用动前端。
 */
@Data
public static class OrderActions {
    private Boolean canConfirm = false;
    private Boolean canCancel = false;
    private Boolean canFinish = false;
    private Boolean canViewProduct = false;
    private Boolean canComment = false;
}
```

```java
private void fillView(OrderVO vo, Long userId) {
    vo.setStatusText(OrderStatus.descOf(vo.getStatus()));

    boolean isBuyer = vo.getBuyerId().equals(userId);
    vo.setMyRole(isBuyer ? "BUYER" : "SELLER");

    OrderVO.OrderActions actions = new OrderVO.OrderActions();
    Integer status = vo.getStatus();
    if (OrderStatus.PENDING.getCode().equals(status)) {
        // 待确认：卖家能确认，两边都能取消
        actions.setCanConfirm(!isBuyer);
        actions.setCanCancel(true);
    } else if (OrderStatus.CONFIRMED.getCode().equals(status)) {
        // 已确认：买家能确认完成，两边都能取消
        actions.setCanFinish(isBuyer);
        actions.setCanCancel(true);
    }
    vo.setActions(actions);
}
```

**这份逻辑是整个模块里最不该被复制到前端的。** 因为是同一份数据、同一个状态，**买家看到 3 个按钮、卖家看到 2 个按钮、已完成的订单两边都看不到任何操作按钮**——全由后端一处算出来。

实测：

```
=== O5. buyer view (status=0) ===   canConfirm=False canFinish=False canCancel=True
=== O6. seller view (status=0) ===  canConfirm=True  canFinish=False canCancel=True
=== O10. buyer view (status=1) ===  canFinish=True   canCancel=True
=== O21. terminal states ===        canConfirm=False canCancel=False canFinish=False
```

**同一份订单数据，不同的人看到不同的操作。** 这就是"服务端按身份定制响应"。

> 这个模式在留言模块也用过（`canDelete`），在这里被系统化了。
> **凡是"这个按钮该不该显示"取决于业务规则的地方，都适合这么做。**

## 3.4 为什么只有买家能点"确认完成"

```java
// 只有买家能确认完成。
// 为什么不让卖家也能点？因为"东西到手了"这件事只有买家知道，
// 让卖家能单方面结束订单，等于给了他一键把交易标记为完成的权力。
if (!order.getBuyerId().equals(userId)) {
    throw new BusinessException(ResultCode.NOT_ORDER_PARTICIPANT, "只有买家可以确认完成");
}
```

**如果卖家也能点会发生什么？**

```
卖家：东西放你楼下了，你确认下完成
买家：（还没到）稍等
卖家：[点击"确认完成"]  ← 订单完成，商品变成已售出，从列表消失
买家：（到了发现东西不对）我要申请售后退款
平台：订单状态是"已完成"，按流程不支持售后
```

**单方面的完成权 = 单方面定义"交易结束"。** 这在有担保交易的平台是致命的。

那**卖家的利益怎么保障**？通过"取消订单 + 拒绝接单"的路径：卖家觉得买家不靠谱，可以在确认前取消。**但他不能替买家宣布交易成功。**

> 二手平台是线下面交，没有平台资金担保，所以规则要更保守：
> **谁承担风险，谁掌握"完成"的按钮。**

## 3.5 取消按钮背后的产品取舍

**为什么买卖双方都能取消？** 因为线下交易的变数太多了：

| 场景 | 谁需要取消 |
| --- | --- |
| 买家买到别的了 | 买家 |
| 买家联系不上卖家 | 买家 |
| 商品其实已经卖给别人了 | 卖家 |
| 卖家觉得买家不靠谱 | 卖家 |
| 约定的时间地点谈不拢 | 双方 |

**如果只有一方能取消，另一方就会被"锁死"**——比如卖家发现商品有隐藏问题不想卖了，却取消不了订单，只能一直挂着，买家还傻等。

**代价是"谁都能取消"意味着订单可能被轻易放弃。** 但对比"一方被锁死"，这个代价可以接受。**而且取消是有记录的**：原因、时间、谁取消的——靠事后追溯来约束，而不是靠事前禁止。

# 第四部分：五条关键业务规则

## 4.1 不能买自己的商品

```java
if (product.getUserId().equals(buyerId)) {
    throw new BusinessException(ResultCode.CANNOT_BUY_SELF);
}
```

**为什么？** 和"不能收藏自己的商品"、"不能给自己商品留言"是同一类问题：**防止卖家刷数据。**

在订单场景下更严重：卖家自己下单自己确认完成，商品的 `status` 会变成"已售出"。**这就制造了一条虚假的成交记录**——而且商品从列表消失了，等于下架了自己的商品。

## 4.2 一件商品同时只能有一个进行中的订单

```java
// 二手商品是"一件"，不能同时卖给两个人。
// 只要已经有一个待确认或已确认的订单，就不允许再下单。
Long activeCount = orderMapper.selectCount(Wrappers.<Order>lambdaQuery()
        .eq(Order::getProductId, product.getId())
        .in(Order::getStatus, OrderStatus.activeCodes()));
if (activeCount > 0) {
    throw new BusinessException(ResultCode.PRODUCT_HAS_ACTIVE_ORDER);
}
```

```java
/**
 * 「进行中」的状态。
 * 二手商品是"一件"东西，不能同时卖给两个人。
 */
public static List<Integer> activeCodes() {
    return List.of(PENDING.getCode(), CONFIRMED.getCode());
}
```

**这是二手平台和电商平台最大的区别。** 京东上库存 100 件，100 个人可以同时下单；二手平台商品就一件，两个人同时下单必然有一个要失败。

实测：

```
=== O4. duplicate order on same product ===
{"code":5006,"message":"该商品已有进行中的订单，请等待卖家处理"}
```

### 诚实说明并发窗口

代码注释里我写清了这一点：

```java
// 注意这里是"事后检查"，理论上存在并发窗口（两个人同时通过检查），
// 但下单是低频操作、影响也仅仅是卖家收到两个订单，他挑一个确认就行。
// 真要做到严格互斥，需要给商品加乐观锁或分布式锁 —— 对本项目属于过度设计。
```

```
时刻 T1: 买家A 检查"有进行中订单吗" → 没有
时刻 T2: 买家B 检查"有进行中订单吗" → 没有
时刻 T3: 买家A 下单成功
时刻 T4: 买家B 下单成功        ← 两个进行中的订单
```

**严格禁止需要加锁。** 但我判断不值得，理由是：

| 维度 | 评估 |
| --- | --- |
| 发生概率 | 极低（要两个人在毫秒级内同时点下单） |
| 影响程度 | 轻微（卖家收到两个订单，他确认一个，另一个取消即可） |
| 加锁成本 | 乐观锁字段 + 重试逻辑，或引入 Redis |

**这个取舍的关键是：我明确知道漏洞存在、知道后果、并且判断可以接受。** 这和"没想到所以没做"是完全不同的两件事。

> 答辩时如果被问到这个，答"我知道有并发窗口，但我评估了概率和影响，
> 认为加锁的复杂度不值得"——比"并发不会有问题"强得多。

## 4.3 取消之后商品必须重新可售

```java
changeStatus(orderId, OrderStatus.CANCELED, ..., false);
// 不需要动商品：商品本来就是"在售"状态，订单取消后自然又可以被人下单
```

**这里的关键是"什么都不用做"。** 因为下单时**没有把商品状态改成"锁定"**——商品始终是"在售"，锁的是"有没有进行中的订单"。

实测：

```
=== O17. buyer cancels ===          {"code":200,"message":"订单已取消"}
=== O18. lisi orders product 2 AGAIN ===   new order id = 3   ← 成功
```

**如果当初设计成"下单即把商品改为已售出"，取消时就必须记得改回来。** 一旦漏了，商品就永远卡在"已售出"，再也没人能买。**"少改状态"是减少 bug 的通用手段。**

## 4.4 完成时商品才标记为已售出

```java
// 交易完成 → 商品标记为已售出，从公开列表里消失
productMapper.update(null, Wrappers.<Product>lambdaUpdate()
        .set(Product::getStatus, ProductStatus.SOLD.getCode())
        .set(Product::getUpdateTime, LocalDateTime.now())
        .eq(Product::getId, order.getProductId()));
```

**只有真正成交了才改商品状态。** 这样"已售出"这个状态是可信的——用户看到"已售出"，就知道确实卖掉了，而不是"有人下了单但还没成交"。

实测：

```

=== O13. public list ===         iPhone 关键词的公开列表 total = 1（原本 2 件，售出那件消失了）
```

## 4.5 通知：每一步都要让"对方"知道

订单流程有多个需要通知的节点：

| 事件 | 通知谁 | 内容要点 |
| --- | --- | --- |
| 买家下单 | 卖家 | 有人想买你的商品，请尽快确认或取消 |
| 卖家确认 | 买家 | 请按约定联系卖家完成交易 |
| 一方取消 | **对方** | 谁取消的 + **为什么** |
| 买家完成 | 卖家 | 交易已完成，商品已标记售出 |
| 平台下架 | **双方** | 商品被下架，订单自动关闭 + 原因 |

```java
// 通知对方 —— 让谁取消的、为什么取消都写清楚，
// 否则对面只看到"订单没了"，很容易产生纠纷
Long notifyUser = isBuyer ? order.getSellerId() : order.getBuyerId();
String who = isBuyer ? "买家" : "卖家";
notificationService.send(notifyUser, NotificationType.ORDER,
        "订单已取消",
        who + "取消了「" + order.getProductTitle() + "」的订单。原因："
                + StrUtil.blankToDefault(reason, "未填写原因"),
        orderId);
```


# 第五部分：订单号怎么生成

```java
private String generateOrderNo() {
    // 格式：OD + 年月日时分秒毫秒 + 4 位随机数
    // 时间戳保证基本有序（方便按号排序排查），随机数避免同一毫秒内碰撞
    return "OD" + DateUtil.format(new Date(), "yyyyMMddHHmmssSSS") + RandomUtil.randomNumbers(4);
}
```

生成结果：`OD202610191802189607857`

拆开看：

| 部分 | 内容 | 作用 |
| --- | --- | --- |
| `OD` | 前缀 | 一眼看出这是订单号（和商品、用户的 id 区分开） |
| `20261019180218960` | 时间戳到毫秒 | 可按时间排序，排查日志时很有用 |
| `7857` | 4 位随机数 | 同一毫秒内不碰撞 |

**长度 23 字符，数据库字段是 `VARCHAR(32)`，留了余量。**

### 为什么不用自增、不用 UUID

| 方案 | 问题 |
| --- | --- |
| 自增数字 | 泄漏业务量（订单号到 100 万 = 成交 100 万单），且能被猜 |
| UUID | 太长（36 字符），用户抄写和口述都痛苦 |
| 时间戳 + 随机 | 有序、可读、够短、难猜 ✅ |

### 撞了怎么办

```java
try {
    orderMapper.insert(order);
} catch (DuplicateKeyException e) {
    // order_no 上的唯一索引撞了。概率极低，但撞上时给用户一个明确的提示，
    // 而不是抛出一句看不懂的数据库错误
    throw new BusinessException("订单号生成冲突，请重试一次");
}
```

`order_no` 上有唯一索引。同一毫秒内生成两个相同随机数的概率是 1/10000，**加上唯一索引兜底，就是"理论上不可能出现重复订单号"。**

**即使概率极低，也要处理。** 因为一旦发生，用户会看到一句 "Duplicate entry 'OD2026...' for key 'uk_order_no'" 的数据库错误——**完全看不懂，也帮不了他。**

# 第六部分：与已有模块的联动

## 6.1 管理端下架商品 → 自动关闭进行中的订单

这是本阶段最有价值的一处联动。**如果不做会怎样：**

```
1. 买家下单，卖家确认 → 订单进入"已确认"
2. 管理员发现这个商品违规，强制下架
3. 商品从平台消失了，但订单还是"已确认"
4. 买家还在等卖家联系他面交 —— 而商品已经被平台删了
```

**买卖双方都在蒙在鼓里。** 他们在按一个已经不存在的交易继续安排。

```java
// 商品被下架了，它上面没走完的订单不能再挂着 ——
// 否则买家还在等交易，卖家却已经被平台下架了商品。
orderService.closeActiveOrdersByProduct(productId, dto.getReason());
```

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void closeActiveOrdersByProduct(Long productId, String reason) {
    List<Order> actives = orderMapper.selectList(Wrappers.<Order>lambdaQuery()
            .eq(Order::getProductId, productId)
            .in(Order::getStatus, OrderStatus.activeCodes()));
    if (actives.isEmpty()) {
        return;     // ← 没有进行中的订单就直接返回，不用发无用的 UPDATE
    }

    orderMapper.update(null, Wrappers.<Order>lambdaUpdate()
            .set(Order::getStatus, OrderStatus.CLOSED.getCode())
            .set(Order::getCancelReason, StrUtil.blankToDefault(reason, "商品已被平台下架"))
            .set(Order::getUpdateTime, LocalDateTime.now())
            .eq(Order::getProductId, productId)
            .in(Order::getStatus, OrderStatus.activeCodes()));

    // 通知买卖双方。商品下架是平台行为，两边都该知道，
    // 否则他们还在等着跟对方交易
    for (Order o : actives) {
        String content = "「" + o.getProductTitle() + "」已被平台下架，相关订单已自动关闭。原因："
                + StrUtil.blankToDefault(reason, "商品已被平台下架");
        notificationService.send(o.getBuyerId(), NotificationType.ORDER, "订单已关闭", content, o.getId());
        notificationService.send(o.getSellerId(), NotificationType.ORDER, "订单已关闭", content, o.getId());
    }
}
```

三个细节：

**① 先查再改。** 因为要通知具体的人，得先知道有哪些订单。而且没有订单时直接返回，省掉一次无用的 UPDATE。

**② 通知双方，不是只通知买家。** 商品下架是平台行为，卖家也需要知道"我的商品被下架了，相关订单也关了"。

**③ 用 `CLOSED(4)` 而不是 `CANCELED(3)`。** 因为这不是"用户取消"，而是"平台处置"——状态要如实反映原因。

实测：

```
=== O20. admin force off-shelves product 2 ===
{"code":200,"message":"已强制下架，并已通知卖家"}

=== O21. buyer sees the order ===
  order[3] 已关闭  canConfirm=False canCancel=False canFinish=False
      reason: 商品描述与实际不符，强制下架
```

**订单被关闭了，而且关闭原因就是管理员填的原因** —— 用户能看懂发生了什么。

## 6.3 通知的 `bizId` 语义差异

项目里有两种 `bizId` 用法，前端必须区分：

| 通知类型 | `bizId` 是什么 | 点击跳转 |
| --- | --- | --- |
| 1 审核结果 | 商品 ID | `/product/{id}` |
| 3 留言回复 | 商品 ID | `/product/{id}` |
| **2 订单状态** | **订单 ID** | **`/user/orders`** |

```js
// 点击通知跳到对应的页面：
//   1 审核结果 / 3 留言回复 → bizId 是商品ID → 商品详情页
//   2 订单状态            → bizId 是订单ID → 我的订单页
if (item.bizId) {
  visible.value = false
  if (item.type === 2) {
    router.push('/user/orders')
  } else if (item.type === 1 || item.type === 3) {
    router.push(`/product/${item.bizId}`)
  }
}
```

**为什么订单通知不跳商品详情？** 因为**订单已经结束了**（已完成/已取消/已关闭），跳到商品页没什么用；用户需要看的是"订单现在什么状态、原因是什么"。

**同一个 `bizId` 字段承载不同含义，靠 `type` 区分。** 这是通用做法，但一定要在两端都写清楚——否则将来加通知类型时很容易跳错页面。

## 6.4 一条文案的修正

测试时我发现了这个通知：

```
原因：商品已被平台下架：商品描述与实际不符，强制下架
```

**"商品已被平台下架"出现了两遍。** 原因是我在调用时拼了一段前缀：

```java
// ❌ 以前
orderService.closeActiveOrdersByProduct(productId, "商品已被平台下架：" + dto.getReason());
```

而通知模板里本来就有这句话：

```java
"「" + o.getProductTitle() + "」已被平台下架，相关订单已自动关闭。原因：" + reason
```

**修正是"谁负责组织这句话"要明确**：

```java
// ✅ 现在：只传原因，"商品已被平台下架"由模板统一组织，
// 否则拼出来会变成"原因：商品已被平台下架：xxx"这种重复的前缀
orderService.closeActiveOrdersByProduct(productId, dto.getReason());
```

修正后：

```
「机械革命极光pro」已被平台下架，相关订单已自动关闭。原因：商品描述与实际不符，强制下架
```

> **拼接多段文案时，先想清楚"哪一层负责哪一段"。**
> 最常见的文案 bug 就是相邻两层各拼了一部分，结果重复或矛盾。

# 第七部分：前端实现

## 7.1 双视角：我买到的 / 我卖出的

```js
const role = ref('BUY')

const query = reactive({
  current: 1,
  size: 10,
  role: 'BUY',
  status: null
})
```

```sql
<choose>
    <when test="query.role == 'SELL'">
        AND o.seller_id = #{userId}
    </when>
    <otherwise>
        AND o.buyer_id = #{userId}
    </otherwise>
</choose>
```

**为什么用两个 Tab 而不是一个列表混在一起？**

因为**同一个订单，买家和卖家看到的重点完全不同**：

| | 买家关心 | 卖家关心 |
| --- | --- | --- |
| 首要问题 | "我的东西什么时候到" | "有没有人要买" |
| 该做的操作 | 确认完成 | 确认接单 |
| 对方是谁 | 卖家 | 买家 |

**混在一起会让"我该做什么"变得模糊。** 分开之后，用户点进对应 Tab 就知道自己该干什么。

Tab 上还带了待处理数量的徽标：

```js
/** 两个视角的待处理数量，显示在 Tab 上提示"有事要办" */
async function loadCounts() {
  const [buy, sell] = await Promise.all([
    // 买家关心"已确认"（该去交易了），卖家关心"待确认"（该处理了）
    pageOrders({ current: 1, size: 1, role: 'BUY', status: 1 }),
    pageOrders({ current: 1, size: 1, role: 'SELL', status: 0 })
  ])
  buyCount.value = Number(buy.total)
  sellCount.value = Number(sell.total)
}
```

**注意买家和卖家关心的状态是不同的**：

- 买家关心 `status=1`（已确认）—— 卖家接单了，我该去面交了
- 卖家关心 `status=0`（待确认）—— 有人下单了，我该处理了

**如果两边都用同一个状态计数，卖家会看到一堆"该我去交易"的提示——而实际上那些单子他还没接。** 这类细节决定了功能是"能用"还是"好用"。

`Promise.all` 是第二次用到了（第一次在后台的 Tab 计数），两个请求并发，省一半往返时间。

## 7.2 按钮完全由 `actions` 驱动

```vue
<div class="order-actions">
  <el-button size="small" @click="goProduct(order.productId)">查看商品</el-button>
  <el-button v-if="order.actions?.canComment" size="small" @click="goComment(order)">
    联系对方
  </el-button>

  <el-button v-if="order.actions?.canConfirm" size="small" type="primary" ...>
    确认接单
  </el-button>

  <el-button v-if="order.actions?.canFinish" size="small" type="success" ...>
    确认完成
  </el-button>

  <el-button v-if="order.actions?.canCancel" size="small" type="danger" plain ...>
    取消订单
  </el-button>
</div>
```

**整个模板里没有一处 `order.status === 1` 这样的判断。** 前端完全不知道状态机的规则，只负责把后端给的布尔值渲染成按钮。

**好处：**

1. 状态机规则改了（比如"允许卖家也取消已确认的订单"），**只改后端一处**，前端一个字不动
2. 前端不会出现"按钮显示了但点了报 403"的尴尬
3. 新同事看这段模板，不需要理解订单业务也能改样式

> 这是**"把判断推给最了解规则的那一层"**。前端最了解的是"怎么显示"，
> 后端最了解的是"什么时候允许做什么"。**各管各的。**

## 7.3 危险操作要"说清后果"

```js
async function handleFinish(order) {
  try {
    await ElMessageBox.confirm(
      `确认「${order.productTitle}」这笔交易已经完成吗？确认后商品会标记为已售出，且无法撤销。`,
      '确认完成',
      { type: 'warning', confirmButtonText: '确认完成' }
    )
  } catch {
    return
  }
  ...
}
```

**注意提示语的组成：**

| 部分 | 内容 | 作用 |
| --- | --- | --- |
| 具体对象 | 「联想拯救者 R9000P 游戏本」 | 用户可能有多个订单，必须指明是哪个 |
| 后果 | 商品会标记为已售出 | 让他知道这一步的影响面 |
| 不可逆 | **且无法撤销** | 最重要的警告 |

**"无法撤销"这四个字是关键。** 这个操作是不可逆的，用户必须在点之前就知道。**把不可逆的后果藏在心里、等用户发现时才说"这个改不了"——那是最糟糕的交互。**

对比"取消订单"的提示就轻得多，因为它可以重新下单：

```js
await ElMessageBox.prompt('取消原因会通知给对方，建议写清楚，避免误会', '取消订单', {...})
```

**提示语的"重量"要和操作的"重量"匹配。**

## 7.4 下单后不强制跳转

```js
await createOrder({...})
orderVisible.value = false
ElMessage.success('下单成功，等待卖家确认')

// 弹窗提示去订单页，而不是强行跳转 —— 用户可能还想再看看这个商品
try {
  await ElMessageBox.confirm('订单已提交，要去「我的订单」看看吗？', '下单成功', {
    confirmButtonText: '去看看',
    cancelButtonText: '继续浏览',
    type: 'success'
  })
  router.push('/user/orders')
} catch {
  // 用户选择继续浏览，什么都不做
}
```

**为什么不让它自动跳转？**

用户下单后可能还想：
- 再看看商品描述确认细节
- 给卖家留个言说明时间
- 收藏一下，方便后面找

**自动跳走会打断这些操作。** 给他一个选择，比替他决定更好。

**注意 `catch {}` 不能省**——`ElMessageBox.confirm` 在用户点"继续浏览"时会 reject，不捕获就会抛未处理的 Promise 异常。

## 7.5 下单按钮的显示条件

```vue
<el-button v-if="product.status === 1" type="primary" @click="openOrderDialog">
  <el-icon><ShoppingCart /></el-icon>
  立即下单
</el-button>
```

只在商品**在售（status===1）** 时显示。已售出的商品不该有下单按钮——虽然后端也会拦，但**让用户看不到注定失败的操作，比让他点了再报错好**。

```js
function openOrderDialog() {
  if (!userStore.isLogin) {
    ElMessage.warning('登录后才能下单')
    router.push({ path: '/login', query: { redirect: route.fullPath } })
    return
  }
  // 用资料里的手机号预填，省得每次手打

  orderForm.tradeLocation = product.value?.tradeLocation || ''
  orderForm.remark = ''
  orderVisible.value = true
}
```

**两个预填很关键：**

- `contact` 从用户资料里带出来 —— 用户填过一次手机号，就不该让他再填一次
- `tradeLocation` 从商品里带出来 —— 卖家写的地点通常就是要交易的地方，买家改一下就行

**好的默认值 = 用户少打字。** 这类优化几乎零成本，但体验差别很大。

# 第八部分：安全清单与验收

## 8.1 本阶段的安全设计

| 攻击手法 | 后果 | 防护 | 代码位置 |
| --- | --- | --- | --- |
| 买自己的商品 | 刷虚假成交记录 | `CANNOT_BUY_SELF` 校验 | `OrderServiceImpl.create` |
| 同一商品被两人下单 | 一物二卖 | 检查进行中订单 | `OrderServiceImpl.create` |
| **买家自己确认订单** | 绕过卖家，虚假成交 | 只有卖家能确认 | `OrderServiceImpl.confirm` |
| **卖家自己标记完成** | 单方面宣布交易结束 | 只有买家能确认完成 | `OrderServiceImpl.finish` |
| 第三方操作别人订单 | 破坏他人交易 | `NOT_ORDER_PARTICIPANT` 双重校验 | 每个流转方法 |
| 撤销已完成的订单 | 破坏交易凭证 | 终态不可流转 | `requireStatus` |
| 前端传别人的订单 ID | 越权 | 从订单行读取 buyerId/sellerId 比对 | `OrderServiceImpl` |
| 商品下架后订单悬空 | 双方继续无效交易 | 下架时自动关闭订单 + 通知双方 | `closeActiveOrdersByProduct` |
| 订单号被猜 | 遍历他人订单 | 时间戳 + 随机数 + 唯一索引 | `generateOrderNo` |
| 自增 ID 暴露业务量 | 泄漏平台规模 | 对外只暴露 `orderNo` | `Order.orderNo` |

**最值得强调的是第二条和第四条**：它们防的不是"外部攻击"，而是**交易双方互相占便宜**。平台类系统的权限设计，很多时候防的是"平台用户之间的不当得利"。

## 8.2 验收清单（24 项实测）

**下单（4 项）**

| # | 场景 | 期望 | 实测 |
| --- | --- | --- | --- |
| O1 | 匿名下单 | 401 | ✅ |
